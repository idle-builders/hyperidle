## Findings by severity

### CRITICAL
None.

### WARNING

**W1 — `--write-coverage-allowlist` cannot reuse `writeAllowlist()`'s filter; the plan under-specifies the seed mechanism.** The existing `writeAllowlist()` (guard ll.274-283) writes files matching `isStubDirty && !hasAbsentSkipIf`. The coverage-debt seed is a *different* predicate: files with `missingHarnesses(source).length > 0`. The plan says "seed it now with the AR3–AR6 currently-stubbed files (the same five already on the stub allowlist)" and asserts the two sets are identical today. **That coincidence is load-bearing and unverified.** The five stub-allowlisted files (`AL6-*`×4, `ah5-*`) are stub-dirty; whether each *also* fails `missingHarnesses` depends on whether they happen to declare all four `requireHarness` lanes — most AL6/ah5 tests gate a single harness, so they almost certainly DO fail coverage, but the builder must derive the coverage-debt list from the *coverage* predicate (`--write-coverage-allowlist` running `missingHarnesses` over selected files), **not** hand-copy the stub list on the plan's say-so. If a stub-allowlisted file already declares all four (unlikely but possible), hand-copying would falsely allowlist a clean-on-coverage file → instant `debt paid, remove` FAIL on `main`. **Build the writer to compute the set; do not seed by copy.**

**W2 — `declaredHarnesses` false-positive surface on the stub-allowlisted files themselves.** The coverage rule (§1) runs over *every* `isHarnessIntegrationPath` file, including the five staged ones. Their bodies contain `requireHarness("claude")` etc. — the regex `requireHarness\s*\(\s*([^)]*)\)` then `["']([a-z-]+)["']` will parse those. Fine. But two edge cases the builder must cover with the unit tests the plan already calls for (task 2): (a) a `requireHarness("claude", "codex")` *multi-arg* call — the inner `[^)]*` capture + `matchAll(HARNESS_NAME_LITERAL)` handles it (both literals captured), good, but add a fixture for it; (b) a commented-out or string-literal `requireHarness("codex")` inside a doc comment would be falsely counted as declared — the tolerant regex cannot distinguish code from comment. This is a **false-NEGATIVE** risk (a file looks covered because a comment mentions a harness it doesn't actually gate) — the *opposite* of the bug AR2 fixes, and it weakens the gate. Low likelihood, but the plan's "tolerant regex over the file body" should acknowledge it. Mitigation is cheap: the attestation per-harness floor (§2) is the backstop — a comment-declared but un-gated harness contributes zero executed assertions → floor FAILs. **Defense-in-depth saves this; note it explicitly so the builder doesn't "fix" the regex into brittleness.**

**W3 — the coverage check does not exempt service `*.integration.test.ts`, but the predicate already does — confirm the prompt's stated false-positive concern is moot.** The prompt asks whether the coverage rule wrongly flags a unit `*.test.ts` or a web/service `*.integration.test.ts`. Ground truth: the rule runs only inside `ruleFor`, gated by `isHarnessIntegrationPath(p)` (guard l.146), and the predicate (`honest-harness-predicate.ts`) matches ONLY `…/harness/__tests__/*.integration.test.ts` + the one explicit `session-provisioning` exception. A `*.test.ts` unit (no `.integration`) and a service `*.integration.test.ts` outside `harness/__tests__/` are **never selected**. **So the false-positive class the prompt worries about cannot occur** — *provided the builder reuses `isHarnessIntegrationPath` for the coverage rule and does not widen selection.* The plan says it does ("applied to every selected file"). Good — but this is the single most important invariant to not break: **the coverage rule MUST share the exact predicate, never a looser glob.** Flag it in the task list as a non-negotiable.

**W4 — `SUPPORTED_HARNESSES` lockstep is real but only ONE direction is compile-enforced.** §0's type-assert is `type _AssertCovered = SupportedHarness extends HarnessName ? true : never`. This proves every *supported* name is a valid HarnessName. It does **NOT** prove the reverse (that the mirrored literal `SUPPORTED_HARNESSES_MIRROR` in `require-harness.ts` equals the canonical `SUPPORTED_HARNESSES` in `scripts/lib`). If someone adds `"cursor-agent"` to the canonical constant but forgets the mirror, `check` stays green and the two drift silently. The plan's prose ("structurally equal") over-claims what the single assert delivers. **Fix is trivial and the builder should add it:** a bidirectional assert — `type _M = SupportedHarness extends typeof SUPPORTED_HARNESSES_MIRROR[number] ? typeof SUPPORTED_HARNESSES_MIRROR[number] extends SupportedHarness ? true : never : never`. Since `require-harness.ts` can't import the `scripts/` constant, the mirror is unavoidable; make the *type identity* (not just one-way assignability) compile-checked. As written, the lockstep is a half-guarantee. Cheap to close; must be closed or the "single source of truth" claim is partly comment-rot — the exact failure mode §0 exists to prevent.

**W5 — `verify-attest.ts` must add `agenticExecutedByHarness` to the SIGNED payload AND `check-attestation.ts`'s `Attestation` interface, or the back-compat path silently disables the new floor forever.** The plan handles back-compat correctly in principle (`byHarness === undefined → null`, mirroring `srcHash?`/`agenticExecuted?`). But there's an ordering trap: `assertPerHarnessFloor` returns `null` on `undefined`. If the builder wires `check-attestation` to call it but forgets to write the field in `verify-attest`, **every attestation validates green with the per-harness floor permanently inert** — and nothing fails, because that IS the legacy path. There is no test that proves a *fresh* attestation carries the field. The plan's task 8 sanity-break (force codex early-return → floor RED) is the right proof, but it only works if the field is being written. **Add an explicit assertion to the build: a fresh `verify-attest` run's payload must contain `agenticExecutedByHarness` with all four keys.** Otherwise the §2 floor can ship dead exactly like AR2's original global floor was too weak — the recurrence class the amendment targets.

**W6 — codex/opencode AC2 under-proof is honestly disclosed but the per-harness floor's interaction with the fallback needs one more sentence.** §3's fallback (demote file-write → `outcome:"completed"` + real cost/tokens) is sound and matches `cli-adapter-real-binary`'s proven assertions (I read them: codex asserts `outcome==="completed"` + conditional cost; opencode asserts `completion` + `outcome==="completed"`). The plan correctly states the harness still RAN, satisfying §2's floor. **The subtle point the plan should make explicit:** the per-harness floor counts *executed assertions*, and a demoted lane still executes `expect(result.outcome).toBe("completed")` → contributes ≥1 executed assertion to the codex bucket → floor passes. Good. But if a builder demotes a lane to a *bare* `requireHarness` describe with the assertion inside a conditional that the model nondeterminism skips, the bucket could be 0 despite the lane "running." The floor counts `passed|failed`, not "the describe was entered." **Mandate: every lane's `test()` body must contain at least one unconditional `expect` that runs whenever the turn completes** (the `outcome==="completed"` floor assertion). The plan implies this; make it a hard task constraint so a flapped codex lane fails LOUD (floor RED) rather than mints a 0-bucket green.

### NICE-TO-HAVE

**N1 — `[harness:X]` tag could be derived, not hand-written, eliminating mistag risk.** The prompt asks "could an author defeat the floor by mistagging?" Yes: a typo `[harness:codx]` buckets to `codx`, contributing 0 to `codex` → floor FAILs (safe-fail, good) — but `[harness:claude]` on a lane that actually gates codex would mis-credit. The §4 helper `runThroughHarness` + `SUPPORTED_HARNESS_LANES` loop makes `describeTag = \`[harness:${lane.harness}]\`` *derived from the same `lane.harness` that drives `requireHarness`* — so for AR3–AR6 the tag CANNOT drift from the gate. AR2's own test keeps explicit describes (§3 rationale: divergent observable output). **Recommend AR2's four describes also derive the tag from a const** rather than hand-type the bracket string, closing the mistag hole for AR2 too. Minor; the loop form already closes it for the consumers that matter.

**N2 — `extractAgenticCounts` signature change is a breaking change to a shared lib; confirm `verify-attest` is the only caller.** §2 changes `extractAgenticCounts`'s return type from `AgenticCounts` to `AgenticCountsByHarness`. `verify-attest.ts:36` imports it. The builder should `grep` for other importers before changing the return shape (or add `byHarness` as an additive field and keep the two scalars, which the plan already does — `AgenticCountsByHarness` keeps `agenticExecuted`/`agenticSkipped`). Additive, so low-risk; just confirm.

**N3 — timing budget honesty.** §3 estimates 3–6 min wall-clock for the four-lane file with `retry:2`. With three real CLI turns at up to 90s each ×3 attempts worst-case, a fully-flapping run could approach the 240s per-test ceiling ×4. The estimate is for the happy path. Not a blocker (real machine, binaries installed, `retry:2` absorbs jitter not logic), but the builder should expect the matrix file to dominate local verify wall-time.

## Why 8 and not higher

Two things keep it off a 9: (1) **W4** — the single-direction type-assert means the "single source of truth" is, as written, a half-lockstep that can silently rot, which is *precisely* the failure mode §0 is sold as preventing; the plan over-claims "structurally equal." (2) **W5** — the new floor can ship inert (field-not-written) and nothing fails, mirroring AR2's original too-weak global floor; the plan needs an explicit "prove the field is written on a fresh attestation" step, not only the early-return sanity-break. Both are cheap closes, neither is a redesign — hence buildable, not blocked.

## Why not lower

The hardest unknowns are de-risked, not hand-waved: the vitest field is empirically confirmed (I ran it), the codex/opencode fallback is the *already-shipped builtin posture* (reviewed code, not speculation), `gh` exclusion is type-correct, the predicate already prevents the unit/service false-positive class the prompt worried about, and the defense-in-depth split (lint=source, attestation=execution) genuinely makes the subset-coverage regression require defeating *two independent* mechanically-enforced gates. The plan grounds every per-harness setup in real existing helpers (`provisionClaudeSandbox`/`provisionCodexHome`/`CLI_TOOL_CONFIGS`) rather than inventing.

## Disposition

**READY TO BUILD.** No designer revision required. The builder must treat W1, W3, W4, W5, W6 as hard task constraints (compute don't copy the coverage seed; share the exact predicate; make the lockstep bidirectional; prove the floor field is written; mandate an unconditional floor assertion per lane). W2/N1 are watch-items the existing defense-in-depth already backstops.
