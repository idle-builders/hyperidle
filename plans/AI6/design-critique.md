### WARNING
- **[approved.md §4 — hover vs selected]** The slash-menu ratified fix is **incomplete against its own AC and validation scenario.** Verified at `slash-menu.tsx:218` the component binds `onMouseEnter={() => setSelectedIndex(index)}` — pointer-hover *sets* `selectedIndex`. Hover and keyboard-selection are the **same state variable**, not two states. After the §4 className swap, a mouse-hovered item satisfies `index === selectedIndex`, so it renders the accent (selected) tint and the `hover:` neutral class never fires. The AC ("hovered and selected visually distinct") and the validation scenario ("hover item A + select item B, assert A neutral, B accent") are **unsatisfiable as written** — you cannot have A hovered-but-not-selected while B is selected, because hovering A selects it. The design treats this as a pure visual two-tone rule but the real divergence is behavioral (hover collapses into selected). → Either (a) the design must state that slash-menu's "selected" is keyboard-only and decouple pointer-hover from `setSelectedIndex` (a behavior change — conflicts with the "no behavior changes / chrome only" constraint, so must be called out explicitly and waived), or (b) re-scope the validation to a menu/list that genuinely holds both states independently (TabBar already does; the design itself notes TabBar is the reference). The design must not hand `/architecture` a className-only fix for a behavioral problem.
- **[approved.md §3 — StatusChip in tracking scope]** `StatusChip.tsx:104` (verified `tracking-[0.05em]`) is in the §3 migration list, but AI6's sibling AI5 spec lists "status chips (**AI4**)" as AI4's territory. AI6's own out-of-scope block does not claim or disclaim StatusChip. → Confirm AI4 has not already ratified/owns StatusChip's caps tracking before AI6 edits it; if AI4 owns the chip's typography, drop `StatusChip.tsx:104` from AI6's list to avoid two WPs editing the same line. Low blast radius but a real ownership ambiguity.

### SUGGESTION
- **[approved.md §1 — two focus treatments]** The "exactly two treatments: control-ring + input-glow" framing is sound and well-argued, but it is the design's own self-identified weakest point (States/A11y). The risk: a reviewer or the focus e2e reads input-glow as the divergence being resolved. The design correctly pushes the mitigation to DESIGN.md. Reinforce: the e2e must assert *per element-class* (controls → 1px outline; inputs → box-shadow glow), never a single global "all focus looks identical" assertion — otherwise the AC's "looks the same on every interactive component" is contradicted by the (correct) input-glow exception.
- **[approved.md §2 — `--scrim` / AppShell]** The design correctly identifies the scrim is already tokenized and the AppShell consumer is web (AI5) scope. Good boundary discipline. No action — flagged only to confirm the reviewer agrees the scrim half of the color AC is satisfied in-DS by "token exists + documented," with the wiring deferred to AI5.
- **[approved.md §6 — `ease-[ease]` → `ease-[var(--motion-ease)]`]** Verified `--motion-ease: cubic-bezier(0.25, 0.1, 0.25, 1)` which is precisely the CSS `ease` keyword curve — so the three conversions (`SearchField.tsx:41,50`, `NavItem.tsx:60`) are pixel-identical, not a visual change. Correct call; safe.

### What's Working Well
- **Coherence is the whole point and the design nails it (10).** Every off-palette literal maps to a named semantic token with both light + dark values verbatim from current code, so the migration is rendering-neutral by construction. The decision to fold near-identical tints (`0.06`/`0.08`/`0.1` accent-primary variants) into one `--accent-primary-dim` rather than minting three near-duplicate tokens is exactly the restraint the aesthetic credo wants — and the design explicitly rejects a redundant neutral-row-hover token in favor of the existing `color-mix(text-secondary, X%)` idiom.
- **Faithful to source, not inventive.** The focus convention is pulled from the documented `clickable.ts:15`, the tracking values from the `tokens.css:85-90` @lore (which itself says the 0.02em values are Lucid-era leftovers), and the renderer container rule picks the already-correct `block/` family as canonical rather than inventing a third chrome. The "Rejected" section is real, not straw-manned (2px ring, forced-input-onto-ring, `--tracking-title`, color-mix scrim each have a concrete reason).
