### CRITICAL

- **[plan §"AC → validation method" AC-1, AC-2; §"Risks"] The lint gate does NOT detect the alias-class divergences that are the core of AC-1/AC-2 — verifiability hole.** The plan asserts: "AC-1 … `npm run lint` (AQ-001 off-grid, AQ-004 off-scale) zero violations" and "AC-2 … `npm run lint` + grep guard." But the eslint rules only flag *arbitrary-value* classes (`gap-[16px]`, `text-[14px]`). The real source divergences are DaisyUI/Tailwind **alias** classes: Worker `gap-4` (SettingsWorker.tsx:158), Models/Agents `gap-3`, `text-sm`/`text-xs` throughout (SettingsModels.tsx:123,176,194,205; SettingsAgents.tsx:535,562,571…). `npm run lint` passes whether or not the builder converts these. So AC-1 ("no off-grid spacing remains") and AC-2 ("no … divergent control") have **no enforcing gate** for their most common violation. The plan's own AC-2 row hedges ("add a targeted grep in CI only if a rule gap exists") — the rule gap DOES exist and the plan must commit to the grep, not leave it conditional. Fix: AC-1/AC-2 verification must include a concrete static check that catches the alias forms — either (a) a committed grep-based static check enumerating forbidden tokens (`gap-3`, `gap-4`, `gap-6`, `text-sm`, `text-xs`, `input input-`, `btn `, `toggle toggle-`, `badge `) across the 10 files, run in CI, OR (b) note that these are caught only by the snapshot-net diff + manual review and downgrade the lint claim. As written the plan over-claims its automated coverage. (Recurrence: CC-007-adjacent — plan references a gate that does not do what the plan says.)

- **[plan §"Ordered task list" Task 3/9; §Migrations; §protectedTests] Plan's test-file paths are wrong, and it OMITS a real test file that exercises the changed surfaces.** Every cited test path is off by a `__tests__/` segment: the plan says `packages/web/src/settings/SettingsWorker.test.tsx` but it lives at `packages/web/src/settings/__tests__/SettingsWorker.test.tsx`; `X4-SettingsModels.test.tsx:162` is at `…/settings/__tests__/X4-…`. More importantly, the plan never lists **`packages/web/src/__tests__/SettingsAgents.test.tsx`** (196 lines) or **`packages/web/src/__tests__/SettingsProfile.test.tsx`** (loading test at line 164) — both render the components AG7 rewrites. (Verified SettingsAgents root test only asserts `getByText(/no teams/i)` and SettingsProfile loading asserts absence of the Save button, so both happen to survive — but the plan must enumerate them in protectedTests/migrations so the builder runs them, rather than discovering a red suite at Task 11.) Fix: correct all test paths to include `__tests__/`, and add `packages/web/src/__tests__/SettingsAgents.test.tsx` + `SettingsProfile.test.tsx` to the protectedTests list with a note that both are text/absence-based and should survive.

### WARNING

- **[plan §"Plan reconciliation" StatusChip row; Task 7; §Risks 1] The status→color mapping the plan specifies produces the WRONG colors and the plan treats it as "Low risk."** Plan maps Worker connecting→`paused`, Agents harness-unavailable→`behind`/`blocked`. But `paused` = `--status-info` (blue, StatusChip.tsx:77), not warning. So "Connecting" renders blue and "Disconnected"→`behind` renders amber — a transitional state looks calmer than a connecting state, and "Harness unavailable" (mapped to `behind` amber OR `blocked` red — plan is inconsistent between Task 9 saying "behind/blocked" and §1.9 design saying warning) is under-specified. This is a correctness issue for AC-2's "render identically/meaningfully," not merely cosmetic. Fix: pin one explicit color per state in the plan (e.g. Connected=healthy, Connecting=paused[blue, "in progress"] OR behind[amber], Disconnected=neutral/unknown, Harness-unavailable=behind[amber]) and resolve the Task-9 "behind/blocked" vs design "warning" contradiction. Note: tests assert label TEXT only (`getByText(/connecting/i)` SettingsWorker.test.tsx:362), so they will NOT catch a wrong color — this needs the manual screenshot review in AC-7 explicitly assigned.

- **[plan §"AG6 Row adoption" Task 8; §Risks 3] The org-chart edge table → Row/ItemList migration has an anatomy mismatch the plan does not address — it may not be the "cleanest fit, lowest risk" claimed.** `Row` anatomy is `title (13px, flex-1) + subtitle + trailing cells (11px mono) + actions` (Row.tsx:193,197,124). An org edge is three *peer* columns (from / mechanism / target) with no natural title and a delete action. Forcing it into Row means either: from→title, target→subtitle (loses the columnar from|mechanism|target reading the current `<table>` gives), or all three into 11px-mono `cells` with an empty/placeholder title (AQ-113: Row title is REQUIRED — `title: ReactNode` is non-optional, Row.tsx:68). The current table renders from/target at 13px sans + mechanism at 13px mono; Row cells are 11px mono — a visible downsize. The plan picks org-chart as the AG6 adoption *because* it's the cleanest, but it is a genuinely awkward fit. Fix: the plan must specify the exact Row mapping (what is title, what are cells, what tone) and confirm it does not regress the three-column readability — OR reconsider whether Credentials (which has a real title+subtitle+trailing-chip shape that fits Row natively, CredentialsTab.tsx:227-238) is the better AG6 adoption surface. As written Task 8 hand-waves "cells: from / mechanism(mono) / target" without resolving the required-title constraint.

- **[plan §"AC → validation method" AC-3; AC-3 tension] AG6 adoption on a SINGLE surface (org-chart) is a defensible reading of AC-3, but the plan's justification for keeping the Agents `<table>` is thinner than the spec's "all list/table surfaces" wording demands.** The spec AC-3 says "all list/table surfaces in Settings render through the shared item-row/table primitive (AG6)." The plan adopts Row on org-chart only and keeps Agents `<table>` (Task 9) + Credentials flush rows (Task 10) on the "inline-expand a11y cost" rationale. The a11y rationale is REAL and correct (Row's nested-button heuristic forces div[role=button] and the colSpan edit-row pattern genuinely fights Row anatomy — verified Row.tsx:181-185, SettingsAgents.tsx:612-625). But "all … surfaces" is plural and explicit. This is the one place a strict reviewer/founder could reject the WP at ship. Recommendation (not a blocker for the plan score): either (a) adopt Row on Credentials too (it fits natively and has no colSpan-expand problem — the edit reveal is already a sibling div, CredentialsTab.tsx:281), making it 2 of 3 surfaces and a much stronger AC-3 story, or (b) get explicit founder/spec sign-off that ≥1 surface + control-consistency satisfies AC-3. The plan currently bets the AC on a justification doc; strengthen the bet by migrating Credentials, which is low-risk.

- **[plan §"AC → validation method" AC-7; §Task 11] AC-7 requires "the whole page is visually tested via Playwright … every section screenshotted top to bottom" — the plan substitutes the snapshot net + ad-hoc screenshot and does not commit to a per-section capture.** Spec AC-7 and the validation scenarios are explicit about a top-to-bottom Playwright screenshot pass reviewed for cross-section consistency. The plan's AC-7 row says "catalog-snapshot net re-blessed … Playwright screenshot of full Settings page each section (manual review in /review)." Given MEMORY (visual-regression: no screenshots in CI; e2e is local-only), the *gate* correctly stays the DOM-snapshot net — that is right and the plan should NOT add a Playwright CI job. But AC-7's coherence judgment ("the review finds the page coherent") is a human/visual act the plan defers to "/review" without naming who captures the per-section screenshots or where. Fix: assign the per-section visual review explicitly to the Phase-4 /review (local screenshot of the running app, section by section) and state that the snapshot net is the regression gate while the screenshot review is the AC-7 coherence sign-off. This also closes the color-correctness gap from WARNING-1 (wrong StatusChip color is only catchable by eyes).

It's defensible (Button conveys disabled), but it is a UX change, not pure tokenization — and it touches the protected save-flow. If Backend is the "one fully-compliant section," verify it actually uses `text-[13px]`/`text-[12px]` literals, or it is not the baseline the plan claims and Task 1 becomes a real edit, not verify-only.

- **[plan §"Design-it-twice"] Good — one real decision (Models dot vs StatusChip) with a non-strawman alternative.** The (A) tokenized-dot option is genuinely viable and fairly argued. This satisfies the design-it-twice requirement honestly.

### What's Working Well
- **Plan reconciliation is the model of how to do it (CC-007 defense).** The plan grepped the real primitive source and caught the four traps that would have been build-time surprises: Input className lands on the wrapper (not the input), Toggle is role="switch" (not checkbox), Skeleton dropped the `.skeleton` class, StatusChip has no "connecting". Every one verified correct against source. This is exactly the spec⇆reality discipline the rubric rewards.
- **Test-migration honesty re: "tests must not drive behavior."** The plan correctly classifies the checkbox→switch and `.skeleton`→`[role=status]` updates as selector-tracking (the production change is correct per design; the test follows the new DOM contract) — not behavior-bending to make a test pass. It explicitly cites the MEMORY rule and keeps the functional/persistence assertions frozen in protectedTests. Right call, right framing.
