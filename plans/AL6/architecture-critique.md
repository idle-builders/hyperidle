# AL6 — Architecture critique

## v3 — provisioning re-prompt loop (harness-agnostic forcing)

**Reviewer verdict: NEEDS-REVISION. Score 5/9.** The relocation idea (forcing → provisioning layer) is structurally correct and the loop pseudocode is coherent. But the plan rests on one load-bearing claim that the real adapter code FALSIFIES: that a re-engaged turn's forcing message reaches a CLI/isolated agent via `config.messages` + "prompt threading." Neither CLI nor isolated has any prompt/messages instruction channel at all — the task reaches them ONLY through files (`AGENTS.md`/`CLAUDE.md`) the provisioner writes ONCE before the loop. The plan's §3.3 hand-waves this ("thread it into the CLI prompt/args") against an adapter that has no prompt arg. This is the SAME class of hole as v2 (forcing that doesn't reach the external model), now hidden one layer deeper. AC4's center-of-gravity — "force a real EXTERNAL harness, proven live" — is not met by this plan as written.

---

### Bar check (the one question that matters)

> Does v3 actually FORCE on a real EXTERNAL (non-Claude) harness, proven live?

**No, not as specified.** The re-prompt loop runs a second `startSession`, but for cli/isolated/remote the forcing message has no path to the model. The loop will spin N times spawning identical re-runs (same sandbox files, no new instruction) and then settle `not_returned` — which is reject, exactly v2's outcome, dressed as forcing. The live eval that would catch this (§5) is itself aspirational (see CRITICAL-2).

### Findings

#### CRITICAL-1 — The Mode-1 forcing carrier does not exist for cli or isolated. The re-engage is a no-op re-spawn.
`packages/server/src/harness/cli-harness-adapter.ts:183-289` — `startSession` consumes ONLY `config.sandboxPath`, `config.resolvedModel`, `config.mcpConnectionInfo`. It builds args from a fixed template set `{{sandbox}} {{model}} {{apiKey}} {{baseUrl}} {{mcpUrl}}` (`:35`). There is **no `{{prompt}}`/`{{messages}}` template, no stdin write, no `config.messages` read anywhere in the file** (grep: zero hits for `messages`/`prompt`/`assembledPrompt`). The task instruction reaches a CLI agent EXCLUSIVELY via `writeSandboxAgentsMd(sandboxPath, assembledPrompt)` (`session-provisioning.ts:651`), written ONCE in Phase 8.5 before the run. The plan's §2.3 explicitly keeps the sandbox "created once … reused across runs; re-engagement does NOT re-provision the sandbox."

Consequence: `reEngageConfig` appending `{role:"user", content: AL6_FORCE_RETURN_MESSAGE}` to `config.messages` (architecture §3.1) changes a field the CLI adapter never reads. A second `startSession` re-spawns the identical subprocess in the identical sandbox with the identical AGENTS.md — the agent sees no forcing message. The loop burns `AL6_MAX_FORCE_RETURNS` re-spawns then settles `not_returned`. **This is reject, not force** — the v2 hole, relocated.

The plan's §3.3 anticipates this ("adapters that read the prompt … also append the forcing message to the kickoff prompt the adapter passes to its harness (cli: into the `{{...}}`-templated prompt arg)") but **no such prompt arg exists** — `CLI_TOOL_CONFIGS` (`adapter-pool.ts:272-301`) passes only `{{workspace}}`/`{{apiKey}}`, and the task content is never an arg. The only viable real carrier is **rewriting AGENTS.md/CLAUDE.md in the sandbox between runs** (append the forcing message to the assembled prompt and re-write the file before re-`startSession`). The plan does not specify this and actively contradicts it (sandbox reused, not re-provisioned). **Required fix:** the architecture must designate the sandbox-file rewrite as the cli/isolated carrier, prove it reaches the agent, and reconcile it against the "sandbox created once" invariant (re-writing a file in an existing sandbox is fine; the plan must say so explicitly and the red test must assert the file content changed).

Isolated has the same gap: `isolated-harness-adapter.ts:128` does `child.send({ type: "start", config })` to the worker, which forks a `ClaudeAgentSdkAdapter`. The inner SDK's instruction surface is `query({ prompt: "Begin working on your assigned task." })` (`claude-agent-sdk-adapter.ts:236-239`) + CLAUDE.md in cwd — NOT `config.messages` (the SDK adapter never reads `messages` either; grep confirms). So the isolated Mode-1 re-engage also fails to deliver the forcing message unless the sandbox file is rewritten. The plan's "inner SDK also fires its Stop hook, so isolated is doubly forced" is the ONLY thing that actually forces an isolated turn — which means isolated forcing is STILL Claude-SDK-dependent, re-introducing exactly the founder's objection for that harness.

#### CRITICAL-2 — The external live eval (§5) is aspirational; the AC4 live-proof DoD is unmet by the plan.
`packages/eval/src/provision-harness.ts` registers ONLY `BuiltinHarnessAdapter` (`:71`) and reads force-count from `builtinAdapter.getSessionForceCount` (`:120`), a builtin-only method. The eval runner resolves models via `resolveModelTier` and the SDK/builtin direct path (`runner.ts`, `cli.ts` — OpenRouter/Anthropic model IDs); there is **no existing wiring to register a `CliHarnessAdapter` that runs the local `claude` CLI**, and no `claude`-CLI args config in eval (the prod `CLI_TOOL_CONFIGS` covers aider/goose/opencode, not `claude`). The plan's §5.1 ("register a CliHarnessAdapter … invoke the locally-available `claude` CLI, ndjson format — same path AF10 cost tests use") cites a path that does not exist as plumbing — AF10 cost tests construct a `CliHarnessAdapter` in-test with a hand-written args array, they do not provide a reusable `claude`-CLI eval registration. Building this requires: (a) a `claude`-CLI args template that actually passes the task (back to CRITICAL-1 — `claude -p`/`--print` with the prompt, OR sandbox-file delivery), (b) the `claude` binary present locally (DoD un-runnable in its absence — plan concedes skip-if-absent, which means the AC4 live teeth can silently never run), (c) force-count surfaced at turn level. Until CRITICAL-1 is solved, the cli eval cannot prove forcing because forcing cannot reach the cli agent. **The single live proof the founder demanded is, as planned, not yet a real lane.**

#### CRITICAL-3 — `forceReturnCount` is not yet a turn-level value; the plan asserts it as if it exists.
`ProvisionSessionResult` (`session-provisioning.ts:215-231`) has NO `forceReturnCount` field today — only `returnVerdict`. The current loop is single-pass (one `startSession` → one drain → teardown); there is no `forceCount` in `runSession`. The plan correctly identifies the fix (T6/§2.4 add `forceReturnCount` to the result, sourced from the loop), but several downstream claims (AC1/AC3/AC4 tests assert `forceReturnCount===1`, eval reads `result.forceReturnCount`) treat it as load-bearing. This is fine AS A PLAN, but note: the builtin Layer-A path increments `getSessionForceCount` INSIDE the adapter and the gate returns in-turn, so the provisioning loop's `forceCount` stays 0 for builtin (the loop never re-engages). The eval's `force_return_injected` judge (`force-return.ts:110`) reads `forceReturnCount` — if the turn-level count is 0 for builtin (Layer A handled it) the existing builtin scenario's judge regresses to 0 unless the plan keeps BOTH sources reconciled. The plan says "getSessionForceCount can stay for builtin parity" (§5.2) but does not specify the eval reading the MAX of the two or summing them — under-specified, will silently break the kept builtin scenario. **Fix:** specify that the eval force-count = `result.forceReturnCount` (Layer-B re-engagements) PLUS the adapter's in-turn count (Layer-A), or the builtin judges break.

#### WARNING-1 — Adapter-pool slot reuse across two `startSession` calls is flagged ⚠️UNVERIFIED and is a real hazard, not a footnote.
`session-provisioning.ts:874-896` releases `adapterPool.release(adapterId)` after EACH `stopSession`, and `:732` releases on start-failure. The current code releases exactly once per session. The loop calls `startSession`→`stopSession` N+1 times on one resolved `harness` instance while holding ONE `adapterId` lease. Releasing per-run inside the loop (as the unchanged drain body does at `:894`) then re-running `startSession` re-enters a slot that has been returned to the pool — a concurrent session could grab it. The plan's fallback ("hold the slot across the loop, release once at the end", §2.3) is the correct design and should be the PRIMARY plan, not a conditional — the per-run release MUST be lifted out of the loop body. As written, the loop body still contains the per-run release (the drain is "unchanged"), which is a concurrency-accounting bug. Promote the hold-across-loop to the mandated shape.

#### WARNING-2 — Double `session_ended`/cost-double-count risk from running N drains in one turn-span.
The drain body accumulates `totalCostCents` per event and the teardown calls `endSession`/`recordCostAndCheck`. The plan says cost "accumulates across runs" (§2.3) — but `recordCostAndCheck` is called PER cost_update event INSIDE the drain (`:819`), so running the drain twice double-counts the first run's cost into `agents/teams.costActual` only if the SAME cost_update events replay — they won't (new run, new events), so per-event recording is fine. HOWEVER `endSession` is currently called ONCE at teardown after the single drain; the plan correctly moves teardown after the loop. The risk is the `onHarnessStarted?.()` fire (currently at `:753`, once, before the gate) — the plan's §2.3 `firstRun` guard is necessary and correctly identified. Confirm the plan also guards `sessionRunRegistry.register` (currently `:741`, per start) — re-registering the same `sessionId` across runs must replace, not duplicate, the abort affordance. The plan mentions register/deregister per run (§2.3) but a per-run register on the SAME `sessionId` key overwrites cleanly (Map) — acceptable, but the deregister must happen ONCE after the loop (it currently lives at `:907`, post-drain), else a mid-loop deregister drops the abort affordance for run #2. Plan should pin deregister to post-loop.

#### WARNING-3 — The `canForceReturn`→`hasNativeReturnHook` rename touches ~30 sites, ~25 of them test files; T2/T10 understate the blast radius.
grep `canForceReturn`: 5 adapters + `mock-harness-adapter.ts` + `harness-adapter.ts` interface + `harness-adapter.d.ts` (generated) + ~22 test files (adapter-pool, mcp-route, af7, R1, AM2, X3/X5, AK2/AK3, AD2, AF10, workers, agent-profile, AL6-return-gate*, session-provisioning, claude-agent-sdk-adapter, harness-adapter.test). The plan's §9 says "builder greps the literal and updates each call site" — fine, but `AL6-return-gate.test.ts` and `AL6-return-gate.integration.test.ts` encode the ENTIRE v2 semantics ("Tier-1 vs Tier-2", "canForceReturn table", reject-path expectations at `:521-545`, `:617-690`). These are not mechanical renames — they assert the rejected v2 behavior and must be REWRITTEN to the v3 semantics (every adapter forced, none reject-only). `AL6-return-gate.test.ts` is on the `protectedTests` list (the plan lists it) — the plan says "updates limited to the cap rename," but the v2 file asserts a reject table that v3 deletes. The plan contradicts itself: a protected test cannot keep its meaning AND have its reject-table assertions removed. Resolve: these AL6 v2 behavioral tests are NOT protected-as-is; they must be re-authored. State that explicitly.

#### WARNING-4 — `canReEngage` static-exhaustiveness is a real lint/type need, but the plan's "static assertion" is a runtime test, not a static guard.
CLAUDE.md: static codebase properties → type system or lint rule, not a test. The plan's AC4 "static assertion: no in-tree adapter returns `canReEngage:false`" (architecture §4, §9) is implemented as a vitest test importing all five `getCapabilities()`. That catches the five current adapters but NOT a future sixth adapter shipping `canReEngage:false` silently — a runtime test only checks what it enumerates. A genuine static guard (the CLAUDE.md-correct tool) would be: make `canReEngage` a required field (compile-fails a missing one — good, the plan does this) PLUS an eslint-plugin-design rule or a type-level brand that forbids the literal `false` outside a justified allowlist. The plan's prose claims "a reviewer grepping 'which harness can't be forced' finds nothing architectural" — but a required boolean field CAN be `false` and the type system won't stop it. Either accept that `canReEngage:false` is a legal value guarded only by a runtime test (honest, weaker) or add a lint rule. Don't claim static-impossibility you don't have.

#### NIT-1 — SDK `continueSession` (Mode 2) is correctly flagged ⚠️UNVERIFIED and correctly non-critical (Layer-A Stop hook handles SDK in-turn). Good. The plan's fallback (omit `continueSession`, use Mode-1) is sound for SDK because the Stop hook is the real forcing path — but note this means Mode-2 is dead weight in v3; consider deferring the optional interface method entirely until a harness needs it (YAGNI). Adding `continueSession?` to the interface now, implemented by one adapter as a backstop to a path that already works, is speculative surface.

#### NIT-2 — Latent (out-of-scope) bug spotted: `CLI_TOOL_CONFIGS` (`adapter-pool.ts:275,285,294`) still uses `{{workspace}}` while `cli-harness-adapter.ts:35` only resolves `{{sandbox}}` (AK1 rename). `{{workspace}}` is never substituted → the literal string `{{workspace}}` is passed as a CLI arg. Not AL6's job, but if the builder threads a forcing prompt through CLI args they'll trip over this. Flag for a separate fix.

### What v3 must fix to clear the bar

1. **Designate the REAL cli/isolated carrier.** It is the sandbox instruction file (`AGENTS.md`/`CLAUDE.md`), not `config.messages` and not a nonexistent prompt arg. The re-engage step must re-write the assembled prompt (append `AL6_FORCE_RETURN_MESSAGE`) into the sandbox file BEFORE the next `startSession`, and the architecture must reconcile this with the "sandbox created once" invariant (rewriting a file in the existing sandbox is the mechanism — say so). Prove the rewritten file reaches the agent.
2. **Make the external eval a real lane or admit it isn't.** Either wire a `claude`-CLI args template that delivers the task+forcing (e.g. `claude -p <prompt>` or file-based) and register it in `provision-harness.ts`, with force-count from `result.forceReturnCount` reconciled with the builtin Layer-A count — OR concede AC4's live proof rides on the integration test + a file-carrier assertion, and document the eval as future. Do not present an un-runnable lane as the DoD.
3. **Mandate hold-slot-across-loop and post-loop deregister** as the primary loop shape (not ⚠️ fallbacks).
4. **Re-author, don't rename, the AL6 v2 behavioral tests** that encode the reject table; remove them from "rename-only / protected-as-is."
5. **Fix the mock-adapter premise:** the AC4 Mode-1 mock must NOT read `config.messages` to "see" the forcing — it must mirror the real carrier (sandbox file or its own equivalent), or the green integration test will pass while the real CLI silently fails (tests-drive-behavior trap; MEMORY: tests must not drive behavior).

**Carry-forward to Phase 4:** verify, in the built code, that for the cli path the forcing message physically lands where the agent reads it (sandbox file content changed between runs), and that the live cli eval (if shipped) actually executed and recorded `forceReturnCount >= 1` against a real external agent — a green integration test alone does NOT discharge AC4 (MEMORY: live-proof lanes run before ship; AL6 v1/v2 both passed gates and were founder-rejected).
