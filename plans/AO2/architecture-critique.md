### CRITICAL

- **[§1 mount target + §5 capture] Root-mount collides with context-assembly / harness scaffolding; `git add -A` capture pollutes the commit/bundle and can overwrite the repo's own files. The "disjoint subtrees" premise is false.** §1 mounts a single `code` filesystem at `<sandboxPath>` root "so the harness cwd IS the repo." But the sandbox root is *already owned* by other provisioning writers, all targeting `sandboxPath`: `assembleContext` writes `context/ knowledge/ work/ .fabric/manifest.json`; `writeSandboxAgentsMd` writes `AGENTS.md` (line 725); Phase 8b writes `.mcp.json` + CLI MCP configs; `provisionReturnHook` writes `.claude/settings.json` / `.codex/hooks.json` / `.opencode/...`. Two concrete failures: (a) **capture pollution** — §5's `runner.add([])` (`-A`) → commit → bundle stages *all* of that HyperIdle scaffolding into the agent's commit and the durable bundle, so AC2's "the agent's working-tree changes are captured" actually captures changes + a pile of injected control files; (b) **overwrite** — when the materialized repo is HyperIdle itself (the self-hosting target, the entire point of Track AO), `writeSandboxAgentsMd` *overwrites the repo's own `AGENTS.md`/`CLAUDE.md`* and the polluted version is what gets committed. Materializing *before* context assembly (the §1 fail-fast ordering) does not fix this — assembly still clobbers afterward, and `add -A` still stages it. **Fix:** make a real decision the plan currently skips — either (i) mount the repo in a dedicated subdir (`<sandbox>/repo/` or `<sandbox>/workspace/`) and run the harness/build/test with `cwd` at that subdir (revisit the §1 claim that the harness cwd must be the sandbox root — confirm whether the harness cwd is fixed to `sandboxPath` or can be the repo subdir), or (ii) keep root-mount but make capture explicit-pathspec / `.gitignore`-scoped so scaffolding never enters the commit/bundle AND guarantee assembly never overwrites a tracked repo file. This is load-bearing for AC2 correctness and for self-hosting; it must be resolved before `/write-tests`.

### WARNING

- **[§5 captureBack wiring] `runSession` has no handle on the mounted-filesystem list.** Mount happens in `admitSession`; capture happens in `runSession`. `AdmittedSession` (the only thing passed admit→run) does not carry which filesystems were mounted, and the plan never says `runSession` re-runs the driver query. captureBack as written has nothing to iterate. **Fix:** carry the mounted filesystem rows on `AdmittedSession` (preferred — avoids a re-query that could drift if injections changed mid-session), or state explicitly that `runSession` re-derives via `params.agentId → injections → filesystems` before the 3 destroy sites.

- **[§3/§4 + §Type signatures] Mounter couples to the concrete `ServiceConnectionResolver` and orphans the AO1 `FilesystemAuthResolver` seam, leaving `mount`'s frozen `auth` param vestigial.** The plan keeps the AO1-frozen `FilesystemMounter.mount({ filesystem, sandboxPath, auth })` signature but §4 says the mounter ignores the adapter's `resolve()` and self-resolves the token via a new `ServiceConnectionResolver.resolveTokenByConnectionId`. So: (a) who passes `auth`? Phase 5.5 provisioning has no request-userId and `resolve()` returns `{mode:"none"}` anyway → `auth` is permanently `null`/ignored, which the plan never states; and (b) the mounter constructor takes the concrete AN1 class, not the `FilesystemAuthResolver` seam AO1 built for exactly this consumer — directly contradicting the plan's own stated goal that "AN2 can later subsume." **Fix:** either drop the dead `auth` param from the call path and document that the mounter self-resolves (and add the owner-resolving method to the *seam* `FilesystemAuthResolver`, not just the concrete class), or wire through the seam. Pick one and make the data flow coherent — don't carry a param the body ignores.

- **[§2/§5 + §Risks] The capture mechanism's core ref-spec is inconsistent and unproven, yet AC2 durability hinges on it.** §2's `bundle` doc-comment says "all local commits **not in the original remote tip**," but the command is `git bundle create <path> HEAD` (everything reachable from HEAD, no base). On a `--depth=1 --single-branch` clone there is no remote-tracking base ref to diff against, and `git bundle` historically restricts shallow histories. The plan correctly flags this UNVERIFIED in §Risks — but it is the *load-bearing* mechanism for AC2 ("not lost when sandbox destroyed"), not a peripheral risk. **Fix:** pin the ref-spec (bundle the branch ref or `--all`, or capture the base sha at clone-time and bundle `<base>..HEAD`), and make Lane A *restore the bundle to a temp dir and read the agent's commit back* an assertion, not a hope.

- **[§Live-proof] Lane A must name the sanity-break (revert → red), and it simulates the agent edit.** Memory `mock-validation-trap`: a live-proof lane proves nothing unless the reviewer can revert the fix and watch the test go red. The plan never names this step. Also Lane A's "the test acts as the agent's edit" means the *harness* editing path is not exercised here (acceptable per the harness-agnostic boundary — materialization+capture is what AO2 owns), but the plan should state the revert-to-red explicitly: e.g. un-wire the Phase 5.5 mount → Lane A asserts `<sandbox>/.git` absent → red. Confirm it's feasible (it is) and require it.

### SUGGESTION

- **[§2] Specify `clone`'s cwd model.** `createGitRunner(repoPath)` binds a fixed cwd. For clone, bind `repoPath = <target>` and run `git clone -- <url> .` into the (empty, freshly-spawned) cwd, or document the parent-cwd construction. As written, `git clone ... -- <url> <cwd>` with `cwd === <cwd>` is ambiguous.

- **[§4] Use the exact host-scoped key shape.** The verified convention (filesystem-reachability.ts:161) is `http.${protocol}//${host}/.extraHeader`, not the plan's shorthand `http.<host>/.extraHeader`. The plan's own recommendation to factor the header-builder into a shared helper reused by `probeGitRemote` + the mounter resolves this — do that, and the shapes can't drift.

- **[§6] `filesystem_captures.writeback` is a denormalized snapshot of the filesystem's mode.** Fine (capture-time snapshot), but note it duplicates `filesystems.writeback`; document it as an intentional point-in-time copy so a future reader doesn't treat it as authoritative.
