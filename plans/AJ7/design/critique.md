# Design Critique: AnnotatorV2 / AJ7 — Variant A (Devtools rail)

DESIGN-CRITIQUE: variant=a-devtools-rail score=8/10  rounds=1  axes: H:9 S:8 T:8 C:8 Co:8 St:7 A:7 AS:9 PP:7

**Verdict:** Variant A is the right call — it is the only variant whose stable single-region layout makes the keyboard/focus story tractable and honors the founder's no-pin / no-DOM-mutation model cleanly; ship it, but fix the held-box-on-scroll gap and decide re-highlight-when-scrolled-off before build, because both quietly reintroduce a softer form of the drift problem the founder rejected.

This is dev-tool viewer chrome, not a product surface (brief.md reuse-gate). Aesthetic-quality (AQ-*) rules are scored with that in mind: the prototype uses `aj7-` classes with token fallbacks, the builder maps to the production `.anno-*` namespace + real tokens. Token compliance is judged on whether the chosen tokens are *correct*, not on the prototype's literal fallbacks.

---

## CRITICAL

- **[founder-vision drift] The "held dashed box that stays on the selected element while you type" reintroduces a soft version of the pin/drift problem the founder explicitly rejected.** approved.md §3 + state table "Selected" hold a `position:fixed` box at the element's `getBoundingClientRect()` *captured at click time* (prototype: `selected.rect` is frozen in `usePicker`, `AnnotatorV2.stories.tsx:191`, and `OverlayLayer` renders `p.selected.rect` verbatim, line 653). The comment textarea is autofocused and the founder types a multi-line note — during which **any scroll, viewport resize, or canvas re-render moves the element but NOT the frozen box.** That is the exact drift failure mode the founder rejected pins to avoid, just time-boxed to the editing window instead of persisted. The re-highlight path has the same latent bug: `reHighlightNote` reads `rectOf(el)` once on `mouseenter` (line 224) and never updates. → **Fix:** the held box and the re-highlight box must re-measure on `scroll` (capture-phase, window) and `resize` while shown, via a shared `useElementRect(el)` hook that re-reads `getBoundingClientRect()` (rAF-throttled). Architecture must specify this; without it, the box silently lies the moment the page moves. This is the single highest-stakes finding because it touches the founder's load-bearing rejection.

- **[re-highlight miss is under-specified for the common case] Re-highlight of an element that is currently scrolled out of view draws a box off-screen with no feedback.** The notes panel is sticky (`position: sticky`) and always visible, so the founder will hover a note whose element is *above or below the current scroll position* as the normal case on tall page-level stories. `reHighlightNote` only handles the "element not found in DOM" miss (sets `reHi=null`, line 222) — it does not handle "found but off-screen." The box renders at fixed coords outside the viewport and nothing happens visibly; the founder thinks re-highlight is broken. → **Fix:** when the resolved element's rect is outside the viewport, `scrollIntoView({ block: "center" })` first (or show a "scroll to" affordance), then draw. Decide this in /architecture; the "not visible" state in the spec currently conflates "not in DOM" with "in DOM but off-screen" — they need different handling.

## WARNING

- **[a11y: re-highlight + breadcrumb + notes are mouse-only] The entire re-highlight interaction and the notes list are pointer-driven (`onMouseEnter`/`onMouseLeave`, `AnnotatorV2.stories.tsx:433`); note rows are non-interactive `<li>` with `noStaticElementInteractions` suppressed.** For a dev tool that is desktop-mouse-first this is defensible, but the rubric A11y dimension still docks it: a note row has no keyboard focus, no `:focus` re-highlight, no way to trigger re-highlight without a pointer. The breadcrumb crumbs ARE buttons (good), but the comment textarea's `onKeyDown` swallows Esc locally (line 354) while AJ5's parity model routes Esc through a document-level handler that also returns focus to the arm button (`annotation-overlay.tsx:269-289`). → **Fix:** the builder must preserve AJ5's focus-return-to-arm-button on cancel/disarm (approved.md §motion claims this but the prototype CommentField does not implement it). At minimum make note rows focusable buttons so re-highlight is keyboard-reachable, or explicitly accept mouse-only in /architecture with a one-line rationale.

- **[states: no error state for save, no loading state]** AJ5's overlay has both (`saving` + `error`, `annotation-overlay.tsx:58-59,239-266`) because the POST to `/__annotations` can fail (middleware down). The prototype's `save` is synchronous in-memory (line 198) and the approved-design state table drops both states. The real build POSTs to the AJ5 handler and MUST carry the `saving`/`error` states forward — losing them is a regression against the AJ5 contract. → **Fix:** /architecture must list "Saving…" + inline error (retry copy) as required states on the docked comment block, reusing AJ5's `.anno-error` treatment. The state table in approved.md is incomplete here.

- **[occlusion: rail eats 320px permanently on the axis that already costs least]** The synthesis correctly rejected the bottom strip because page stories are *tall*. But the rail's −320px horizontal cost hits *wide* component stories (token tables, multi-column layouts, full app-shell stories) hardest, and those exist in the catalog. The held-box-on-element also means a selection near the right edge of a now-narrower canvas can sit directly under where the eye expects the rail comment field — minor, but the eye-travel trade-off (spec §trade-offs admits "comment input is far from the element") is real and worsens as the canvas narrows. → **Fix:** make the rail collapsible (a chevron to a thin armed-only strip) so wide stories can reclaim width; the sticky always-visible default stays. Cheap, and it directly addresses spec's own admitted weakness.

- **[breadcrumb: duplicate-crumb fiber issue is real and unaddressed]** `ancestorChain` (line 98) walks `parentElement` and calls `resolveTarget` on each ancestor; `resolveTarget`/`resolveComponentTarget` resolves the *nearest component fiber*, so a wrapper `<div>` and its child `<span>` inside the same `BetCard` both resolve `component: "BetCard"`. The screenshot (`state-comment-input.png`) shows exactly this: `unknown › BetCard › BetCard › BetCard` — three identical crumbs, the last styled `--on`. That is noise, not navigation: the founder cannot tell the crumbs apart. → **Fix:** dedupe consecutive crumbs that resolve to the same component+element, OR label crumbs by element descriptor (`div.aj7-betcard-head`) not just component name, so each crumb is distinguishable. This is the concrete form of open-question #2's "duplicate-crumb fiber issue" and it is currently shipping broken in the prototype.

## NICE-TO-HAVE

- **[label collision with own chrome] The floating overlay label is `position:fixed z-index:99997`** (PROTO_CSS line 703) and the rail is also high in the stack. A selection at the top-right of the canvas can place the mono label under or beside the rail header. Low frequency; flag for the builder to clamp the label within the canvas bounds.

- **[label flip is the only edge handling] `HighlightOverlay` flips the label below the box when `rect.top <= 22` (line 124)** but does no horizontal clamping — a label on a wide element near the right viewport edge overflows (it has `max-width:360px` + ellipsis, so it truncates rather than clips off-screen, which is acceptable). Note for the builder, not a blocker.

- **[copy] Arm button reads "Inspect" idle / "Selecting…" armed (`ArmButton`, line 385)** while AJ5 reads "Select"/"Selecting…". The vocabulary lock (concept Phase 3) names the state "pick mode" and notes the *button* may say "Select". "Inspect" is arguably better (devtools-true) but is a deviation from AJ5 + the vocab table — pick one and note it, don't let both ship.

- **[prototype-only, but verify at build] The legacy AJ5 pill leaks into all three screenshots bottom-left** ("Inspect · Round 1 · N notes"). PROTO_CSS hides `.anno-pill` (line 672) but the screenshots still show a pill because the viewer's own mounted `AnnotationOverlay` renders it (and the prototype's suppression selector doesn't match the live toolbar pill). Cosmetic for the design phase; the builder must ensure v2 *replaces* the AJ5 pill, not renders alongside it (approved.md "Change: AJ5 fixed-to-pill popover → docked rail block" implies replacement — make it explicit so two inspectors never coexist).

## Recommendations on the 3 open questions

**1. Comment input: docked-to-rail vs floating-near-element → DOCKED (agree with designer), with one correction.**
Docked is correct: floating (Variant B) occludes the element under review — the exact AJ5 failure the founder named, and the comparison scores it down on Hierarchy/States/A11y for it. The designer's justification ("the held box gives 'at the element' feedback without occlusion") is sound *in principle* but the held box must re-measure on scroll/resize (CRITICAL #1) or it provides false feedback. Docked + a *live-tracking* held box is the right answer; docked + a *frozen* held box is worse than no box. Lock docked; make the box live.

**2. Ancestor breadcrumb in v1 vs defer → DEFER to v1.1 unless the duplicate-crumb fix lands first.**
The breadcrumb is the founder's named nice-to-have and is cheap to *render*, but as prototyped it is broken (WARNING: `unknown › BetCard › BetCard › BetCard`). A breadcrumb that shows three indistinguishable crumbs is worse than none — it implies navigation that does nothing visible. Two paths: (a) ship v1 *with* the dedupe+element-label fix (small, ~half a day), or (b) defer to a fast-follow and ship the inspector's core loop (hover/select/comment/re-highlight) first. Given AJ5 already shipped narrower than wanted, I lean (a) — include it, but the dedupe fix is a *gate*, not optional polish. Do not ship the breadcrumb as-prototyped.

**3. Notes always-visible vs toggle → ALWAYS-VISIBLE (strongly agree).**
This is the clearest call. The founder's task is *reviewing a round* — the notes ARE the work product, and re-highlight-on-hover is the founder's chosen pin-replacement, which only works if the notes are present to hover. Variant B hid notes behind a toggle and lost Hierarchy/A11y for it. Always-visible in a sticky rail (the C-borrowed behavior) is exactly right. Only refinement: give the notes list its own `max-height` + scroll (spec mentions this under Overflow) so a 20-note round doesn't push the comment block off-screen, and so the always-visible promise holds on tall rounds.

## Reuse-vs-rebuild assessment (carry to /architecture)

- **Reuse is correctly scoped.** `resolveComponentTarget` (fiber walk + data-ds + "unknown" fallback), `annotation-store`, `request-handler`, the round model, and the Hearth tokens are all reused verbatim — the prototype's `resolveTarget` is an honest stand-in (it reads `data-aj7-comp` instead of booting the fiber walk, documented at `AnnotatorV2.stories.tsx:60-64`). Good.
- **The `anchor` field is genuinely additive.** The prototype's `anchorId` (a seeded `data-aj7-id`, line 80-90) maps to the concept's "structural path + component + element descriptor." Confirm in /architecture that `AnnotationTarget.anchor` is optional and the handler accepts-but-not-requires it (concept Phase 4 closure) — AJ5 annotations with no anchor must degrade to "not visible", never error.
- **The wiring bug is real and load-bearing.** `main.tsx:473` passes `storyRoot={storyRootRef.current}` which is `null` on the mount render (a ref's `.current` is null during the render that creates the element; mutating a ref does not re-render). So AJ5's `arm()` hits `if (!storyRoot) return` (`annotation-overlay.tsx:143`) and attaches no listeners — **selection silently does nothing today.** The fix (callback-ref → state so the overlay re-renders once the root exists) is correctly flagged in concept Rationale + open-question #4. This must be the *first* task in /architecture's ordered list — every other behavior depends on it.
- **Element-mutating classes correctly retired.** AJ5's `applyHoverOutline`/`applyCapturedOutline` mutate the inspected element's `classList` (`.anno-hover`/`.anno-selected`/`.anno-saved`, lines 96-122) — concept hard-rule #1 forbids this. The v2 separate `pointer-events:none` overlay layer is the right replacement and is structurally a different shape (earns the NEW budget across 3 contexts). Confirmed correct.
- **Overlay host:** open-question #5 (mount the overlay layer in the viewer body, fixed) is the right default for `position:fixed` + viewport-coord `getBoundingClientRect()` — but it is exactly why CRITICAL #1 (scroll re-measure) is mandatory, since fixed coords don't track scroll for free.

## What's Working Well

- **Concept-fit is genuinely the strongest dimension (1.0 in-session, agree).** Notes always visible + re-highlight-one-hover-away + zero canvas persistence + zero DOM mutation falls out of the rail's single-region structure naturally. The architecture of the picker engine (`usePicker`) cleanly separates the engine from the chrome, so all three variants share one tested core — a real reuse win the builder inherits.
- **The single-region layout is what makes the keyboard/focus story tractable** — A wins Hierarchy/States/A11y in the comparison for the right reason: one predictable place for every state. This is correctly identified and is the decisive reason to prefer A over B/C.
