## WARNING

- **[§Type signatures + §Design-it-twice + §Task 1/2] DM/CC-007 — the `diff`/`edit` activity entry does not exist in the real data path.** The plan's `SessionActivityEvent` declares `kind: "tool_call" | "reasoning" | "edit"` with a `diff: { artifactId, label, meta }` field, and `derivePartsFromSession` maps `edit`→a `diff` Embed (Task 2). But the real source — `useSessionActivity`'s `ActivityEntry` — is a closed union of exactly **`tool_call | reasoning | cost_tick`** (`useSessionActivity.ts:31`), and the server activity buffer (`sessions-routes.ts:404` → `SessionActivityBuffer.getActivity`) only ever appends `tool_call_recorded` / `session_ended`. **There is no edit/diff entry anywhere in the activity stream.** The design fixture's two diff Embeds (`sessionDialInFixtures.tsx:136,151`) therefore render data the system cannot produce today. The plan's reconciliation table (row "descriptor↔session link") never caught this because it reconciled the descriptor side, not the activity-shape side. → Either (a) scope AM3 to map only the entry kinds that exist (`tool_call`→prose, `reasoning`→prose, `cost_tick`→header chrome) and DROP `edit`/`diff` from `SessionActivityEvent` + the fixture (the honest, in-scope choice — diffs become a later WP when the buffer captures them), or (b) explicitly add an `edit`/`diff` activity-capture task to the server buffer + `tool_call_recorded` payload AND list it as in-scope. Do not ship an adapter that maps a `kind:"edit"` that no producer emits — that is dead code proving nothing, and the AC4 "two backends → identical Parts" test would assert over a shape the runtime never yields. Pick (a) unless the founder wants diff capture in AM3.

- **[§Type signatures `SessionActivityEvent` vs §Task 1 "lift `ActivityEntry`"] DM — the lift is a reshape, not a lift.** Task 1 says "lift `ActivityEntry` → shared as `SessionActivityEvent`, keep `useSessionActivity`'s union compatible." But the two shapes are structurally different: `ActivityEntry` is `{ type, timestamp:number, data:{...} }` (nested `data`, ms-epoch `timestamp`); `SessionActivityEvent` is `{ kind, at:string(ISO), toolName?, summary?, diff? }` (flat, ISO string). These are not compatible — "lift" undersells a field-by-field remap (`type`→`kind`, `timestamp`(ms)→`at`(ISO), `data.toolName`→`toolName`, `data.argsSummary`/`data.excerpt`→`summary`). → Rename Task 1 to "map `ActivityEntry`→`SessionActivityEvent`" and specify the field mapping + the timestamp conversion (ms-epoch→ISO) explicitly, OR make the adapter consume `ActivityEntry` directly (its real shape) and drop the parallel `SessionActivityEvent` type entirely. The second is simpler and removes a redundant type — recommend it, since `ActivityEntry` is already the normalized backend-agnostic shape AC4 relies on (mirroring it into a second shape adds a translation layer with no consumer benefit).

- **[§Security & abuse cases + §Risks Q1] FMC — config-write path is unspecified, not just deferred.** `onConfigure` (Props) emits a change, but the plan leaves the persistence target as an open question ("default to NO new write endpoint… emit to an existing one or read-only"). That is a contract gap, not a closed decision: AC2 says the user "can configure the session," which implies *some* effect. If AM3 ships read-only emit-to-nowhere, AC2 is only half-met (controls render but configuring does nothing). → Resolve the write target IN the plan before build: either (a) state AM3 is render-controls-only and `onConfigure` is wired to an existing session-launch/agent PATCH with its existing rate-limit cited (name the route + method), or (b) explicitly mark "configuration is surfaced but not persisted this WP" as an accepted AC2 partial and get founder sign-off. As written, the builder has to invent the contract — which is exactly what `/architecture` exists to prevent. Note the security block says "if it persists via an existing PATCH, that endpoint's limits apply" but never names the endpoint, so the route-checklist for the write is empty.

## SUGGESTION

- **[§protectedTests] Names are slightly off — confirm the real files.** The plan cites "the AM1 `part.test.ts` assertions for `derivePartsFromMessages`" and "`PartList.test.tsx` (if present)". The actual frozen contracts are `packages/shared/src/__tests__/AM1-part.test.ts` and `AM1-source-agnostic.test.ts` (the source-agnostic import boundary). "(if present)" is a tell that the architect didn't verify — protectedTests must be exact paths, not guesses (CC-008). → Replace with the two real paths above; both must stay green and `derivePartsFromMessages` behavior must not change.

- **[§Task 5] `harnessType` nullable fallback is hand-waved.** Plan: "Null `harnessType` → fall back to the `builtin` descriptor (or render the model row only)." Two different behaviors joined by "(or)". `harnessType` IS nullable (`schema.ts:71`), so this path is real, not theoretical. → Pick one: builtin-descriptor fallback OR model-row-only, and name the test assertion for it. The selector unit test "incl. the null fallback" can't assert a behavior the plan hasn't chosen.

- **[§Task 8] Test-retarget instruction is vague for 3 importers.** "move those assertions to a surviving surface… or drop the panel-specific assertion" gives the builder latitude to silently delete coverage (money-surface assertions in `AF10-money-surfaces.test.tsx` / `L17-money-web.test.tsx`). Dropping a money assertion because the panel moved is exactly the "weakened test" the adversarial lens flags. → For each of the 3 tests, state whether the money/empty-state assertion MUST be re-homed (cost now in the dial-in header) or is genuinely obsolete. Don't leave "or drop" as the builder's call on coverage-bearing tests.

- **[§AC4 verification] The cross-backend test asserts over fixtures, not over real normalization.** AC4's test feeds "two `ActivityEntry[]` fixtures representing the SAME actions captured from two different backends (already normalized)." Since both fixtures are hand-authored in the already-normalized shape, the test proves the adapter is deterministic — NOT that two backends actually normalize to the same `ActivityEntry`. That cross-backend normalization is AM2's contract (upstream), correctly out of AM3 scope — but the plan should say so explicitly so the test isn't mistaken for proving end-to-end uniformity. → Add one line: "AC4's adapter test proves adapter determinism; the upstream backend→`ActivityEntry` normalization is AM2's proven contract, not re-tested here."

## What's Working Well

- **Layer integrity + reuse discipline (LI:9).** The plan nails the AM1↔AM3 uniformity contract: activity renders through `PartList` unchanged, the adapter (`derivePartsFromSession`) is the only new logic, and AC3's proof is the `no-restricted-imports` ESLint boundary staying green — a static proof that no source type leaked into the renderer. Entry is panel-state (not a route), correctly avoiding the rejected Variant B promotion. The descriptor drives controls with a closed `HarnessOptionControlKind` union and "undeclared ⇒ absent" (no per-backend branching). Every load-bearing AM3 contract is respected.
- **Design-it-twice is real, not theatre (S:8).** The prose-Parts-vs-extend-`PartKind` decision genuinely weighs blast radius (touching the closed union + every exhaustive switch + the conversation snapshot) against bespoke tool chrome, and picks the lower-blast-radius option with a clear "if a future WP needs tool chrome, extend the CLOSED union — never a parallel renderer." That is the correct architectural instinct and it ties directly to AC3.
