# AF12 Retro — Complete the bet and task lifecycle

Branch `feat/AF12-bet-task-lifecycle`. 6-phase pipeline, 10 commits, ~80 min wall (concept 17:59 → cleanup 19:16, 2026-06-11). Verdict DONE first pass, zero blocking findings, all 6 ACs proven (31 green tests: 14 web component + 17 integration; full green phase reported 4088 tests pass).

## What went well

- **Phase-2 critique caught two REAL correctness gaps before a line of code (adversarial-separation paying off).** Architecture scored 8/10, 1 revision round, but the two CRITICALs were load-bearing, not theatre:
  1. **Task-CAS transaction boundary.** Plan said "mirror bet CAS exactly" but the proposed task CAS was a bare `UPDATE ... WHERE state=fromState` with no `db.transaction`. The audit trail is a `JSON.parse → push → JSON.stringify` read-modify-write on the `auditTrail` column — outside the CAS guard. Under a true 3-way race, audit entries clobber (last-writer-wins on the JSON blob). The WHERE-guard alone serializes the winner but does NOT protect the audit RMW. Fix: wrap SELECT-validate + audit-read + CAS-UPDATE in one transaction in BOTH kernel and fabric copies, emit post-commit. Verified in code review as a true structural mirror.
  2. **Async propagation-log microtask ordering.** Propagation handlers wrap work in `void (async () => …)()`, so `propagateTaskToBet` runs on the microtask queue AFTER `/kill` returns. Two consequences the plan missed: (a) AC6 asserting on the async-written `skipped` row would flake; (b) the cascade writes its OWN synchronous `applied` row AND the async upward handler writes a `skipped` row for the same task-kill — two rows. Fix: disambiguate by `sourceEvent` (`'bet_killed'` cascade rows vs `'task_state_changed'` upward), assert AC6 on the deterministic synchronous cascade rows only. Both would have been hard-to-debug runtime / flaky-test issues had they reached build.
- **Concept → design → architecture → critique sequencing produced load-bearing invariants downstream phases honored** (cascade-stops-sessions-WITHOUT-`session_ended`, propagation_log dual-writer, CAS idempotency) — captured as `@lore` at each decision point in `bet-kill-cascade.ts` and `task-state-machine.ts`.
- **Cost-honesty copy survived the critique honestly.** WARNING flagged that "capacity freed immediately" + "sessions stopped" implies cost stops instantly, which AF12 does not guarantee (live harness abort is AF7's seam). Builder dropped "immediately", added "Running agents finish their current step", and docs were updated to match — verified by unit + E2E `not.toMatch(/immediately/i)`.
- **Code review DONE first pass, zero blocking.** Reviewer carried Phase-2 context forward and re-verified every Phase-2 contract in the diff (transaction mirror, field-for-field propagation insert vs `logPropagation`, phantom-row guard, no-`session_ended`-on-stopped). Two-review model (Phase-2 critique + Phase-4 code review) confirmed working.

## Reusable lore

- **"Mirror the X pattern exactly" must name the transaction boundary, not just the WHERE clause.** A CAS guard serializes the winning write but does NOT protect a co-located JSON read-modify-write (audit trail). If you copy a CAS, copy its `db.transaction` envelope or the audit blob clobbers under a 3-way race. (`@lore AF12 AC5` on both kernel + fabric copies.)
- **Synchronous `EventBus.emit()` + `void (async () => …)()` handlers = microtask ordering you must reason about in tests.** Any AC asserting on a propagation_log row written by a handler must either flush microtasks or assert only on the synchronously-written rows. Prefer the synchronous cascade rows — they're deterministic.
- **Two writers to one log table → disambiguate by `sourceEvent`.** The kill cascade writes `applied` rows synchronously AND the upward engine writes a `skipped` row async for the same event. Query by `sourceEvent` ('bet_killed' vs 'task_state_changed'), never by row count.
