### CRITICAL

- **[plan §3 Task-transition CAS] The proposed task CAS is a WEAKER mirror of the bet CAS — it is not transaction-wrapped, and it has no side-effect to protect, but the *emit* ordering it relies on is not actually serialized.**
  Bet CAS (`bet-state-machine.ts:162-220`) wraps the capacity re-read + CAS `UPDATE...WHERE id AND status=fromState` + counter mutation in a single `db.transaction`, and emits **after commit**. The plan's task CAS (§3) is a bare `UPDATE...WHERE id AND state=fromState` with the emit moved below the guard — no transaction. For the task case that is *almost* fine (no counter to mutate), **but** the read-validate-then-CAS-write has a TOCTOU window: the plan reads `fromState` (SELECT), validates `VALID_TRANSITIONS[fromState]`, then issues the guarded UPDATE. Two racers from `accepted` both read `accepted`, both validate `accepted→in_progress`/`accepted→blocked` as legal, then both UPDATE `WHERE state='accepted'` — the second affects 0 rows and throws. That works on SQLite (write-lock serializes) and on PG (row lock). **The gap:** the plan does not state this UPDATE must be the *sole* write in its statement and must not be sandwiched with a non-atomic audit-trail read-modify-write. The audit trail is `JSON.parse(existing) → push → JSON.stringify` (`task-state-machine.ts:62-79`) — a read-modify-write on the `auditTrail` column that is NOT inside the CAS guard's atomicity. Under a true race, the loser's audit read happened before the winner's write; harmless for the loser (it throws), but if a *third* legal transition interleaves, audit entries can be lost (last-writer-wins on the JSON blob). **Fix:** specify that the CAS UPDATE and the audit-trail read must occur such that the audit JSON is re-read inside the same statement context, OR (simpler, matches the bet pattern) wrap the SELECT-validate-UPDATE in `db.transaction(...)` in BOTH copies so the audit read and CAS write are atomic. State explicitly: "mirror bet CAS = same transaction boundary, not just the WHERE clause." As written, the plan calls it "mirror bet CAS exactly" (§3) but omits the transaction — that is the part that makes bet CAS actually safe.

- **[plan §4 step 4 + §Risks 2 / AC6 verification] The cascade's correctness argument depends on async microtask ordering the plan never makes explicit, and the AC6 verification will be flaky because of it.**
  `EventBus.emit()` is synchronous (`event-bus.ts:28,107`) but the propagation handlers wrap their work in `void (async () => ...)()` (`lifecycle-propagation.ts:735`). So when `cascadeBetKill` calls the CAS `transitionTask(...,'killed')`, the `task_state_changed` emit returns immediately and `propagateTaskToBet` is **scheduled on the microtask queue** — it runs AFTER `cascadeBetKill` and the `/kill` handler return. The plan's §4 claim "this emits `task_state_changed(killed)`, which the upward engine catches... but the bet is already `killed`... so logs `skipped`. Correct, harmless." is true ONLY because the bet was transitioned to `killed` *before* `cascadeBetKill` runs (wiring §4: "Order matters: bet must be `killed` first"). Good — the ordering is correct. **But two consequences are unaddressed:** (1) AC6's verification asserts a `propagation_log` skip/applied row "after kill cascade" — that row is written by the **async** `propagateTaskToBet` microtask, which has not run when `/kill` returns. The integration test must `await` a tick / flush microtasks / poll the log, or it will assert on a not-yet-written row and flake. The plan's AC6 verification line (§Acceptance criteria) does not flag this. (2) The cascade writes ITS OWN `propagation_log` rows synchronously (§4 step 5) AND the async upward handler writes a `skipped` row for the same task-kill. So AC6 will see BOTH a synchronous `task <from> -> killed (applied)` cascade row AND an async `... skipped (bet status is killed)` upward row per task. The plan's AC6 assertion must account for both rows existing, or assert on the specific cascade row by `sourceEvent='bet_killed'`. **Fix:** (a) in §Risks/AC6, state that cascade-written propagation rows use `sourceEvent:'bet_killed'` and the upward skip rows use `sourceEvent:'task_state_changed'`, and the test queries by `sourceEvent`; (b) specify the test flushes microtasks (`await new Promise(r=>setImmediate(r))` or the existing test harness's tick helper) before asserting upward rows, OR asserts only on the synchronous cascade rows (preferred — they are deterministic and are what AC6 actually requires).

### WARNING

- **[plan §4 step 3 / Surface 3 copy honesty] The kill-dialog copy "their active sessions stopped" is honest about state-truth but the plan never resolves whether a *live OS process* keeps burning cost — and the design copy quietly drops the cost-honesty line.** Concept Decision 1 explicitly carves out "actually signalling a live harness process to abort" as AF7's seam, and Decision 3 demands the copy be honest about *that* boundary too. The approved copy (§Surface 3): `STOPS: In-progress tasks are killed and their active sessions stopped. / CONTINUES: ... / SAVED: Team capacity is freed immediately.` This is honest about the DB ("stopped" = `outcome='stopped'`), and correctly avoids "terminates running agents." **But** "SAVED: Team capacity is freed immediately" is TRUE (capacity counter decrements synchronously), while a user reading "sessions stopped" + "capacity freed immediately" will reasonably infer **cost stops accruing immediately** — which AF12 does NOT guarantee (a live harness process AF7 hasn't wired the abort for may keep spending). Concept Decision 3 anticipated exactly this ("does 'All active tasks will be halted' still over-promise if the process keeps burning cost?"). The copy is *more* honest than before but still leaves the cost-continuation gap implicit. **Fix:** either (a) add one honest qualifier the design already gestures at — e.g. `STOPS: In-progress tasks and their active sessions are marked stopped (running agents finish their current step).`, or (b) the architect explicitly records that AF12's cascade marks sessions `stopped` at the DB level and that no copy line claims cost stops instantly, and confirms no line implies it. Right now the plan asserts the copy is honest without testing it against the cost-continuation reading. AC3's unit-on-copy test (§AC3 verification "unit on dialog copy matches behavior") must assert the copy contains no claim of instant process/cost termination — specify that assertion, not just "copy matches behavior."

- **[plan §4 step 5 "two writers to propagation_log"] Kernel-direct write to `propagationLog` is acceptable but the plan leaves the row-shape contract informal ("inline a minimal insert ... or expose a tiny kernel logger").** Verified `propagationLog` is exported from `@hyperidle/db` (`db/src/index.ts:87`) so the kernel CAN import the table — good, no layer violation. But "inline a minimal insert ... or expose a tiny kernel logger" leaves the builder a choice that affects row-shape consistency. The fabric `logPropagation` helper sets fields (e.g. `createdAt`, `status`, possibly a generated `id`) that a hand-inlined kernel insert may omit, producing rows that differ in shape from upward rows and breaking any reader that assumes uniform columns. **Fix:** specify the exact insert object (all NOT-NULL columns of `propagation_log`, id generation strategy, `createdAt`) in §4 step 5, matching `logPropagation`'s output field-for-field. Do not leave "or expose a tiny kernel logger" as an open fork.

- **[plan §6 sessions endpoint / AC4] `status: s.state` collapses two distinct terminal outcomes the concept deliberately separated.** Concept Decision 1 + §Risks 1 make a point that session `stopped` (human halt) is distinct from `done`/`crashed`. The endpoint returns `status: s.state` (§6) — so a cascade-stopped session returns `status:'stopped'` and the `SessionRow` renders it "by raw label." Fine for the live-dot (`active`), but the plan's §6 note waffles: "If finer labelling is wanted, prefer `s.outcome ?? s.state` — but ... Use `s.state`." A session row that was cascade-stopped will show the raw string `stopped`; a normally-ended session shows `done`. That is acceptable, but the plan should LOCK it (state-based, confirmed against `SessionRow`'s actual label map) rather than present two options and pick one in prose. **Fix:** confirm `SessionRow`'s label-mapping (`WorkTask.tsx:103-159`) handles `stopped` gracefully (renders a non-empty label, not blank) and state that as the locked contract in §6. If `SessionRow` falls through to blank on an unrecognized `stopped`, AC4's "not permanently empty" is violated for stopped sessions — verify, don't assume.

### SUGGESTION

- **[plan §2 Activate / `/commit`] Verified: `CapacityExceededError extends Error` (not `ApiError`), so it propagates past the `/commit` handler's `InvalidTransitionError`-only catch (`bets.ts:706`) → 500.** The plan's T5 fix is correct and necessary. Note the `/commit` handler also has a `loadTeamMembers` try/catch (`bets.ts:689-694`) that maps `ApiError`→500 and re-throws others — `CapacityExceededError` is thrown later (inside `transitionBet`), not by `loadTeamMembers`, so the new catch belongs in the second try-block (L700-710). Plan §2 places it correctly; just confirm the builder adds the `import { CapacityExceededError }` (plan flags this — good).

- **[plan §3 fabric duplicate] The fabric `transitionTask` audit-trail type is `Array<{from,to,timestamp}>` (untyped strings) while the kernel uses the typed `TaskAuditEntry` union.** Pre-existing drift between the two copies (`lifecycle-propagation.ts:112` vs `task-state-machine.ts:62`). Not introduced by AF12, but since T2 touches this exact function, the plan could note the divergence so the builder doesn't "harmonize" them and accidentally pull a kernel type into fabric (import-ban violation). Leave the loose type; just don't let the CAS edit drift the shape.

- **[plan §4 step 3 "do NOT emit session_ended"] Good call, verified.** `propagateSessionToTask` only acts on `outcome==='completed'` (`lifecycle-propagation.ts:308`), so a `stopped` session would be a no-op even if emitted — but suppressing the emit avoids waking unrelated wildcard handlers. The lore note is warranted. Confirmed harmless.

No CC-007 drift — rare and valuable.
