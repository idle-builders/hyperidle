### WARNING

- **[§Plan reconciliation row 4 + §`ToolContext` addition + Task 5] `ownerUserId` resolution is under-specified — and the analogy to "AN1 routes" is misleading.** AN1 routes read `c.get("userId")` from the **HTTP auth context** of a logged-in human. - **[§Connector resolver + AC4 + Task 6] "active Connection" is not a schema concept, and only `authSource='token'` can actually broker in AN2 — neither is stated.** `serviceConnections` (verified schema lines 1202-1235) has **no `status`/`active` column** — only `health ∈ {usable, needs-attention, expired}` and `authSource ∈ {token, mcp-oauth}`. The resolver returns a token **only for `authSource='token'` with non-null `encryptedToken`**; `mcp-oauth` rows have `encryptedToken=null` → `resolve()` returns null → zero tools (verified resolver lines 56-58). So in AN2 the entire `mcp-oauth` source is silently non-brokerable, and "active" is undefined. → **Fix:** §Connector resolver must define which connections it enumerates (e.g. "all `serviceConnections` for `ownerUserId` where `authSource='token'`; filter on `health` if desired") and explicitly scope AN2 to the `token` source, noting `mcp-oauth` (auth:"none" passthrough or DCR) is deferred — and which AC4 fixture source proves what. Today the plan's `auth:"none"` http fixture proves the transport but bypasses the resolver entirely, so the *credential-attach-from-resolver* path (AC3a) and the *resolver-null-refusal* path (AC3c) need a `token`-source connection row, which the plan's fixture section doesn't set up.

- **[§Live-proof test strategy + AC4] The in-repo SDK `McpServer` fixture is genuine MCP-over-the-wire, but the WP's "≥1 REAL external service" and the founder's live-proof principle are only *honestly* satisfied by the optional, CI-excluded `real-harness` test — make that explicit, not "optional".** The fixture is a real protocol server (not a client stub), which is a meaningful step up and proves the broker code end-to-end. But it is HyperIdle-authored and in-repo: it proves *our* client speaks MCP correctly, not that a *real third-party service* (GitHub/Stripe/`server-everything`) does. The WP text ("proven end-to-end against at least one real external service") and MEMORY [live-proof-lanes-run-before-ship] push for an actual external server in the proof path. `@modelcontextprotocol/server-everything` is **not currently installed** (verified absent). → **Fix:** Either (a) commit to running the `real-harness` test against `server-everything` as a *required local-lane gate before DONE* (add it as a devDependency, document the local run, treat green there as part of the live-proof — not "optional"), or (b) get explicit founder/spec sign-off in the plan that the in-repo SDK-`McpServer` fixture is the accepted "locally-spawned standard MCP server process" allowance (the WP §Plan-calls does allow this wording — quote it). Right now the plan leans on the allowance in one place and calls the real-server test "optional" in another; pick one and state it unambiguously so a builder can't ship with only the fixture and a skipped real test.

- **[§Security & abuse cases — reversibility from external annotations] Trusting the external server's self-declared MCP annotations is a real trust boundary the plan under-examines.** The plan correctly fail-closes *unannotated* tools to irreversible (verified: `classifyReversibility` returns irreversible with no signal). But a **malicious/buggy external server can set `idempotentHint:true` on a genuinely destructive op** → `classifyReversibility` returns `reversible` → runs **direct, ungated**. The plan notes "trust-tier vetting is AN4" but does not state this specific bypass or its blast radius. Per the spec contract "reversibility classification is Kernel/Strategy-owned, never the agent's" — an unvetted external server's self-declaration is *not* Kernel-owned, it's third-party-owned. → **Fix:** §Security must name this explicitly: for AN2's scope (no trust tiers yet), document that an external server's `idempotentHint` is *taken on faith* and the safe-by-default posture is therefore weaker than the spec's "Kernel-owned" ideal until AN4 adds trust tiers. State the AN2 mitigation (community/unvetted servers should arguably default *all* tools to brokered regardless of hints) or explicitly defer with a one-line risk acceptance. This is a deferral decision the plan should make consciously, not leave implicit.
