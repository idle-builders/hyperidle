The reviewer prompt's question — "is reuse-everything genuinely right, or under-designing?" — answered: reuse is right, but the design under-specifies two real founder-legibility moments (created-vs-updated, and which card is current in a long chain). These are WARNINGs, not blockers.

### CRITICAL
- None.

### WARNING
- [approved.md "States + copy" / brief.md probe "How does iteration read?"] **Created-vs-updated is carried entirely by the `ToolCallRow` copy string ("Drafted a bet" vs "Updated the draft").** The `BetCard` itself is byte-identical in both states (same `status="draft"`, same title/excerpt). The brief asserts the founder must "(a) see that a draft was created" — but on iteration the only created/updated signal is one tertiary tinted row. The eye lands on the card (the artifact) per the design's own hierarchy claim, and the card cannot tell you whether this turn made a new bet or edited the one from three turns ago. → Make the distinction legible on the artifact, not only the tool-row: e.g. the `edit_bet` card carries an "Updated" affordance/sub-label, or the iterated card visibly references the same bet id the prior card showed. Decide in `/architecture` whether the copy-only signal is sufficient; if it is, state that as the accepted tradeoff explicitly.
- [comparison.md "Worst at" + self-critique 9/10 note] **Historical-card accumulation in a long iteration chain is acknowledged but not designed.** One draft, edited N times → N near-identical `BetCard`s stack in the timeline, all `status="draft"`, all pointing at the same bet, only the newest being current. The design accepts this ("the thread is a log and the bet id is stable") but gives the founder no way to tell the live card from a stale one. For a 6-turn shaping session this is real timeline noise and a wrong-card click risk (founder clicks an old card showing stale excerpt → WorkBet shows the current bet → mismatch with what they clicked). → At minimum, the spec should state that all cards navigate to the *same live bet* (so a stale-excerpt click is not a wrong-bet navigation, only a stale-preview surprise). Confirm `onClick` always uses the bound bet id, never a per-turn snapshot. Architecture's "which draft" binding (most-recent assistant-authored draft) makes this true server-side; the design should assert it as the mitigation.
- [approved.md "Component mapping" — `BetCard` `team` prop] **`BetCard` requires a `team` (team name string), `title`, and `description` — none are present in the `create_bet` tool output** (`{betId, status, teamId}`). The design says `team`=team name, `title`=goal, `description`=body excerpt, but these come from a bet fetch (`useBet`), not the toolCall. The design correctly implies a fetch ("from a bet lookup") but does not state the loading state for the card while that fetch is in flight. → Specify the card's own loading/skeleton state (or render the `ToolCallRow` alone until the bet resolves). "Loading: existing Thinking… indicator" covers the turn, not the post-turn card fetch.

### SUGGESTION
- [approved.md "States + copy" — error] Error copy "I couldn't create the draft — you don't have a team yet." is good and honest, but it is server-authored reply text, not a design-system state. Confirm it renders as normal reply text (no card, no row) — the design says so; just ensure `/architecture`'s Task 7 produces a plain reply, not a `notice` card (notices are reserved for `missing_key`/`missing_harness`/`provider_error`).
- [brief.md "Mobile"] Mobile claim "BetCard is responsive" is asserted, not verified. Low risk (BetCard renders fine in WorkBet at column width), but the embed-under-bubble container width in the overlay differs from WorkBet. No action required for v1; note as untested.
