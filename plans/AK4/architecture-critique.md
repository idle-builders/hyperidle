# Architecture Critique: AK4

ARCHITECTURE-SCORE: 6/10  rounds=1  score-line: SA:8 LI:8 AC:6 DM:9 N:8 MD:6 FMC:6 S:6 V:5

Verdict: **REVISE.** Overall 6 and there are two CRITICALs that, left unfixed, make AC4 (iteration via `edit_bet`) non-functional and AC2's tool-scoping claim false. The plan's *shape* is right (bounded loop in the conversational path, task-free ToolContext, reuse `executeToolCalls`, no second runtime, draft-only edit guard). But three load-bearing claims about the existing code are wrong, and Verifiability (the codebase's first principle) is thin. Fix the two CRITICALs and the Verifiability gap, then this is a 7-8.

All claims below were checked against the actual branch (`feat/AK4-assistant-drafts-bet`), not taken on faith.

### CRITICAL

- **[plan §"Types/contracts" + §"Ordered tasks" Task 2] The chosen registry path does not contain `edit_bet`, so AC4 cannot work as planned.** The plan says Task 2 calls `buildToolRegistry(ctx, {role:'assistant'})` (from `tool-registry.ts`). But `ALL_TOOL_DEFINITIONS` in `tool-registry.ts` registers `create_bet` (`wrapForRegistry(createBetTool, ["assistant"])`) and **does NOT register `edit_bet` at all** — `editBetTool` is only assembled in `assistant-tools.ts`'s `toolsForAssistant()`, a *different, dead* code path (see below). So `buildToolRegistry(ctx,{role:'assistant'})` yields a registry where `edit_bet` is absent → the model can never call it → AC4's "iteration updates the same draft" is impossible. The plan conflates the `tool-registry.ts` path (live, used by `runAssistantTurn`/session-provisioning) with the `assistant-tools.ts` path (dead). → Fix: register `editBetTool` (and decide whether `update_task_status`/`edit_block` belong) in `ALL_TOOL_DEFINITIONS` with `["assistant"]` role, OR have the turn use a purpose-built assistant bet-tools registry. State which, and add it as an explicit task. Until `edit_bet` is in the registry the turn drives, AC4 is unbuildable.

- **[plan §"Types/contracts" — "SessionConfig change … sets `tools: <assistant tool names>`" + §design-it-twice B1] `SessionConfig.tools` is never read by the builtin adapter; the loop uses `session.toolDefs` (the WHOLE injected registry). The "scope the model to create_bet/edit_bet" claim is false.** Verified: `runChatTurn` (and `runExecuteTurn`/`runPlanningTurn`) pass `tools: session.toolDefs` to `callLlm`; `session.toolDefs` is populated by `setSessionToolRegistry` → `toolDefsFromRegistry(registry)` = every tool in the registry. `SessionConfig.tools` has no consumer in `builtin-harness-adapter.ts`. Consequence: with `buildToolRegistry(ctx,{role:'assistant'})`, the conversational Assistant is handed the FULL assistant role surface — `create_team`, `add_agent`, `create_routine`, `update_routine`, `submit_review`, `handoff_to`, `send_message`, `create_task` — not just `create_bet`/`edit_bet`. That is a far wider authority than AK4's concept ("authors/updates exactly one draft bet") and a real abuse surface: a conversational turn could now create teams, add agents, hand off, or post reviews. → Fix: the turn must inject a registry containing ONLY the bet-drafting tools (build a 2-tool registry, or filter). Do not rely on `SessionConfig.tools`. The plan must name the exact tool whitelist the conversational registry exposes and verify it (a unit test asserting the injected `toolDefs` are exactly `[create_bet, edit_bet]`).

### WARNING

- **[plan §"Acceptance criteria" AC3(b) + §reconciliation re: HIGH_RISK_TOOLS] The plan's premise that HIGH_RISK_TOOLS enforces a pre-execution gate is wrong — it is DEAD CODE — so the "resolution" is moot, but the plan should say so and AC3's static guarantee should target the right artifact.** Verified: `HIGH_RISK_TOOLS`, `ASSISTANT_TOOLS`, and `toolsForAssistant()` in `assistant-tools.ts` are imported by NOTHING in production (only their own result file + tests). The docstring "the dispatcher checks this set" describes a gate that was never built. So there is no live pre-execution review gate to bypass — the plan's hard-rule-#3 "resolution" is correct by accident. AC3(b)'s real static guarantee is: **the registry the conversational turn injects contains no commit/ship/kill tool, and no such tool exists in the codebase** (`grep` for `commit_bet`/`ship_bet`/`kill_bet` → none; commit is only `POST /bets/:id/commit`). That is a lint/static property, correctly NOT a runtime test. → Fix: (a) reframe AC3(b) around the *injected conversational registry* (not `toolsForAssistant()`, which the turn never uses); (b) the "no commit tool" property is best a unit assertion on the injected registry's tool names plus a grep-based lint, as the plan says — keep it static, good. (c) Update or delete the misleading `assistant-tools.ts` docstring/dead code so the next agent doesn't trust a gate that isn't there (note for `/write-code` or a follow-up; out of strict AK4 scope but flag it).

- **[plan §"Ordered tasks" Task 4 — "which draft" binding] The most-recent-assistant-authored-draft binding is under-specified against real failure modes the reviewer prompt named.** "Most-recent `draft` bet authored by `ast-${userId}` in this conversation" — but: (i) **bets have no thread/conversation FK** (`create-bet.ts` writes `{id, teamId, description, doneCondition, hypothesis, status, createdAt}` — no `threadId`, no `authorId`/`createdBy`). So "authored by ast-${userId} in this conversation" is **not queryable from the bets table** as written. The binding must come from the thread transcript (scan prior `payload.toolCalls` for `create_bet` ok results → newest `betId`), not a bets query. The plan says "resolve … in this conversation" but never says HOW given no conversational FK. → Fix: state the binding source explicitly = parse the thread's prior assistant messages' `toolCalls` for the newest `create_bet` `betId`, then verify it is still `status='draft'` (if committed, do NOT rebind — drop it, let a new draft be created or reply honestly). (ii) Race/concurrency: `inFlightTurns` already serializes per `userId:threadId`, so two concurrent turns can't double-create — note this as the mitigation. (iii) Multiple drafts in one thread (founder asks for two bets): plan's cardinality is "one draft per conversation" but nothing enforces it — the binding picks newest, silently orphaning earlier drafts. Accept or constrain; state which.

- **[plan §"Failure-Mode Coverage" / §"Acceptance criteria"] Loop-bound exhaustion has no defined behavior or test.** Plan caps `maxToolIterations=3` but never says what happens when hit: does the turn still persist a reply (never-silent invariant), or does it silently stop? The existing task loop has a `runMaxIterationsTurn` wrap-up; the conversational loop has no equivalent. → Fix: specify that on cap-hit the turn emits a completion with whatever text exists (or a fallback reply) so AH3's never-silent invariant holds, and add a test: stub adapter scripted to emit a tool_use every iteration → assert a reply is still persisted and ≤3 tool executions occurred.

- **[plan §"Security & abuse cases" — cross-team] `create_bet` has intentional cross-team scope (`@lore AE3: Cross-team scope is intentional`) and does NOT verify the teamId belongs to the user — it only checks the team exists.** The plan says `teamId` is "bound server-side from the resolved user team, NOT from raw model output where avoidable." Good — but "where avoidable" is doing heavy lifting. If the model passes a `teamId` (the tool requires it as input), and the prompt-injected/hallucinated teamId is some *other* team that exists, `create_bet` will happily draft a bet on it. The mitigation must be hard, not "where avoidable": the turn must IGNORE any model-supplied teamId and force `ctx.teamId = users.teamId` for `userId`. → Fix: state that the conversational `create_bet` path overrides/injects `teamId` from `users.teamId` and the model cannot redirect it. (Note: `users.teamId` exists and is the single-team source — team resolution is straightforward, plan's "single/default team" is correct.)

### SUGGESTION

- **[plan §"Verifiability" / AC tests] Verifiability is the weakest dimension (5) and it is this codebase's first principle.** The AC tests are described as integration tests with a "stub adapter scripted to emit a create_bet tool call" — but the plan never names the existing stub-adapter mechanism or confirms one can script tool_use → completion sequences for the *builtin* adapter's new loop. AH3's tests bypassed `startSession` with stub adapters (per the @lore S7 note). The new behavior lives INSIDE `runChatTurn`'s loop on the *builtin* adapter — a stub adapter that bypasses `startSession` will NOT exercise the loop. → Confirm the test drives the real builtin adapter with a scripted `callLlm` (mock the LLM, not the adapter), or the AC2/AC4 integration tests will test a stub, not the loop. Name the LLM-mock seam. Add `builtin-harness-adapter.test.ts` (Task 1's adapter unit test) to the verification list as the primary proof of the loop — it is, but make AC2/AC4 explicitly assert through the real loop too.
- **[plan §"Risks" snapshot net] The snapshot-net risk is mis-stated: `AssistantOverlay` is in `packages/web`, not `packages/design-system`, so it is NOT a catalogued story and the catalog snapshot net does not cover it.** `BetCard` IS catalogued but AK4 does not change `BetCard`. So no re-bless is needed unless a design-system story changes (it won't). → Drop or correct the snapshot risk; the relevant web test is a `.test.tsx` component test for the overlay (Task 6), which the plan already has.
- **[plan §protectedTests] Good list, but add `packages/server/src/harness/__tests__/builtin-harness-adapter.test.ts` (or wherever the adapter loop tests live) to protectedTests — Task 1 changes the most-shared harness file and the existing task-loop behavior (planning/execute/reflect) must not regress.** The conversational loop change sits next to `runExecuteTurn`; a regression there breaks every task session.

### What's Working Well

Design-it-twice B (B1 vs routing through the task path) is a real tradeoff, not theatre.
- Plan reconciliation correctly identified the AC1-already-shipped reality and the `tools: []` gap at the right line. The draft-only `edit_bet` guard (Task 5) and the no-DB-migration conclusion are both correct against the actual schema and `edit-bet.ts` (which today has zero status check — guard genuinely needed).
