## Q1 — REST vs RPC-per-action vs GraphQL vs MCP-as-the-API

### 1.0 MCP protocol facts that constrain every option (T1)

- **2025-11-25 spec.** JSON Schema 2020-12 became the default dialect for tool schemas (SEP-1613). Tool-name guidance added (SEP-986: 1–128 chars, `[A-Za-z0-9_.-]`, unique per server). Input-validation errors are to be returned as tool *execution* errors (`isError: true`) so the model can self-correct, not protocol errors (SEP-1303). `inputSchema` MUST be a JSON Schema object with `type: "object"`; `outputSchema` optional; `structuredContent` for typed results. Streamable HTTP = one endpoint, POST per message, optional SSE; a client GET opens a standalone SSE stream for server→client messages; `Mcp-Session-Id` sessions; `Last-Event-ID` resumability; servers may drop SSE connections and let clients "poll" (SEP-1699). — https://modelcontextprotocol.io/specification/2025-11-25/changelog , https://modelcontextprotocol.io/specification/2025-11-25/server/tools , https://modelcontextprotocol.io/specification/2025-11-25/basic/transports
- **2026-07-28 spec (final, published 2026-07-28; RC 2026-05-21).** Big transport change: "Removal of the GET stream endpoint. Removal of protocol-level sessions." Protocol is stateless — no `initialize` handshake; each request carries version/capabilities in `_meta` (SEP-2575). `tools/list` "MUST NOT vary per-connection" but "MAY vary by the authorization presented on the request — for example, returning only the tools the caller's granted scopes permit". Server→client interactions become Multi Round-Trip Requests (`InputRequiredResult`, SEP-2322); servers "MUST NOT initiate JSON-RPC requests". Long-lived change notifications ride a `subscriptions/listen` POST whose response is a long-lived SSE stream. The filter is closed: `toolsListChanged`, `promptsListChanged`, `resourcesListChanged`, `resourceSubscriptions: string[]`; "The server MUST NOT send notification types the client has not explicitly requested." `notifications/resources/updated` carries only `uri`. SSE resumability removed ("Resumable SSE streams via `Last-Event-ID` are not supported"). `Mcp-Method` and `Mcp-Name` headers REQUIRED on every POST. `inputSchema`/`outputSchema` loosened to any 2020-12 keywords (SEP-2106). Tasks moved to an extension. Stateful tools must use explicit handles as ordinary arguments. Roots/Sampling/Logging deprecated. — https://modelcontextprotocol.io/specification/2026-07-28/changelog , https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http , https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/subscriptions , https://modelcontextprotocol.io/specification/2026-07-28/server/tools , https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/
- **Authorization (2025-11-25, still the model in 2026-07-28 with hardening).** "The Model Context Protocol provides authorization capabilities at the transport level." MCP server = OAuth 2.1 resource server; client MUST send RFC 8707 `resource`; server MUST validate audience; token passthrough forbidden; stdio "SHOULD NOT follow this specification, and instead retrieve credentials from the environment." Per-tool authorization is not specified beyond "Servers MUST: Validate all tool inputs · Implement proper access controls". — https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization
- **MCP Apps extension (2026-01-26, folded into the 2026-07-28 extensions framework).** A server can ship an HTML UI rendered by the *host* in a sandboxed iframe; that UI may issue `tools/call` which the host proxies to the server. This is UI-inside-an-agent-host, not a standalone app's frontend. — https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx
- **TypeScript SDK.** README describes v2 implementing 2026-07-28, Zod v4 (`import * as z from 'zod/v4'`), Standard Schema (Valibot/ArkType) also accepted, `registerTool` with `inputSchema`/`outputSchema`, Streamable HTTP with stateless mode, thin `@modelcontextprotocol/hono` adapter. npm `latest` dist-tag still resolves to 1.30.0 on 2026-09-11 — v2 tagging not verified (T1 with uncertainty). — https://github.com/modelcontextprotocol/typescript-sdk
- **Zod 4 → JSON Schema.** `z.toJSONSchema()` targets "draft-2020-12" by default (also draft-07/-04/openapi-3.0); `io: "input"` vs output; unrepresentable types (Date, Map, transforms) throw by default; `.meta()` descriptions copied. — https://zod.dev/json-schema . Known SDK issue: descriptions from Zod 4 schemas not propagating into tool definitions in some cases (issue #1143, opened 2025-11-20; shown closed, resolution text not visible in fetch). — https://github.com/modelcontextprotocol/typescript-sdk/issues/1143
- **Hono ↔ MCP.** `@hono/mcp` wraps the SDK's `StreamableHTTPTransport`; works on Node/Bun/Deno/Workers; provides `simpleMcpAuthRouter`. — https://github.com/honojs/middleware/tree/main/packages/mcp

### 1.1 REST (resource routes)

- (a) Named actions: the strongest primary evidence is *against* mirroring resource endpoints into tools. GitHub's MCP lead: "One-to-one mapping with APIs was a poor goal" (T2, arcade.dev quoting Sam Morrow, 2026-03) — https://www.arcade.dev/blog/enterprise-mcp-lessons-from-githubs-mcp-server-launch/ ; Morrow's own post: ">100 tools (just over 40 by default)", "agents get worse at using GitHub as we add more tools", "Everyone used the default settings", fix = "reduced default tool count by 49%", "consolidated CRUD operations", output tokens cut ">75%" on `list_pull_requests` (T2) — https://sam-morrow.com/blog/progressive-discovery-in-mcp-part-1 . Notion: the open-source 1:1 API mapping "created suboptimal experiences for AI agents, like high-context token consumption" (T2, 2025-07-15) — https://www.notion.com/blog/notions-hosted-mcp-server-an-inside-look . Cloudflare: "An MCP server is not our entire API schema… one tool from our MCP server may map to one API, another tool may map to many" (T2, 2025-05-01) — https://blog.cloudflare.com/thirteen-new-mcp-servers-from-cloudflare/ . Anthropic: "Tools can consolidate functionality, handling potentially multiple discrete operations (or API calls) under the hood"; "More tools don't always lead to better outcomes" (T2, 2025-09-11) — https://www.anthropic.com/engineering/writing-tools-for-agents .
- (b) End-to-end types: no primary source claims REST gives inferred TS types without a codegen/contract layer; ts-rest/oRPC/Hono RPC are the contract layers (see 1.2).
- (c) JSON Schema: OpenAPI→tool generation is what Notion did (OpenAPI→Zod→tools, T2) and what Stripe's generic `stripe_api_read`/`stripe_api_write` + `stripe_api_search`/`stripe_api_details` do (T1) — https://docs.stripe.com/mcp .
- (d)–(f): nothing REST-specific in the sources beyond standard bearer auth.

### 1.2 RPC-style, one procedure per action

**tRPC (T1 unless noted)**
- v11 released 2025-03-21, "largely backward-compatible" with v10; adds SSE subscriptions as an alternative to WebSockets, `httpBatchStreamLink`, FormData/binary. — https://trpc.io/blog/announcing-trpc-v11 . Latest 11.18.0 (2026-06-17, npm).
- (a) Procedures are named; routers nest. (b) Inference from router type, no codegen.
- (c) OpenAPI: official `@trpc/openapi` exists in the monorepo, generates OpenAPI 3.1 by static type analysis, TODO still lists SSE subscriptions/non-JSON; docs page titled "OpenAPI (alpha)", "versioned like 11.x.x-alpha". — https://github.com/trpc/trpc/tree/main/packages/openapi , https://trpc.io/docs/openapi . MCP: community only — `trpc-mcp` (Jacse; stdio; `meta({ openapi: { enabled: true } })`; 3 commits, 42 stars) — https://github.com/Jacse/trpc-mcp ; `trpc-to-mcp` (iboughtbed; selective) — https://github.com/iboughtbed/trpc-to-mcp . No first-party MCP output.
- (d) Context/middleware carries the actor; the server-actions post states "For any API endpoint that is exposed over the network, you need to validate and authorize requests" and that server actions "are by no means a silver bullet" (2024-05-23). — https://trpc.io/blog/trpc-actions
- (e) Docs: "we recommend using SSE for subscriptions as it's easier to setup and doesn't require setting up a WebSocket server"; `tracked()` + `lastEventId` for resume; warning "make sure you set up the event listener before fetching events from your database". — https://trpc.io/docs/server/subscriptions
- (f) Electron: `electron-trpc` / `trpc-electron` (fork for v11) add an `ipcLink`; discussion #4675 (2023) shows running one tRPC client over IPC and another over HTTP in the same app was awkward (T2). — https://electron-trpc.dev/ , https://github.com/mat-sz/trpc-electron , https://github.com/trpc/trpc/discussions/4675

**oRPC (T1 unless noted)**
- 1.15.0 (2026-08-08), ~5.6k stars. Contract-first optional; Standard Schema (Zod/Valibot/ArkType). Own comparison table (vendor, T1-as-self-description): OpenAPI spec generation oRPC ✅ / tRPC 🟡 / Hono ✅; typed SSE oRPC ✅ / tRPC ✅ / Hono 🛑; Next server actions oRPC ✅ / tRPC ✅ / Hono 🛑; "AI SDK integration" oRPC ✅ only. — https://orpc.dev/docs/comparison
- (c) `@orpc/ai-sdk` "Converts a procedure into an AI SDK Tool by leveraging existing procedure definitions" — i.e. one declaration → HTTP + LLM tool, but AI SDK tools, not MCP tools. — https://orpc.dev/docs/integrations/ai-sdk . `https://orpc.dev/docs/integrations/mcp` returned 404 on 2026-09-11: no first-party MCP adapter found.
- (e) Event iterator = async generator; `lastEventId` handed to the handler; `withEventMeta` sets id/retry; "Reconnection with the last event ID is handled automatically" with the Retry plugin. — https://orpc.dev/docs/event-iterator
- (f) Adapters listed: Node, Bun, Cloudflare Workers, Deno; no Electron adapter listed. — https://github.com/middleapi/orpc
- Performance claims ("~20% faster type-check, ~28% less memory on 3,000 procedures") appear only in aggregator guides — **T3, unverified**. — https://www.pkgpulse.com/guides/orpc-vs-trpc-vs-hono-rpc-type-safe-apis-2026

**Hono RPC (`hc`) (T1)**
- Docs: "When using RPC, the more routes you have, the slower your IDE will become" because "massive amounts of type instantiations are executed"; official advice is to compile types before use; sub-apps must be chained into `app.route()` or inference is lost; a handler returning a `.then()` chain "loses its response type, so the client infers `unknown`"; `c.notFound()` breaks inference; monorepo needs `strict: true` on both sides. — https://hono.dev/docs/guides/rpc
- Issue #3869 (2025-01-30, open): 8-minute esbuild compile in a multi-hundred-module app; inferring the whole app to produce client types. — https://github.com/honojs/hono/issues/3869 . Issue #3893 (2025-02-06, open, triage): TS2589 "excessively deep" with `app.route('/', router)` + `testClient`, type collapses to `any`. — https://github.com/honojs/hono/issues/3893 . Issues #3738/#3749: union responses inferred as `null`, generic imports lose inference. — https://github.com/honojs/hono/issues/3738 , https://github.com/honojs/hono/issues/3749
- (c) No first-party procedure→tool projection; MCP served separately via `@hono/mcp`. (e) `streamSSE` helper with `id`/`event`; error thrown after stream start bypasses `onError`. — https://hono.dev/docs/helpers/streaming

**ts-rest (T2/T3)** — "Future of ts-rest" issue #797 opened 2025-05-07 asking whether maintainers intend to continue; no maintainer reply visible in the fetched page. PR activity continued into early 2026 per search summaries (T3). — https://github.com/ts-rest/ts-rest/issues/797

**Plain JSON-RPC 2.0 (T1)** — request = "A String containing the name of the method to be invoked" + params; notifications (no `id`, no reply); batch arrays; "transport agnostic… within the same process, over sockets, over http". MCP itself is JSON-RPC. — https://www.jsonrpc.org/specification

### 1.3 GraphQL

- (a) Mutations are named actions; Apollo's guidance is to make mutations "as specific as possible… semantic actions", not one monolithic update (T2) — https://www.apollographql.com/blog/graphql/basics/designing-graphql-mutations/ . Linear's public API uses `issueCreate` / `issueUpdate` (T1) — https://linear.app/developers/graphql .
- (b) Types reach React via a codegen step (GraphQL Code Generator: config + generate + watch mode) (T1) — https://the-guild.dev/graphql/codegen/docs/getting-started
- (c) Apollo MCP Server (Rust) turns static GraphQL operations into MCP tools, or lets the model introspect; "No writing tool code, just define the fields you need in the operation" (T2, 2025-05-22) — https://www.apollographql.com/blog/building-mcp-tools-with-graphql-a-better-way-to-connect-llms-to-your-api , https://github.com/apollographql/apollo-mcp-server
- (e) graphql.org subscriptions page returned 403; not cited.
- Note: Linear ships both GraphQL and MCP, but neither Linear source states its MCP tools are generated from the GraphQL schema; a third-party review says the tools use "curated parameter sets rather than exposing Linear's full GraphQL filter capabilities" (T2) — https://blog.fiberplane.com/blog/mcp-server-analysis-linear/

### 1.4 MCP over Streamable HTTP as the app's own primary API

- (a) Tools are named actions by construction (T1).
- (b) No inferred end-to-end TS types: the wire contract is JSON Schema; SDK `registerTool` gives handler-side types from Zod; the client sees `tools/list` at runtime. Vercel's `mcp-to-ai-sdk` exists precisely because dynamic definitions "drift" and generic descriptions lower accuracy, so they generate static tool files into the repo (T2, 2025-09-17) — https://vercel.com/blog/generate-static-ai-sdk-tools-from-mcp-servers-with-mcp-to-ai-sdk . Supabase ships `createToolSchemas()` for typed client-side use (T1) — https://github.com/supabase/mcp
- (c) Native: Zod→2020-12 via SDK.
- (d) OAuth 2.1 resource-server model; token audience-bound; `tools/list` may vary by scopes (T1, above). Stdio: credentials from environment.
- (e) After 2026-07-28 the only server-push channel is `subscriptions/listen` with a closed filter (tools/prompts/resources list changes + `resources/updated` for subscribed URIs, payload = `uri` only). Domain events would have to be modelled as resources and re-read after each `resources/updated`. No resumability. This is a direct reading of the spec text; the spec does not discuss application-domain events (T1 + inference).
- (f) Stateless by design in 2026-07-28 ("any server instance can handle" requests) (T1). Required `Mcp-Method`/`Mcp-Name` headers and header/body validation add transport obligations a plain HTTP client would not have (T1).
- Does anyone run MCP as their own UI's API? **No evidence found.** Cloudflare's `use-mcp` React hook (2025-06-18) connects a React app to *remote* MCP servers with OAuth handled — positioned as connecting to external servers, not as an app's backend (T2) — https://blog.cloudflare.com/connect-any-react-application-to-an-mcp-server-in-three-lines-of-code/ . MCP Apps is UI hosted inside an agent client (T1). A 2026-02 consultancy post proposes mounting an MCP server beside the HTTP app sharing services — "MCP as backend-for-frontend for LLMs", explicitly two interfaces for two consumers (T3) — https://shinesolutions.com/2026/02/26/building-mcp-your-llms-new-backend-for-frontend/ . Every shipped product examined (Q2) runs MCP as a second surface over an internal service/API layer.
- Tool-count / context evidence: GitHub tool definitions ≈50k tokens (Vercel, T2); tool-selection accuracy drops as tool count grows (RAG-MCP 43%→<14%; per-tool 300–600 tokens) — aggregator numbers, **T3** — https://getunblocked.com/blog/mcp-tool-overload/ . Anthropic's own guidance favours "a few thoughtful tools targeting specific high-impact workflows" (T2).

## Q3 — "Actions" as the first-class backend unit

- **React Router / Remix actions (T1).** One `action` per route module; invoked by `<Form>`, `useSubmit`, or fetchers; "When the action completes, all loader data on the page is revalidated". A route-shaped unit, not a project to tools. — https://reactrouter.com/start/framework/actions
- **Next server actions + tRPC (T1, 2024-05-23).** tRPC's experimental caller lets a procedure be a server action; they caution server actions "lack essential API safeguards" and are "by no means a silver bullet". — https://trpc.io/blog/trpc-actions
- **Phoenix contexts (T1).** "Contexts are modules that encapsulate data access and data validation"; a context "centralizes all functionality related to" a domain "instead of scattering logic around controllers, LiveViews, etc." — the named-function boundary with thin web callers. — https://phoenix.hexdocs.pm/contexts.html
- **Convex (T1).** Functions are the unit: queries (reads, reactive), mutations (transactions), actions (side effects). Zen: "Use a query for nearly every app read"; "never use an action if a query or mutation will get the job done"; don't set UI state from mutation return values, "Let queries and the sync engine do that." — https://docs.convex.dev/understanding/zen . LLM tools: `createTool({ description, args: zod, handler(ctx) })` where the handler calls `ctx.runQuery/runMutation`; docs do not offer exposing an existing Convex function as a tool without a wrapper. — https://docs.convex.dev/agents/tools
- **Zero (Rocicorp) (T1).** `defineMutator` — "A copy of each mutator exists on both the client and on your server"; server copy adds authorization; push endpoint runs the server mutator "in a transaction against your database"; mutators are named (`issue.update`). Fit: "Zero is not local-first. It's a client-server system with an authoritative server"; "doesn't support offline writes"; TS clients only; needs `zero-cache` with a SQLite replica. — https://zero.rocicorp.dev/docs/mutators , https://zero.rocicorp.dev/docs/when-to-use
- **Electric (T1).** "Electric does not do write-path sync"; four write patterns from "online writes" via your existing API (simplest) to through-the-DB (heavy dependency, complex schema machinery). — https://electric.ax/docs/guides/writes
- **Linear sync engine (T2, 2024-08-14).** Client mutates an in-memory object graph; a transaction queue persists to IndexedDB and posts to the backend; server publishes over WebSocket; LWW rather than CRDTs. — https://www.fujimon.com/blog/linear-sync-engine
- **One declaration → HTTP + tool.** Evidence of this exact projection: oRPC procedure → AI SDK tool (T1); Notion OpenAPI→Zod→MCP tool pipeline (T2); Supabase `createToolSchemas` (T1); MCP SDK `registerTool` takes the Zod schema that also validates the handler (T1). No source describes one declaration projecting to a UI action as well; the UI side is always hand-wired.
- **Vertical slice** (T3, .NET-centric): one file per feature holding command + validator + handler + endpoint. — https://milanjovanovic.tech/blog/vertical-slice-architecture
- **Practitioner statements on surface size.** Anthropic: few tools targeting high-impact workflows (T2). Cramer: tools should steer intent, not expose endpoints (T2). GitHub: 100+ was too many; ~40 default still cut by half (T2). Nobody in the sources addresses "17 actions" specifically; the closest data points are Stripe (10 tools + generic read/write), Notion (18), Sentry (8 visible), Linear (23), all in the 8–25 band.

## Q4 — One event stream, two audiences (humans: notifications; agents: triggers)

- **Outbox in a Linear-like product (T2, 2026-02-26, Plane).** Postgres triggers write to an outbox "atomically within the same database transaction"; a poller claims batches with `FOR UPDATE SKIP LOCKED` and publishes to a RabbitMQ fanout feeding three consumers: webhook dispatcher, automation engine, live server (Socket.IO). At-least-once; `event_id` UUID for idempotency; lessons: "Triggers beat application-layer detection"; "Publishing full event context eliminates consumer-side API coupling". — https://plane.so/blog/building-zero-loss-event-streaming-with-postgresql-django-and-rabbitmq
- **Outbox semantics (T2, Dudycz).** Outbox = at-least-once; consumers must be idempotent (unique message-id constraint, upserts). Polling interval is hard to tune; logical-replication push avoids it but needs PK + WAL-retention care (2022). — https://event-driven.io/en/outbox_inbox_patterns_and_delivery_guarantees_explained/ , https://event-driven.io/en/push_based_outbox_pattern_with_postgres_logical_replication/
- **LISTEN/NOTIFY limits.** Recall.ai (T2, 2025-07-01): `NOTIFY` takes a global `AccessExclusiveLock` at commit to serialize notifications; with "tens of thousands of simultaneous writers" it caused three outages (2025-03-19..22); they moved the logic to the application layer. — https://www.recall.ai/blog/postgres-listen-notify-does-not-scale . DBOS rebuttal (T2, 2026-07-24): per-transaction NOTIFY capped at ~2.9K writes/s; batching notifies in memory and flushing in one transaction reached ~60K/s with 15–100 ms latency, keeping slow polling as a fallback. — https://www.dbos.dev/blog/postgres-listen-notify-scalability . Atomic Object (T2, 2025-02-26): NOTIFY→SSE bridge; each connected user holds a server + DB connection; doesn't work through transaction poolers (PgBouncer); watch connection timeouts. — https://spin.atomicobject.com/postgres-listen-notify-events/
- **Postgres-as-queue, when it's enough.** Prisma (T2, 2026-07): SKIP LOCKED table queue covers "sending emails, delivering webhooks, generating exports, syncing external APIs"; "use `NOTIFY` to wake the worker… and keep a slow poll as the fallback"; move off it only when you can name the limit: sustained thousands of jobs/s (vacuum), many-consumer fan-out ("a log like Kafka"), or rate-limit/priority features. — https://www.prisma.io/blog/you-dont-need-a-job-queue-postgres-already-has-skip-locked . Yen (T2, 2026-05-04): bloat, vacuum pressure, MultiXact SLRU contention appear at "thousands of concurrent workers". — https://richyen.com/postgres/2026/05/04/postgres_job_queue.html
- **Libraries (T1).** pg-boss 12.31.0: SKIP LOCKED, transactional enqueue with Drizzle/Knex/Kysely/Prisma adapters, cron/RRULE, retries, DLQ, pub/sub fan-out, LISTEN/NOTIFY wake-up; Node ≥22.12, PG ≥13; single maintainer. — https://github.com/timgit/pg-boss . graphile-worker 0.18.0: "Jobs start in milliseconds thanks to Postgres' LISTEN/NOTIFY"; "runs right from within the node project". — https://worker.graphile.org/
- **Push to browsers.** tRPC recommends SSE over WebSocket for subscriptions and provides `tracked()`/`lastEventId` resume (T1). oRPC event iterator with `lastEventId` + retry (T1). Hono `streamSSE` (T1). MCP 2026-07-28 itself is SSE-on-POST with no resume (T1). General SSE-vs-WS articles are T3 and add nothing beyond "SSE for one-way push".
- **Agents as consumers.** In the sources, agent triggers are just another consumer of the same stream (Plane's "automation engine"). MCP offers no domain-event channel; agent triggers must be delivered outside MCP (webhook/queue/subscription) — inference from spec text (T1 + inference).
- **In-process bus.** No reputable source specifically endorses a bare in-process EventEmitter fan-out; the small-team sources all start from a Postgres table (outbox or jobs) and add NOTIFY as an optimisation, not the source of truth.

## What the evidence supports (and what it doesn't)

**Supported by T1/T2:**
1. Every shipped product examined runs MCP as a **second, curated surface** over an internal action/API layer; none uses MCP as its UI's transport. Tools are hand-shaped around intents, counts sit roughly 8–25 by default, and 1:1 endpoint mirroring is the one clearly stated regret (GitHub, Notion).
2. The agent authenticates **as the user via OAuth** and inherits the user's existing permissions (Linear, Notion, Atlassian, GitHub, Stripe, Supabase). The MCP auth spec only covers transport-level bearer/audience; per-tool authorization is the server's job — consistent with "same invariant function decides the UI button and the tool".
3. A **single declaration** (name + Zod input/output + handler) already projects to HTTP and to LLM/MCP tools in first-party tooling: MCP SDK `registerTool`, oRPC → AI-SDK tools, Notion's OpenAPI→Zod pipeline, Supabase `createToolSchemas`. Zod 4 emits JSON Schema 2020-12 by default, which is the MCP default dialect. No source shows the same declaration also driving a UI action; that wiring is always by hand.
4. **MCP is a poor primary event channel** after 2026-07-28: the only server-push is `subscriptions/listen` with a closed set of protocol notifications (payload for resources = `uri` only), no resumability, and servers may not initiate requests. Domain events to humans and agents need their own channel.
5. For a small team, the sources converge on **Postgres table as source of truth** (outbox or jobs table with SKIP LOCKED), NOTIFY as a wake-up optimisation with a slow-poll fallback, at-least-once + idempotent consumers, and adding a broker only when a nameable limit is hit (thousands of jobs/s, many-consumer fan-out, priority/rate features). Plane's design shows one outbox feeding webhooks, automations and live UI.
6. Among TS RPC options: tRPC v11 is stable with first-party SSE subscriptions but only alpha OpenAPI and community MCP; oRPC has first-party OpenAPI, resumable SSE, and procedure→AI-SDK tool projection but no MCP adapter and is younger; Hono RPC has documented, still-open type-inference cost/collapse issues around `app.route` that grow with route count.

**Uncertain / not supported by evidence found:**
- Whether any product will adopt MCP as its own app API remains unproven; only a T3 consultancy post argues for co-mounting, and it still keeps two interfaces.
- oRPC vs tRPC type-check performance numbers are T3 (aggregator sites) and were not reproduced.
- Tool-count vs accuracy numbers (43%→<14%, 300–600 tokens/tool) come from aggregators citing papers I did not read directly (T3); the qualitative direction is backed by GitHub, Sentry, Anthropic, Cloudflare (T2).
- MCP TypeScript SDK v2 (2026-07-28 support) is described in the README, but npm `latest` still resolves to 1.30.0 on 2026-09-11; which tag ships v2 was not verified.
- Linear's tool count (23) and Notion's (18) are third-party counts as of late 2025/early 2026 and may have changed.
- PostHog tool count and auth method, and Stripe agent-toolkit internals, were not visible in the pages fetched.
- Nothing in the sources speaks to a 17-action surface specifically; the "small curated surface" guidance is the closest available.
