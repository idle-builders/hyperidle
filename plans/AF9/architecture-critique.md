### WARNING

- **[plan §AC1 verification / Task 1] The AC1 test as written will be flaky — `emit` does not await the async relevance handler.** `EventBus.emit` is synchronous over handler *invocation*, but the relevance handler is `void (async () => { ... recomputeScores ... })()` (Task 1's own shape). So `app.request("GET /api/knowledge/:id")` returns and `emit` returns *before* `recomputeScores` writes `relevanceScore`. The AC1 method ("GET once (or twice), then assert `relevanceScore` is now non-null") races the async recompute and will intermittently read the pre-write value. The codebase already has the correct pattern: `lifecycle-propagation.integration.test.ts` wraps every post-emit assertion in `await vi.waitFor(async () => {...})` precisely "because the handler is async fire-and-forget." → **Fix:** AC1 verification must assert through `await vi.waitFor(...)` (poll until `relevanceScore` is non-null), not a single synchronous read after GET. State this explicitly in the AC1 method and in Task 1's test note so `/write-tests` doesn't author the racy version. (AC4's routine path is awaited directly via `runBuiltinRoutine`, so it is not affected — only the emit-driven AC1.)

- **[plan §AC4 / Task 4] AC4 risks being only partially met for the "common case," and the plan half-admits it.** AC4 is "attention-sorted triage orders by a *real, populated* score rather than a constant." Task 4 piggybacks `recomputeScope` on the daily promotion sweep over a *bounded* pool. Two soft spots: (1) `recomputeScope` *requires* a filter (`FILTER_REQUIRED`) and *rejects* oversize batches (`BATCH_TOO_LARGE`, hard cap `MAX_RECOMPUTE_BATCH`) — so "the provisional + active pool" is NOT a valid argument as loosely stated; the plan's R3 fallback ("scope to the sweep's bounded candidate set") is the only form that actually type-checks and runs, and that set is just the items the sweep *scanned*, not the whole triage surface. (2) On a *daily* cadence, a normally-created item that is never a promotion candidate may sit with null `attentionScore` for up to 24h — attention-sorted triage on freshly-created items still orders by null/constant in that window. → **Fix:** (a) Make Task 4 commit to the R3 narrow form (filter by the candidate `ids`) as the *primary* design, not a fallback — the broad-pool phrasing is dead on arrival against `recomputeScope`'s guards. (b) State explicitly in the AC4 method which population path covers the common case, and verify the AC4 test seeds items that the sweep actually touches (so the populated-score assertion is real, not coincidental). If the intent is "eventually populated on cadence," say so; don't let the AC read as "populated on create."
