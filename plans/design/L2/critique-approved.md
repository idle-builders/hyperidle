## Did the synthesis address the original critique's 3 MINOR findings?
- Pill chrome dropped: yes. §2.3 is explicit — "NO pill background. NO border." Just text + glyph in inline-flex with `gap: 4px`. Resolves the heading-scale tag-look, the baseline wobble, and the wrap-onto-empty-line problem.
- Strip radius `--r2`: yes. §2.4 documents top corners 0 (flush continuation) / bottom corners `--r2` for `single`/`thread`; all four `--r2` for `lost` in the foot. Echoes parent's body frame, code, and table radii.
- 3-position spec locked + screenshots: yes. §10 question 7 commits the architect to 3 positions × {rest, hover, focus} × {dark, light} = 18 goldens in the design-system Playwright suite. Reasonable budget.
- A11y tightening (aria-hidden + parent button): yes, per-position. §2.3 splits cleanly: `trailing-inline` uses `aria-hidden` on decorative text + parent `<button>` with `aria-label`; `chrome-top-right` is plain `<button>` (lives outside prose); `image-overlay` is a labelled button in image's tab order. Read-order stays clean.

## Any new issues introduced by the synthesis pull-ins or the critique-driven changes?
1. **MINOR — Mobile tap target conflicts with AQ-015.** §2.3 and §7 specify a 24×24 tap target on mobile, but `aesthetic-quality.md` AQ-015 mandates ≥ 44 CSS px on every interactive element at viewport ≤ 1024 px. The architect should resolve this — either widen the affordance's hit area to 44 px (visual stays 14 px glyph; pad the wrapping `<button>`) or document the affordance as exempt with concept-quality justification. Recommend the former; it's a one-line fix.
2. **MINOR — `position: absolute` parent button on hover may break list-item geometry.** §2.3 says the wrapping `<button>` is "absolute over the trailing area on `:hover` / `:focus-within`." For `list_item` `trailing-inline`, absolute positioning could overlap the item's bottom-margin / next-item top. The architect should verify with a focused list-with-discussion screenshot in the 18-golden set. Not blocking for /architecture; flag for the visual-regression baseline.
3. **MINOR — Image overlay tab order claim.** §2.3 says the image overlay button is "in tab order when the image is focused." Images are not focusable by default. Architect should clarify whether the image gets `tabindex="0"` (making the image itself a tab stop, which is unusual) or whether the affordance is itself the focus stop adjacent to the image. The latter is conventional.

None of these are structural; all three are architect-handles, not design-redos.
