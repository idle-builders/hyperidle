# Architecture Critique: AK3 — Committing a bet starts work

ARCHITECTURE-SCORE: 6/10  rounds=1  score-line: SA:8 LI:8 AC:7 DM:8 N:8 MD:7 FMC:5 S:6 V:7

Scored against codebase reality, not the plan's self-description. Every reconciliation claim was grep-verified. The plan is structurally strong — correct boundary placement, real dispatch reuse, honest design-it-twice, full AC→verification table, populated protected-tests and route-checklist. It is held back to **6** by one load-bearing technical claim that does not survive contact with the code (the AH3 precedent does **not** do what the plan says it does for the two hardest parts), and by failure-mode gaps around the CAS guard and the "running" status terminal-window.

## Reality checks performed (what I verified)
- `bet-state-machine.ts:228` emits `bet_state_changed { streamId: bet.teamId, betId, fromState, toState }` after commit, exactly once (CAS `WHERE status = fromState`). **Subscriber input is real.** ✔
- `lifecycle-propagation.ts` (fabric) subscribes `bet_state_changed` but acts only on `completed`/`killed`. Plan correctly puts the new subscriber **kernel-side** in `packages/server/src/services/`, not fabric. **Boundary placement correct.** ✔
- `task-dispatcher.ts` fires on `task_state_changed(accepted)` requiring `ownerAgentId NOT NULL`, idempotent via `hasActiveSession`. `transitionTask` allows `proposed→accepted` and emits `task_state_changed` (`task-state-machine.ts:8,109`). **Dispatch reuse path is real; no second route.** ✔ (C4)
- `create-task.ts` sets `ownerAgentId = ctx.agentId` and derives `betId` from `ctx.taskId` (parent task). **The plan's reason for a new tool is correct** — naive create_task reuse would mis-own every task to the PM and has no parent task to derive betId from. ✔ (C3)
- `handoff-protocol.ts:184-202` has the exact eligibility join shape (join `teamMembers` by `task.teamId` → `users WHERE teamId IN memberGroupIds AND status='active' AND role=…`). `AGENT_ROLE_CATALOG` + `findRoleCatalogEntry` exist with `category: "team"|"strategy"|"individual"`. **Eligibility predicate (R1) is grounded.** ✔

The two claims that **fail** the reality check are in §Plan-reconciliation row 3 and §Design-it-twice, both leaning on AH3 — see CRITICAL-1 and CRITICAL-2.

## CRITICAL

- **[plan §Plan-reconciliation row 3, §Design-it-twice synthesis, §Risks R3] The plan claims AH3 is the precedent for Strategy-port context assembly into a scratch sandbox — AH3 does the OPPOSITE.** `runAssistantTurn` (`assistant-turn.ts`) explicitly does **no** sandbox context assembly: its `@lore AH3` notes "no task/bet, no sandbox context assembly," it builds context inline via `composeAssistantPrompt`, and runs the session with `sandboxPath: ""` and `tools: []`. The plan instead wants the decomposition turn to call `getActiveStrategy().assembleContext(...)`. But `ContextAssemblyRequest` (`strategy-port.ts:29-47`) is hard-shaped to a **session admission**: it requires `sessionId`, **`taskId`** (non-optional), `agentId`, `agentRole`, `teamId`, `isRoutine`, and a real `sandboxPath` the Strategy writes files into. A task-free decomposition turn has no task and no provisioned session sandbox. The plan hand-waves a "scratch sandbox" but never says what `taskId` is passed (there is no task yet — that is the whole point of decomposition), nor who creates/cleans the scratch sandbox dir, nor that `assembleContext` MAY THROW (`strategy-port.ts:107`) and the plan's "resolves without throwing" contract must wrap it. → **Fix in the plan:** either (a) specify the exact synthetic `ContextAssemblyRequest` (what `taskId`/`sessionId`/`sandboxPath` are for a task-free turn, `isRoutine: true` so a real Strategy won't read task context, who mkdir/rm's the scratch dir, and the try/catch that converts an `assembleContext` throw into `blocked/failed`), OR (b) drop the Strategy-port call for v1 and assemble PM context inline like AH3 actually does — and then **stop claiming C5 boundary compliance via the port**, because inline assembly is exactly what AH3 does and is honest. Pick one; right now the plan asserts port compliance while citing a precedent that bypasses the port. This is the single biggest gap.

- **[plan §Design-it-twice synthesis, §Risks R2] Session-less execution of `propose_bet_tasks` is unspecified, and the cited precedent cannot run tools.** `builtin-harness-adapter.ts:8-9` documents that the tool registry "is session-scoped (bound to a specific ToolContext with sessionId, agentId, taskId, sandboxPath, watcher)." `ToolContext` (`tool-registry.ts:39-46`) requires non-optional `agentId`, `sessionId`, **`taskId`**, `sandboxPath`. AH3 ran with `tools: []` precisely because there is no task-free tool path. So "the PM calls `propose_bet_tasks` during a harness turn" needs a ToolContext that does not naturally exist for a task-free turn — and `taskId` is the very field the tool must NOT derive betId from (betId comes from the turn's bet). The plan's R2 admits this is unresolved ("if session-less tool exec proves too costly, fall back to deterministic-insert … flag to reviewer") — **flagged.** A plan whose chosen option (A: real PM turn calling a tool) rests on a code path the plan itself isn't sure exists is not yet buildable. → **Fix:** either pin the concrete session-less tool-exec mechanism (cite the real file/function that invokes a tool without a full `provisionSession`, and define the synthetic ToolContext incl. what `taskId`/`sandboxPath` hold), OR make the **deterministic-insert path the v1 primary** (PM produces a structured task list; server inserts via the same `propose_bet_tasks` insert logic invoked directly, not through the harness tool-call loop) and keep the real-harness-tool path behind the `runDecompositionTurn` seam as a later upgrade. Do not ship "Option A" as chosen while its execution path is a question mark — that is design-it-twice theatre (Option A "wins" but the synthesis can't run it).

- **[plan §Subscriber, §AC table AC7] The CAS idempotency guard has a crash-recovery hole that breaks C1, and the plan does not address it.** The guard is `decomposition_status NULL→'running'`; a re-fired event whose CAS hits 0 rows no-ops. But: if the process crashes (or the turn is abandoned) **after** the CAS sets `'running'` but **before** a terminal status is written, the column is stuck on `'running'` forever, and on restart the CAS can never re-acquire it (it is no longer NULL) — so the bet sits permanently in the UI "Decomposing" state with zero tasks. That is a **direct C1 / AC3 violation** ("never sits indefinitely"). The plan's AC6 only covers a turn that throws/times out **within a live process**; it does not cover a `'running'` row orphaned by a crash. → **Fix in the plan:** either (a) add a recovery sweep on boot that finds `decomposition_status='running'` bets older than the window and resolves them to `blocked/failed` (mirrors the dispatcher's accepted-task sweep), or (b) make the UI treat `running` as bounded — but that pushes the lie to the client. (a) is correct. State which. Without it, "running" is not a guaranteed-terminal state and AC3 is not met under crash.

## WARNING

- **[plan §Security & abuse cases — Cost] The cost claim cites a path that lives in fabric and is glossed.** `checkCostCap`/`recordCostAndCheck` are defined in `packages/fabric/src/services/cost-cap.ts` and imported into `session-provisioning.ts`. The plan says decomposition "runs through the existing Kernel cost path (cost stays Kernel-side per boundary)" — but (a) the cost functions physically live in the fabric package (the kernel-strategy doc §3 acknowledges this as a pre-AK2 hard-import gap; cost is *conceptually* Kernel even if the code hasn't moved), and (b) more importantly, those functions are wired into **`session-provisioning`**, which the decomposition turn explicitly does NOT call (R2: "do NOT spin a full `provisionSession`"). So the decomposition PM turn, as planned, **bypasses the session cost path entirely** — an LLM turn with no `checkCostCap` gate. → **Fix:** specify exactly how the task-free decomposition turn enforces the cost cap (which function, called with what `streamId`/team budget, before the turn), or state explicitly that v1 decomposition runs uncapped and why that's acceptable (e.g. one bounded turn behind the human-gated commit). Right now the plan claims cost is "Addressed" while the chosen turn path doesn't touch the cost code.

- **[plan §Decomposition service — Deps] `BetDecompositionDeps` carries `workspace: SandboxAdapter` and `sandboxBasePath` but the field is named `workspace` — the locked vocabulary purged "workspace" as the unit (kernel-strategy-split §4: `~~workspace~~ → sandbox`).** The boot wiring (`server-factory.ts` snippet) also assigns `workspace: workspaceAdapter`. → Rename to `sandbox: SandboxAdapter` to match the locked nouns; using the purged term in a brand-new interface re-introduces the vocabulary the track is eliminating. Naming nit with a locked-doc basis, hence WARNING not SUGGESTION.

- **[plan §AC table AC2, §Failure modes] No timeout value is named for the decomposition turn.** AH3 has `ASSISTANT_TURN_TIMEOUT_MS`; the plan's AC6 asserts "times out → blocked/failed" but never states the bound or which constant governs it. "Decomposing must be bounded" is design Open-Q2 and concept C1's hard requirement. → Name the timeout constant + value (reuse `ASSISTANT_TURN_TIMEOUT_MS` or define `DECOMPOSITION_TURN_TIMEOUT_MS`), and have AC6's test inject a fast-timeout like AH3's `turnTimeoutMs` override. Without a named bound the "bounded" contract is unverifiable.

- **[plan §Tool propose-bet-tasks — owner assignment] Round-robin owner fallback can strand work and is under-specified.** "owner = eligible team agent matching `ownerRole` (fallback: round-robin over eligible agents)" — but if `ownerRole` is a team role with **no** eligible agent (e.g. PM proposes a `growth` task on a builder-only team), round-robin assigns it to a builder, silently mis-owning the work. The dispatcher will then provision a builder session for a growth task. The concept (C3) requires owners be eligible, which round-robin satisfies *mechanically*, but the plan never says whether a role-mismatch should instead be a per-task blocker or just best-effort-assign. → Specify: round-robin-over-eligible is acceptable v1 (decomposition quality is out of scope per spec), but state it explicitly and add a test asserting every produced task lands on an eligible agent even when `ownerRole` has no exact match. Otherwise the builder may "fail" the task or invent role-strictness not in the plan.

- **[plan §Web, design precedence] The plan must pin the precedence order to `approved.md` (`tasks>0` first), NOT the variant-spec order.** `honest-task-state/spec.md:38` and `variant.tsx:38` list `draft → populated`, which hides real tasks on a draft bet that has tasks. `approved.md` correctly lists `tasks>0 → draft → blocked → decomposing`. The plan §Web says "precedence: tasks>0 → draft → blocked → decomposing" — **correct** — but it should explicitly note the variant-spec ordering is superseded so the builder doesn't copy the buggy lower doc. → One sentence in §Web: "Precedence follows approved.md (tasks>0 first); the variant-spec draft-first ordering is superseded." (Cross-ref design-critique WARNING-1.)

## SUGGESTION

- **[plan §Sovereignty / AC5]** AC5's verification is "Static + test: assert no new outbound side effect." That is hard to assert as a positive. Strengthen to a concrete negative: enumerate that decomposition's only writes are `tasks` rows + the two `bets` columns + event emits, and the AC5 test asserts the decomposition turn registers `tools: [propose_bet_tasks]` ONLY (no network/file/MCP tool), so the agent cannot take an external action. C6 holds because tasks only reach `review` via existing machinery — good — but make the "no new tool surface" the testable assertion.
- **[plan §Decomposition service step 3] "pick PM decomposer (team product_manager, else first eligible)"** — "first eligible" as the decomposer is arbitrary and could pick a non-PM (e.g. a brand_voice agent) to author the breakdown. Decomposition quality is out of scope, but document the fallback choice (any team-category agent can author) so it reads as deliberate, not accidental.
- **[plan §Migration]** Forward-only additive columns are fine for SQLite+Postgres (nullable `text`, no default) — no dual-driver hazard. Good. Add a one-line rollback note (drop the two columns) per the data-model rubric; currently absent.
- **[plan §Risks R3]** "Confirm no DB writes in minimal `assembleContext` couple to a real session row" — verified true (minimal `assembleContext` only writes scaffold files, `minimal-strategy.ts`). You can mark R3 RESOLVED. But it only matters if CRITICAL-1 is resolved in favor of keeping the port call.

## What's Working Well
- **Boundary discipline is correct and grep-verified.** The subscriber is kernel-side (not bolted onto fabric's `lifecycle-propagation`), task creation is never behind the Strategy port, and the dispatch reuse (C4) is real — accepted owner-assigned tasks are exactly what `task-dispatcher` already consumes. No forked provisioning route. This is the hardest thing to get right and the plan nails it.
- **The reconciliation table is honest and mostly accurate** — it correctly identifies that `create-task`'s `ownerAgentId=ctx.agentId` + parent-task-betId semantics are wrong for decomposition (the load-bearing trap the concept flagged), and the eligibility join is grounded in a real existing pattern (`handoff-protocol.ts`). The AC→verification table is concrete (named tests, injectable `runDecompositionTurn`/`runTurn` overrides for deterministic integration tests without LLM credentials), and protected-tests + route-checklist are populated — exactly the CC-003/CC-007/CC-008 recurrences this critique exists to catch, mostly pre-empted.

---

## Verdict
**NEEDS REVISION.** Score 6/10 with 3 CRITICALs. The plan's skeleton is sound and most of it is buildable as-is, but the two AH3-misattribution CRITICALs (Strategy port + session-less tool execution) mean the **core mechanism of how the PM turn runs and creates tasks is not yet specified against the real code** — the cited precedent does the opposite of what the plan needs for exactly those two steps. Plus the CAS crash-orphan hole is a latent C1/AC3 violation the plan must close. Resolve all three CRITICALs (and the cost-bypass WARNING, which is really a fourth correctness gap) before `/write-tests`.
