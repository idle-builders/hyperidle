## CRITICAL

- **[plan §Wiring decision / §File inventory→CI / Task 10] CI cannot boot the visual gate — `bun` is never installed in CI.** All three Playwright configs boot the viewer with `webServer.command: "bun run serve"` (verified: `playwright.config.ts:15`, `playwright.l1.config.ts:18`, `playwright.workbench.config.ts:24`). CI (`ci.yml`) runs `ubuntu-latest` with only `actions/setup-node@v4` + `npm ci` — **there is no `bun` on the runner**, and the plan's CI step adds only `playwright install --with-deps chromium`. The `webServer` boot would fail with `bun: command not found`, the gate would never run, and AC4 ("verify passes with NO skipped visual checks") would be silently vacuous in CI — the exact failure mode this workpackage exists to prevent. **Fix in plan:** either (a) add `oven-sh/setup-bun` to the CI job before `npm run ds:sync`, OR (b) change the `webServer.command` from `bun run serve` to `npm run -w @hyperidle/design-system serve` (vite is the runtime; bun is just the launcher) so no new CI toolchain is needed. Option (b) is the cleaner inversion — it also removes the last bun dependency from the gate. The plan must name this explicitly; today it is unaddressed in both the wiring section and Task 10.

- **[plan §Mechanism spec "Component set" / Task 2] Auto-deriving the component list from `discoverStories()` inside the Playwright test is not viable as written.** The plan states (twice) the builder should "derive the list from `discoverStories()` output rather than a hand-maintained array, so new stories are auto-covered." But `discoverStories(...globSources)` consumes `import.meta.glob` results — a **Vite-only** construct (verified `discovery.ts:99` + `main.tsx:21` glob calls). The Playwright spec runs in Node via `@playwright/test`, **not** through Vite — which is precisely why the current `visual-regression.test.ts` hardcodes the `COMPONENTS` array. Calling `discoverStories()` from the test will not enumerate anything. **The viable path exists but the plan misdescribes it:** the test must enumerate at *runtime* by navigating to the viewer catalog page (`:8098/#`) and reading the rendered component links from the DOM (the catalog renders one link per `StoryModule` and one `.demo-section` per variant — verified `main.tsx:176,244`), then visiting each `#<Component>` route. **Fix in plan:** replace "derive from `discoverStories()`" with "enumerate catalogued components by reading the live viewer catalog DOM at runtime (Playwright navigates the catalog, collects component routes), then screenshots each — no hand-maintained array, no Vite import." If the builder instead keeps a static array, the plan must say so and add a check that the array matches the catalog (otherwise AC2's "every catalogued component" silently drifts — the very gap the plan claims to close).

## WARNING

- **[plan §Wiring decision] "Add `ds:sync` to the `verify` chain" does not by itself reach CI — and the plan half-acknowledges this without reconciling it.** Verified: CI does **not** run `npm run verify`; it lists steps individually (check, lint, knip, mock-inventory, build×2, validate-attestation) and the attested path is `npm run test:all` (vitest only). So the gate reaches CI **only** via the separately-added CI step, not via the verify chain. The plan does add both, but its AC4 verification row conflates them ("`npm run verify` (now includes `ds:sync`) green" is the *local* proof; CI green is a *separate* path). State plainly: local AC4 = `verify` chain includes `ds:sync`; CI AC4 = the new explicit CI step. Also note the existing guards (`nimmly-guard`, `demo-fixture-guard`, `token-guard`) run in `verify` but **not** in CI — so the new `design-source-guard` (Task 9) will likewise be local-only. That is consistent with the existing pattern and fine, but the plan should say AC1's guard is local-only (like its siblings), not imply CI enforces it.

- **[plan §Central decision "Decision" line] The platform-determinism story is asserted, not proven, and the plan's own mitigation may force a choice between a red CI and a weakened gate.** The plan correctly flags Mac-blessed vs Linux-CI AA/font jitter as the highest risk and proposes platform-agnostic `snapshotPathTemplate` + 5% ratio. But the whole gate's value rests on the *unproven* assumption that one baseline set survives both platforms within 5%. If it doesn't, the plan's fallback ("capture baselines on CI/Linux and commit those") means baselines are Linux-rendered and a Mac developer's local `verify` would then drift against them — re-introducing the same cross-platform problem in the other direction. This is a genuine fork the plan leaves to "builder MUST validate," which is acceptable for an L workpackage, but the plan should commit to **one canonical capture platform** (recommend: CI/Linux is the blessing authority, since CI is the gate that blocks merge; local `verify` tolerates the 5% against Linux baselines) rather than leaving it ambiguous. Otherwise the builder may bless on Mac, pass locally, and discover red CI only at Task 12 — with no clean recovery short of re-blessing on Linux.

- **[plan §Mechanism spec / §protectedTests] The old gate covers interactive hover/focus states and DOM-marker presence on BOTH html and tsx; the plan only explicitly preserves marker-presence (TSX half) and is silent on the ~22 interactive-state tests.** Verified `visual-regression.test.ts:361-477` runs hover+focus pixel-diff for 11 `INTERACTIVE_COMPONENTS`. "Equivalent coverage to the retired gate" (the stated constraint and a key scrutiny point) requires deciding their fate. `toHaveScreenshot` can capture forced states too, but the plan never says whether interactive-state baselines are in or out. **Fix in plan:** explicitly state interactive hover/focus states are (a) re-captured as additional `toHaveScreenshot` baselines, or (b) dropped with a documented rationale. Silent omission = coverage regression masquerading as a 1:1 replacement.

- **[plan §File inventory MODIFY / Task 6] L1 spec rewrite uses `data-ds-shell` markers the plan never mentions.** The L1 spec (`thread-components.spec.ts:54`) asserts `[data-ds-component="..."], [data-ds-shell="..."]` because Tier-3 shells emit `data-ds-shell`, not `data-ds-component`. The plan's marker-presence task only mentions `data-ds-component`. `ThreadShell` is a shell. If the rewritten marker test checks only `data-ds-component`, it will false-fail on shells. Builder needs the dual-marker note carried forward.

## Verdict

**APPROVED WITH REQUIRED FIXES — overall 7/10, two CRITICALs must be resolved in the plan before the builder starts.**

The plan is structurally sound, the inversion is correctly understood, and the central decision is well-reasoned. But two wiring gaps would make the gate fail to run (bun-in-CI) or fail to enumerate (discoverStories-in-Node) — both would render AC2/AC4 vacuous, the precise outcome this workpackage forbids. Neither requires a redesign; both need a named fix in the plan text (CI bun setup or swap `webServer` to `npm run serve`; replace "derive from discoverStories()" with runtime catalog-DOM enumeration). The three WARNINGs (verify-vs-CI reconciliation, canonical capture platform, interactive-state coverage) should also be folded in to prevent a Task-12 surprise. Once the two CRITICALs are addressed in the plan, this is a clean go for `/write-tests`.
