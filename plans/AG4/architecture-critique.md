## Verdict
Ship the plan. The single most important architectural risk — Back collapsing into Up and re-breaking deep links — is correctly handled: the plan extracts the EXISTING `navigateToParent` (AppShell L191, `@lore AE4`, explicit parent paths, NOT `navigate(-1)`) into a pure `parentPathFor` and keeps Up structural. Deep-link safety, shortcut-collision mapping, and the canGoForward fallback are all reasoned, not hand-waved. Findings below are refinements, not blockers; three should be applied to the plan before `/write-tests` because they will otherwise surface as builder ambiguity.

### CRITICAL
- none

### WARNING
- **`parentPathFor` fallback contract is unspecified and silently changes behavior.** Plan §EXTRACT says `parentPathFor(pathname): string` is "lifted verbatim" from `navigateToParent`, and the task-1 test asserts "unknown→same". But the real `navigateToParent` fallback (AppShell L208) for an unmatched route is `navigate(-1)` — a **history** op, not a path. A pure `string`-returning function structurally **cannot** reproduce `navigate(-1)`; "unknown→same path" is a different behavior (no-op vs go-back). This is a Back-vs-Up boundary case: the fallback is the one place the old code mixes a history op into the parent resolver. → Plan must state explicitly what `parentPathFor` returns for an unmatched route (recommend: return the current pathname / a typed `null` so the caller no-ops, and DROP the `navigate(-1)` fallback — it was itself a latent deep-link smell). Then `navigateToParent` becomes `const parent = parentPathFor(p); if (parent && parent !== p) navigate(parent);`. Add the unmatched-route case to the task-1 unit test with the chosen contract, and add it to `protectedTests` reasoning so the AE4 mobile test still passes.
- **Text-input-guard source pointer is half-wrong.** Plan §NEW-hooks and §Required-reading say "copy guard from `useCommandK`/AppShell L445". `useCommandK.ts` has **no** text-input guard (verified — it fires ⌘K globally and only `preventDefault`s). The real, correct guard is AppShell **L446-447** (`tagName === input|textarea || isContentEditable`). A builder who clones `useCommandK` as instructed ships `useNavShortcuts` with no typing guard → violates the "must not fire while typing" constraint + AC-5. → Fix the pointer to AppShell L446-447 as the sole guard template; drop the `useCommandK` reference for the guard (keep it only as the document-keydown/preventDefault template).
- **7th breadcrumb site (`KnowledgeCreate`) breaks the "one breadcrumb owner" premise.** The route-checklist and §EDIT enumerate 6 consolidation sites. `KnowledgeCreate.tsx` L117 has its own hand-rolled `<nav aria-label="Breadcrumb">`. It is correctly excluded from the nav **cluster** (it's a create page, not a detail route — `isDetailRoute` `@lore AE4` excludes `/knowledge/new`), so Back/Forward must NOT appear there. But leaving its breadcrumb hand-rolled means the design's core justification ("one `Breadcrumb` DS component, kills divergence") ships with a known divergent 7th instance. → Either add KnowledgeCreate to task 6 as a breadcrumb-only migration (DS `Breadcrumb`, no `leading` cluster) and update the route-checklist with an explicit "create page: breadcrumb yes, cluster no" row, OR document it as a deliberate exclusion with rationale (like the Conversations exclusion). Silent omission is the wrong option — it's the exact coherence gap the consolidation exists to close.

### SUGGESTION
- **§Decision-2 canGoForward fallback is sound; tighten the verification.** `canGoForward = window.navigation?.canGoForward ?? false` with Forward-omitted-when-false is the right safe default (matches design's "omit phantom Forward"). The ⚠️ UNVERIFIED flag is honestly carried. Playwright runs Chromium, which exposes `window.navigation`, so AC-2's forward-traversal E2E **will** exercise the real path — but jsdom unit tests won't. → Add to task-2 test the explicit assertion that `canGoForward === false` when `window.navigation` is `undefined` (the fallback branch), so the safe degrade is itself covered, not just assumed. Already mostly implied by §Risks; make it an explicit test bullet.
- **Scope of the 6-page consolidation is justified, not creep.** The Breadcrumb DS component touching 6 pages reads like scope expansion against the "M budget" worry, but it is the minimum to satisfy AC-3 ("every detail screen shows hierarchy + 1-step up") + the design's anti-divergence goal. Every one of the 6 is an existing detail route in the route-checklist. No page is touched that an AC doesn't reach. This is correct — flagging only to record the budget question was considered and resolved in the plan's favor.
- **`window.history.state.idx` RR-internal coupling is well-mitigated.** Plan §Decision-2 + §Risks pin the behavior with a unit test asserting `idx` increments after a push, and capture the @lore. RR v7.14.1 confirmed in package.json. Good defensive instinct for an undocumented internal — no change needed.
- **AgentProfile team-aware up-target divergence is handled correctly.** Route-checklist notes AgentProfile's richer team-aware `to` is kept on the breadcrumb segment while `parentPathFor` stays the generic `agents→conversations` fallback for the mobile button. This is the right call (don't flatten the page's better data into the generic resolver) and it's documented, not hidden.

### What's Working Well
- **The load-bearing concept rule is architecturally enforced, not just restated.** Back = `navigate(-1)` (temporal, AppShell), Up = `parentPathFor` (structural, explicit paths). The plan keeps these in different modules with different source-of-truth (history vs pathname), exactly as concept.md §Phase-4 contracts demand. The `@lore AE4` regression the concept doc fears is structurally prevented by extracting the existing-and-correct resolver rather than rewriting it. This is the discipline this workpackage most needed.
- **AC → verification table is concrete and harness-aligned.** Each AC names the actual test type (E2E URL+affordance assertions, jsdom unit with stubbed `history.state`/`window.navigation`, component-per-page render). Failing-test-first ordering is real (task 1 test before refactor, etc.). `protectedTests` correctly freezes the AE4 mobile-drawer test against the `parentPathFor` refactor and the existing navigation.spec assertions — the two contracts most at risk from this change.
