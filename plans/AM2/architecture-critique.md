The plan's task 3 (multi-key fix) and AC3 diagnosis are correct. ✅
- **Descriptor type has no per-backend fields** (`harness-capability-descriptor.ts:76+`) — the no-per-backend-branch claim holds. ✅
- **New files don't exist yet** (`harness-session-probe.ts`, `harness-native-normalization.ts`, the AM2 fixtures) — consistent with this being a forward plan, not a post-hoc rationalization.

The plan does the thing iteration 1 failed to do: it names the three open evidence links explicitly, ties each to its AC + validation scenario, and mandates real execution with fixture capture. It is honest about what is unproven (opencode event schema → `unknown`) and where the boundary is fuzzy (SDK-vs-CLI auth mismatch). It is not a 9-10 because two real-proof links have a hole an implementer could slip a stub through, the OpenAI-model-availability risk is under-specified, and one named test's skip-gate is wrong for the very key the plan relies on.

### CRITICAL

- **[plan §AC-verification item 4 + Evidence-chain "builtin gateway readiness" + Risk(AC3)] The discovery integration test's gateway-key gate excludes the only key present on this machine, so the builtin path will SKIP unless explicitly fixed — and the plan does not name that fix.** `AM2-real-harness-discovery.integration.test.ts:18` computes `gatewayKeyConfigured = Boolean(process.env.ANTHROPIC_API_KEY ?? process.env.OPENROUTER_API_KEY)` — `OPENAI_API_KEY` is absent from this expression, and `:70` gates the only builtin assertion on it. Today that test SKIPS, and the AC5-discovery-half row asserts `result.builtin.state === "ready"`. The plan's task 3 fixes `probeBuiltinGateway`, but item 4's verification text says only "asserts builtin probe is `ready`/`unauthenticated` keyed to the configured-provider credential set" — it never says to update `gatewayKeyConfigured` to include `OPENAI_API_KEY`/`openai_compatible_api_key`. If the implementer fixes the probe but not the test gate, the builtin discovery assertion stays skipped on a machine that can prove it — the exact iteration-1 failure mode (a provable path left unexecuted). → **Fix:** add an explicit verification line to item 4 (and a row to the evidence chain): "`gatewayKeyConfigured` MUST include `OPENAI_API_KEY` (and any `openai_compatible_api_key` credential); on this machine the builtin discovery assertion executes and asserts `state === 'ready'` with the matched credential name — not skipped." State that an all-skipped builtin discovery on this machine is a review failure, mirroring the AC5 session-probe risk language.

- **[plan §AC-verification item 6 (AC3) + §Type signatures] AC3's real-call branch is mandated in prose but has no asserted lower bound that forces a real network round-trip, so a degraded/mocked `callLlm` could satisfy it.** The plan says "assert real normalized `token_usage` (input/output > 0), `cost_update`, and `completion` events, and a `SessionResult` with non-zero `cost`/`tokenUsage`." `input/output > 0` and `cost > 0` are good, but nothing pins the assertion to *real OpenAI output* — a builder under time pressure could point `baseUrl` at a local stub returning a canned usage block and pass every assertion. AC3 is the AC most prone to fake-proof (it already was in iteration 1's spirit). → **Fix:** require the test to assert at least one property only a real provider produces: the returned `completion.text` is non-empty AND not equal to the prompt, OR the response carries a real OpenAI `model`/`id` field echoed through `LlmResponse`, OR `cost` matches the published `gpt-4o-mini` rate within tolerance for the observed token counts. Add an explicit "no stub server / no fixture / no recorded cassette for AC3 — the call hits `https://api.openai.com` live" line to the verification, paralleling the AC5 "MUST execute here" language. Without a real-output discriminator, AC3's verification is presence-of-events, not proof-of-real-call.

### WARNING

- **[plan §Risk(AC3) + §AC-verification item 6] The `gpt-4o-mini` fallback-on-error path is described loosely enough to silently degrade into a skip that masks a broken gateway.** The risk says "on a non-permanent provider error … fall back to the model the key *can* call, or … skip with the exact provider error." That is reasonable, but "fall back to the model the key can call" is unbounded — the test could iterate models and, on a key that can call *nothing*, skip with a provider error that looks legitimate but actually means the whole `openai-compatible` path is broken. → **Fix:** bound the fallback to a closed, named list (e.g. `["gpt-4o-mini", "gpt-3.5-turbo"]`); on a 401/403 (auth) error, FAIL (the key is configured-but-invalid, a real bug), not skip; skip only on 404/model-not-available across the whole named list, with the model list and final error in the skip reason. Distinguish auth failure (fail) from model-availability (skip) explicitly.

- **[plan §AC-verification item 7 (AC6) + §Normalization direction] AC6's equivalence proof for the *builtin* leg is asserted but the builtin event never passes through `normalizeNativeHarnessEvent` — so "two harnesses, same action, same downstream shape" is only proven for Codex↔Claude, not Codex↔builtin.** §Normalization direction says "OpenAI-compatible chunk usage (builtin) already flows through `trackUsage` → union events; no pre-normalizer needed." That is true, but it means the builtin's `token_usage` is produced by a *different code path* than the Codex/Claude fixtures' `token_usage`. The AC6 test (item 7) names "the builtin AC3 event from #6" as one of the three inputs but only explicitly asserts Codex+Claude equivalence. If the builtin leg is the one the dial-in (AM3) renders most, leaving it out of the equivalence assertion weakens the central AC6 claim. → **Fix:** make item 7 assert the three-way equivalence explicitly: the `token_usage` emitted by the real builtin call (#6) and the `token_usage` produced by `normalizeNativeHarnessEvent("codex", codexFixture)` and `("claude-code", claudeFixture)` are structurally identical (same `type`, same field shape), indistinguishable to a downstream consumer. State which fields are compared (`type`, `prompt`/`completion` token keys) so the equivalence is concrete, not "toEqual on whatever shape happens to emerge."

- **[plan §AC-verification item 5 (AC5 session probe) + §Risks] The session probe asserts "a non-empty machine-readable event line is captured" but does not require the captured line to contain the usage/cost payload AC6 depends on — a probe could pass on a `thread.started` line and leave AC6's fixture useless.** Item 5 accepts `turn.completed` / `item.completed` / `thread.started` as valid captured types, "and, when present, a `usage` object." For Codex, only `turn.completed` carries the `usage` the AC6 normalizer maps to `token_usage`. If the probe captures and commits the *first* event line (`thread.started`), the AC6 fixture has no usage and the normalization equivalence cannot be proven from it — AC5 goes green while silently breaking AC6's input. The probe→fixture→normalize topology the plan is proud of has a gap at the probe's capture selector. → **Fix:** specify that the captured/committed fixture line MUST be the usage-bearing event (`turn.completed` for Codex with a `usage` object; `result` with `usage`/`total_cost_usd` for Claude). The probe may observe earlier lines but commits the usage-bearing one; if no usage-bearing line is emitted, the probe records that and AC6 marks that family `unknown` (same treatment as opencode) rather than committing a usage-free fixture.

- **[plan §Protected tests + §Migrations(additions)] The plan changes the assertion intent of `harness-event-normalization.test.ts` (correct) but does not enumerate which *other* suites assert the old "unknown" normalization behavior, risking a cross-suite break.** The plan says existing tests asserting `claude-code` presence won't change because the SDK adapter still registers it — good. But the normalizer is shared (`packages/shared`); any consumer test that relied on a real Codex/Claude line normalizing to `UnknownHarnessEvent` will now break. The plan asserts only the one test file changes. → **Fix:** add a one-line verification: "grep `UnknownHarnessEvent` across all `*.test.ts` and confirm no other suite asserts a *real* native line normalizes to unknown; if any does, list it in protected-tests with its required update." (CC-008.)

### SUGGESTION

- **[plan §"What is NOT deferred" + §Design-it-twice] The probe-vs-runtime-adapter boundary is stated three times (reconciliation table, design-it-twice, the ⭐ AC5 row).** The distinction is genuinely important (it's the iteration-1 misread), but the triple-statement reads defensively. Consolidate to one canonical statement in design-it-twice and reference it. Restraint, not repetition, signals the boundary is settled.

- **[plan §Evidence chain row "opencode launchable (session)"] "session-probe test (or skip w/ reason)"** — be explicit on the expected outcome on *this* machine. The dossier says opencode is installed + has an OpenRouter cred, so the probe should EXECUTE here (capturing or marking the schema `unknown`), not skip. As written, "or skip w/ reason" invites a skip on a machine that can run it — the same soft-skip risk as the builtin gate. State: opencode probe executes here; only its event-schema *normalization* may end `unknown`, not its launch proof.

- **[plan §Type signatures `normalizeNativeHarnessEvent`] The signature takes `family: "codex" | "claude-code" | "opencode" | "builtin"` but the body comment says builtin needs no pre-normalizer.** Passing `"builtin"` to a function that no-ops on it is a dead branch. Either drop `"builtin"` from the union (builtin events are already union-shaped and skip this function) or document the no-op return explicitly. Minor type-honesty point.

Keep this pattern for all future harness work.

The plan prefers `unknown` over a guessed `ready` — the concept's core contract, honored.

## New finding (Round 2)

### WARNING

- **[plan §AC-verification item 6 (AC3) + Evidence-chain "real provider call" row] Two of CRITICAL-2's three offered discriminators are non-viable against the real `LlmResponse`/cost code; only option 1 survives, so the fix rests on a single un-flagged option.** (1) **Option 2 — "echoed OpenAI `model`/`id` through `LlmResponse`" is unreachable.** `parseOpenAiResponse` (`llm-client.ts:329-336`) returns only `{ stopReason, content, usage }`, and `LlmResponse` (`llm-types.ts:38-47`) has no `id`/`model` field — both `body.id` (`chatcmpl-…`) and `body.model` are discarded at the parse boundary. A test asserting an echoed model/id cannot compile against the real type. (2) **Option 3 — "`cost` within 5% of published `gpt-4o-mini` rate" is false against real behavior.** `BuiltinHarnessAdapter.estimateCostUsd` (`builtin-harness-adapter.ts:110-112`) looks up `COST_PER_MILLION_TOKENS` (`:85-94`), which contains only `claude-*` models and falls back to `DEFAULT_COST = { input: 3, output: 15 }` for `gpt-4o-mini`. The adapter therefore bills a gpt-4o-mini call at the Claude default rate ($3/$15 per M), NOT OpenAI's published gpt-4o-mini rate ($0.15/$0.60 per M); asserting `cost` within 5% of the *published OpenAI* rate would FAIL. The plan hedges "picking whichever is reachable through `LlmResponse`," which technically protects the build — but it presents three co-equal options when two are dead, inviting a builder to spend time on a branch that cannot pass. → **Fix:** in item 6 and the evidence-chain row, mark option 1 (`completion.text` non-empty AND ≠ prompt) as the **primary required** discriminator (it is the only one reachable through the current `LlmResponse`), and either (a) drop options 2 and 3, or (b) re-scope option 3 to "`cost` > 0 AND consistent with the adapter's own `COST_PER_MILLION_TOKENS` lookup for the billed model" (an internal-consistency check, not a published-OpenAI-rate check) and drop option 2 entirely until `LlmResponse` carries the provider `model`/`id`. This does not block AC3 — option 1 alone forces the live round-trip — but the plan must not list non-viable proofs as if equivalent.

### SUGGESTION

- **[plan §AC-verification item 6 + §Normalization direction] The `cost_update` event field is `totalCost`/`deltaCost`, not `cost`.** Item 6 says "a `SessionResult` with non-zero `cost`/`tokenUsage`" and the evidence-chain references `cost`. The emitted `cost_update` event (`builtin-harness-adapter.ts:905-910`) carries `totalCost`/`deltaCost`/`currency`; `SessionResult.cost` may be a separate aggregate. Name the exact field the assertion reads (`cost_update.totalCost > 0`, or `SessionResult.cost > 0` if that field exists) so the builder doesn't assert on a non-existent `cost` key. Minor field-name precision, not a correctness gap.
