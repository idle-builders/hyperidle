# L3 — Artifact Primitive — Architecture Plan

**Story.** `docs/work-packages/TRACK-L.md` L3.
**Concept.** `docs/concept/HUMAN_INTERFACE_LAYER.md` §4.5.
**Approved design.** `docs/design-explorations/L3/approved.md`.
**Shared contract.** `docs/work-packages/the canonical-shapes contracts under docs/` "Artifact primitive (L3)".

---

## 1. Goal

Ship the Artifact primitive end-to-end: a Drizzle-backed table with one canonical fetch shape; four Hono read endpoints (one per filter axis: task / bet / product / portfolio); a closed view family of four design-system layout components plus four reusable sub-primitives wired against the shape; and the agent-runtime entry path (a single `createArtifact` service used by Task-handoff and the agent harness). Lock the view family closure with both an export boundary and a focused eslint rule, denormalise hot-path joins onto the fetch response, and publish a forward-compatible cost shape that L4 will adopt.

## 3. Type signatures

All types live in `packages/shared/src/types/artifact.ts`. Re-exported from the shared barrel.

### 3.1 Closed `kind` enum (12 + catch-all)

Approved-design §6 lists 12 canonical kinds. We close them as a TS literal union with one explicit catch-all token. The catch-all token is named `unknown_kind` (not `other`, which would collide with the colloquial use) and is the value the renderer dispatches on when the database carries a kind string the current codebase does not recognise.

```ts
export const ARTIFACT_KINDS = [
  "code_diff",
  "deck",
  "contract",
  "dashboard",
  "screenshot",
  "drafted_email",
  "design",
  "data_analysis",
  "decision",
  "running_service",
  "comm_draft",
  "verification",
  "unknown_kind",
] as const;

export type ArtifactKind = (typeof ARTIFACT_KINDS)[number];
```

The DB `kind` column stores the literal string. The fetch route normalises any unrecognised value to `unknown_kind` before responding (see §6.5 — the DB column is intentionally `text` to allow forward-compat ingest, but the wire shape is closed).

### 3.2 `ArtifactPreview` discriminated union

Closed at the same 12 kinds. Each variant carries the minimum the renderer needs for both gallery and single_full_preview.

```ts
export type ArtifactPreview =
  | { kind: "code_diff"; file: string; hunks: ReadonlyArray<DiffHunk> }
  | { kind: "deck"; slideCount: number; firstSlideTitle: string }
  | { kind: "contract"; parties: ReadonlyArray<string>; title: string }
  | { kind: "dashboard"; metrics: ReadonlyArray<{ label: string; value: string }> }
  | { kind: "screenshot"; imageUrl: string; width: number; height: number }
  | { kind: "drafted_email"; to: ReadonlyArray<string>; subject: string; bodyExcerpt: string }
  | { kind: "design"; imageUrl: string; width: number; height: number }
  | { kind: "data_analysis"; findings: ReadonlyArray<string> }
  | { kind: "decision"; claim: string; rationale: string }
  | { kind: "running_service"; url: string; status: "ok" | "degraded" | "down"; statusLabel: string }
  | { kind: "comm_draft"; channel: string; firstMessage: string }
  | { kind: "verification"; suite: string; passed: number; failed: number };

export interface DiffHunk {
  readonly header: string;
  readonly lines: ReadonlyArray<{ kind: "add" | "del" | "ctx"; text: string }>;
}
```

Note `unknown_kind` carries no `preview` payload — when the DB row's kind is normalised to `unknown_kind`, `preview` is forced to `null` on the wire so the renderer hits the catch-all path. This avoids a fourteenth variant and keeps `ArtifactPreview['kind']` as a strict subset of the recognised kinds.

The discriminant **must** match the row's `kind` exactly. Server validation rejects responses where `data.kind !== preview.kind`.

### 3.3 Cost shape (forward-compat with L4)

L4 has not shipped. Per approved-design §8 Q6, we ship a display proxy now and pre-publish the shape into the canonical-shapes contracts under docs/ so L4 can adopt without a re-migration.

```ts
export interface ArtifactCostFromSession {
  /** Money rendered as a pre-formatted display string (e.g. "$0.42") for L3.
   *  When L4 lands, this becomes `Money` (currency-aware, precision-safe). */
  readonly money: string | null;
  /** Token total rendered as a pre-formatted display string (e.g. "12.4k").
   *  When L4 lands, this becomes `TokenUsage` (prompt + completion split, model-tier signal). */
  readonly tokens: string | null;
}
```

The forward-migration path: when L4 publishes `Money` and `TokenUsage`, `ArtifactCostFromSession.money` becomes `Money | null` and `ArtifactCostFromSession.tokens` becomes `TokenUsage | null`. The DS components consume only formatted strings via `ArtifactCostChip`, which absorbs the L4 transition behind a private formatter — call sites do not change. the canonical-shapes contracts under docs/ gets a "Cost shape (L3 publishes / L4 adopts)" note as part of this story.

**Formatter contract.** The DB stores three precision-safe integers (`cost_money_micros`, `cost_tokens_input`, `cost_tokens_output`). The wire shape collapses these to two pre-formatted display strings via `formatArtifactCost(row): ArtifactCostFromSession` in `packages/server/src/services/format-artifact-cost.ts`. Rule: `money` is `null` iff `cost_money_micros IS NULL`; `tokens` is `null` iff BOTH token columns are NULL; otherwise `tokens` is the sum (input + output) rendered in the L3 short form (e.g. `"12.4k"`, `"248"`). When L4 ships, the formatter is replaced by L4's `Money`/`TokenUsage` constructors; the wire field names do not change, only their carried types. This is the only place the input/output token split is collapsed for L3 — when L4 lands, the split surfaces on the wire automatically through `TokenUsage`.

## 4. Database schema (Drizzle, dual-driver)

### 4.1 New table: `artifacts`

`packages/db/src/schema.ts` (SQLite) and `packages/db/src/schema.pg.ts` (PostgreSQL) — kept structurally identical per existing dual-driver pattern.

| Column | Type (SQLite) | Type (PostgreSQL) | Constraints | Rationale |
|---|---|---|---|---|
| `id` | `text` | `text` | PK | UUID v7 string, opaque (concept §4.5 hard rule: not derived from content) |
| `producing_task_id` | `text` | `text` | FK → `tasks.id` `ON DELETE RESTRICT`, NOT NULL | Hard rule #1: artifacts root on tasks |
| `kind` | `text` | `text` | NOT NULL | Stored as-is; normalised to closed enum at the API boundary |
| `preview_json` | `text` | `jsonb` | NULL allowed | The `ArtifactPreview` discriminated union, JSON-serialised. Null until rendered. |
| `cost_money_micros` | `integer` | `bigint` | NULL allowed | Money in micros (1/1,000,000 USD) — same precision pattern Linear/Stripe use; absorbs L4 `Money` cleanly |
| `cost_tokens_input` | `integer` | `bigint` | NULL allowed | Prompt-token total summed across the producing session(s); null until session settles |
| `cost_tokens_output` | `integer` | `bigint` | NULL allowed | Completion-token total |
| `cost_settled_at` | `text` | `timestamptz` | NULL allowed | Set when cost transitions from null → populated; immutability guard hooks off this |
| `created_at` | `text` | `timestamptz` | NOT NULL | ISO 8601 string in SQLite, `timestamptz` in PG |

Indexes:
- `artifacts_producing_task_id_idx` on `producing_task_id` — primary fetch axis
- `artifacts_created_at_idx` on `created_at DESC` — pagination cursor
- (PG only) GIN index on `preview_json` deferred to a follow-up story (no current query targets the JSON body)

@lore comments on the file: "L3 — kind is stored as text but normalised to ARTIFACT_KINDS at the API boundary (forward-compat for new ingest tokens)" and "L3 — cost columns are null-until-settled per concept §4.5 mutability rule; immutability is enforced in the createArtifact / settleCost services, NOT by a DB trigger".

### 4.2 No join tables added

Aggregation by bet / product / portfolio is computed at query time via `JOIN tasks ON tasks.id = artifacts.producing_task_id` and an additional join up to `bets` / `products`. No materialised aggregation table — the read shape and the cardinality (artifacts per bet typically O(10–100)) do not justify it. If perf hot spots emerge, materialise in a follow-up story.

### 4.3 Threads ↔ artifacts join

L1 has not shipped the `attached_host_type / attached_host_id` columns yet. This plan does NOT add them to threads. Instead, the L3 fetch route returns `thread_count: 0` until L1 lands the join, then adopts the L1 contract:

```ts
// L1 publishes (forward expectation):
//   threads(id, attached_host_type IN ('bet','task','knowledge_item','artifact','agent','user'),
//           attached_host_id, ...)
//
// L3 SELECT for thread_count (forward shape):
//   SELECT COUNT(*) FROM threads
//     WHERE attached_host_type = 'artifact' AND attached_host_id = artifacts.id
```

Captured as a `// @lore L3 / L1 forward-compat` block in `packages/server/src/routes/artifacts.ts`.

### 4.4 Migration

`packages/db/drizzle/0007_add_artifacts.sql` and `packages/db/drizzle-pg/0006_add_artifacts.sql` (numbers picked at generate time). Forward-only. The existing `tasks.artifacts` text column is left alone — it carries handoff filenames per `handoff-to.ts:18`, a different concept. ## 5. Server routes (Hono)

`packages/server/src/routes/artifacts.ts`. Mounted at `/api/artifacts` from `app.ts`. Auth via the existing `authMiddleware` (catch-all on `/api`); no per-route auth re-binding.

### 5.1 Endpoints

All four use one Hono router. The router is a single endpoint with a typed query param for axis (see §11 — design-it-twice picked the discriminated-axis pattern).

| Method | Path | Query / params | Body | Response | Auth | Cache |
|---|---|---|---|---|---|---|
| GET | `/api/artifacts` | `axis=task\|bet\|product\|portfolio`, `taskId`/`betId`/`productId` (axis-conditional), `limit`, `cursor` | none | `ArtifactPage` | required (catch-all) | `Cache-Control: private, max-age=15` |
| GET | `/api/artifacts/:id` | `id` | none | `Artifact \| 404` | required | `private, max-age=15` |
| POST | `/api/artifacts` | none | `CreateArtifactInput` | `Artifact` (201) | required + role≥agent | none |
| PATCH | `/api/artifacts/:id/preview` | `id` | `{ preview: ArtifactPreview }` | `Artifact` | required + role≥agent | none |
| PATCH | `/api/artifacts/:id/cost` | `id` | `{ money_micros, tokens_input, tokens_output }` | `Artifact` | required + role≥agent | none |

Notes:
- Two PATCH endpoints exist because of the concept §4.5 mutability rule: `preview` and `cost_from_session` each transition exactly once from null → populated. Two endpoints make the contract explicit and let the immutability guard live in two small handlers.
- POST + PATCH live here even though the agent-runtime is the primary writer (via the `createArtifact` service, §7) — the route exists for tests and any future human-driven backfill.
- DELETE is intentionally NOT exposed. Per concept §4.5 lifecycle: "An Artifact is **not deleted** at this layer."

## 8. Security & abuse cases (STRIDE)

| Threat | Vector | Mitigation |
|---|---|---|
| **Spoofing** | Caller posts `producingTaskId` for a task they do not own | `createArtifact` service joins `tasks` and asserts the auth principal can write to that task (uses the existing task-write check from `tasks.ts`). Missing in: POST /api/artifacts route — added in §5.4 |
| **Tampering** | Filter `taskId` is a path-traversal-ish string | Zod `min(1)` + parameterised query (Drizzle eq); no string interpolation |
| **Repudiation** | Who created which artifact? | `createdBy` audit captured by the existing event-bus emit; `artifact_created` event payload carries the requesting agent id from auth context |
| **Info disclosure** | Cross-tenant artifact id guessing | Fetch route applies the existing tenant-scope filter (joins tasks → bets → products → tenant). 404 (not 403) on cross-tenant lookups so existence does not leak |
| **DoS** | Oversized `preview_json` (e.g. 10MB diff) | Body-limit middleware capped at 64KB for POST/PATCH `preview` endpoints; request rejected as 413. The agent runtime is responsible for truncating diffs before submission |
| **DoS** | Pagination flooding | `limit` default 50, hard cap 200; rate-limiter (`packages/server/src/middleware/rate-limit.ts`) covers `/api/artifacts` per existing default rate (60 req/min/principal) |
| **Elevation** | Viewer-role principal POSTs an artifact | Auth middleware enforces role ≥ agent on POST/PATCH; viewer-role can only GET. The role hierarchy lives in `packages/server/src/middleware/auth.ts` (read-only verification by reading the existing role checks) |
| **Tampering (immutability)** | PATCH overwrites populated `preview` | `settleArtifactPreview` returns 409 IMMUTABLE if `preview_json IS NOT NULL` at update time; a SELECT-then-UPDATE-with-WHERE-NULL pattern makes this race-safe (rows updated = 0 → 409) |

Open security items punted to a follow-up:
- **L3-FU-2: Per-tenant pagination cursor encoding.** The cursor is opaque JSON now; signing it with a tenant-scoped HMAC is a hardening step, not in scope for L3.

## 9. Closed view family enforcement

Layered defence per CC-008. Three layers, smallest first.

### Layer 1 — export boundary (cheapest, always on)

`packages/design-system/src/index.ts` enumerates exactly the 8 names. No `export * from "./Artifact*"`. A protected test (`packages/design-system/src/__tests__/closed-view-family.test.ts`) reads the source of `index.ts`, parses the AST, and asserts:
- The exported names matching `^Artifact` are exactly the eight in the allow-list.
- No additional `Artifact*` `.tsx` files exist in `packages/design-system/src/` outside the allow-list.

This catches the most common path: a future agent adds `ArtifactCard.tsx` and exports it.

### Layer 2 — eslint rule `closed-view-family`

`packages/eslint-plugin-design/src/rules/closed-view-family.ts` — fires on any `.tsx` file whose path matches `packages/design-system/src/Artifact*.tsx` and whose basename is not in the allow-list. Catches the case where someone adds the file but forgets to update the export boundary. Rule is enabled in the design-system package's `.eslintrc.js`.

### Layer 3 — concept-doc anchor (documentation, not enforcement)

Not a defence layer in the runtime/CI sense — purely a pointer. The eslint rule message text includes the path `docs/concept/HUMAN_INTERFACE_LAYER.md` §4.5 hard rule #2, so any future agent who hits the lint failure is led directly to the concept doc. Adding a fifth layout therefore takes three edits in one PR (concept doc + index allow-list + eslint allow-list); the lint failure text orchestrates the order.

**No runtime guard.** A runtime check on `import` order would fire too late and isn't typescript-detectable. The two static checks above (export-boundary test + eslint rule) are the actual enforcement; the concept-doc anchor is the breadcrumb that guides any deliberate fifth-layout addition through the right gate.

## 10. Resolved open questions (the 10 from approved.md §8)

### Q1 — `preview` discriminated-union closure
**Resolved.** Closed at the 12 recognised kinds (see §3.2). `unknown_kind` carries no preview variant — `preview` is forced to `null` on the wire when normalised. No 14th variant.

### Q2 — `kind` enum closure
**Resolved.** Closed TS literal union at the API boundary (`ArtifactKind` literal union, 12 + `unknown_kind`). DB column remains free-form `text` to absorb forward-compat ingest tokens; the API normalises unrecognised values to `unknown_kind` so the renderer always has a valid discriminant. This is the "closed at the wire, lenient at the column" pattern. Concept §4.5 hard rule #2 (closed view family) is unaffected — that's about layouts; this is about kind tokens.

### Q3 — `producing_task_title` denormalisation
**Resolved.** Denormalised onto the fetch response. The fetch route joins `tasks` and selects `tasks.title AS producing_task_title`. Reasoning: every consumer of the gallery card / stack item / single_full_preview / embed needs the title; the alternative (a per-row task fetch) creates an N+1 on the gallery surface. Cost: `producing_task_title` is point-in-time at fetch (a task title rename is reflected on next read). This is acceptable — task title renames are rare and a stale title in a card is a soft failure.

### Q4 — `getArtifactViewProps(artifact)` helper location
**Resolved.** Lives in `packages/shared/src/types/artifact.ts` alongside the Artifact types. Reason: the mapping (`{ kind: "code_diff", preview } → { shape: "text_diff", data: ... }`) is a pure function of the type; no React, no DOM, no DS dependencies. Locating it in shared lets both `ArtifactEmbed` and `ArtifactPreviewSurface` consume it identically. The 5 ArtifactView shapes are imported from `packages/web/src/shell/ArtifactView.tsx` via type-only imports (no runtime dependency from shared on web — only the type names).

⚠️ UNVERIFIED: Cross-package type-only import from `shared` to `web` would invert the dependency direction. Mitigation: lift the 5 ArtifactView shape **types** down to `packages/shared/src/types/artifact-view.ts` as part of step 1 (extract from `web/src/shell/ArtifactView.tsx`); the runtime component continues to live in `web`. This makes `getArtifactViewProps` a pure shared helper with no upstream deps. Verified pattern: existing `packages/shared/src/types.ts` re-exports DB-derived types via type-only imports — same shape.

### Q5 — `thread_count` denormalisation
**Resolved.** Denormalised on aggregation responses. The fetch route runs a `LEFT JOIN (SELECT attached_host_id, COUNT(*) AS thread_count FROM threads WHERE attached_host_type='artifact' GROUP BY attached_host_id) t ON t.attached_host_id = artifacts.id` once per page (200 rows max → cheap). Until L1 publishes the `attached_host_*` columns, the COUNT subquery is replaced with a constant `0` and a `// @lore L1 forward-compat` block. Avoids per-row lookups on hot gallery surfaces.

### Q6 — `cost_from_session` shape (L4 forward-compat)
**Resolved.** L4 has not shipped. L3 publishes `ArtifactCostFromSession = { money: string | null; tokens: string | null }` (display-string proxy). DB stores precision-safe integers (`cost_money_micros`, `cost_tokens_input`, `cost_tokens_output`). Server formats to display strings on read (private formatter in `packages/server/src/services/format-artifact-cost.ts`). When L4 lands, the `Money` and `TokenUsage` types replace the strings on the wire; DB columns and DS components are unchanged because the formatter absorbs the change. the canonical-shapes contracts under docs/ gets a "Cost shape (L3 publishes / L4 adopts)" paragraph as part of step 20 so L4 picks it up without re-deriving.

### Q7 — `state` prop derivation
**Resolved.** Explicit prop on every layout, default `"populated"`. Reasoning: makes loading / error / no-preview testable as discrete fixtures (Storybook story per state), keeps the components dumb (no inference logic), and lets the consumer (which knows whether a fetch is in flight) drive the state. Derived `state` would require every layout to encode "is this fetch loading?" and "did the parent error?" — that knowledge belongs to the consumer.

### Q8 — Storybook build order
**Resolved.** Tier 1 first (4 sub-primitives × 4 states minimum = 16 stories), then Tier 2 (4 layouts × 4 states = 16 stories). Total 32 stories minimum; the `cost-pending` state ships as a Storybook arg toggle on the populated story, not a fifth story per component (so 32, not 40). Build order: KindBadge → CostChip → Timestamp → PreviewSurface → GalleryCard → StackItem → Preview → Embed. Per the existing `require-stories-sibling` eslint rule, every component file ships its `.stories.tsx` sibling.

### Q9 — `design/no-embed-chrome` lint rule
**Resolved.** In scope. Rule `packages/eslint-plugin-design/src/rules/no-embed-chrome.ts` rejects `bg-`, `border-`, `rounded-`, `shadow-` Tailwind class fragments on the JSX root of any component named `ArtifactEmbed` (file-name-keyed; a renamed component is detected by the closed-view-family rule). Implementation pattern follows the existing `no-raw-tailwind-color` rule — string-fragment regex over the `className` JSX attribute. Feasibility verified: the existing rules already inspect `className` strings.

### Q10 — Aggregation contract sort + pagination
**Resolved.** Sole sort is `created_at DESC`. Cursor is opaque (`base64(createdAt + '|' + id)`). Default `limit` is 50, hard cap 200. No filter beyond the four axes for L3; `kind` filter is a follow-up (L3-FU-3).

## 11. Design-it-twice on non-trivial sub-decisions

### 11.1 `kind` enum: closed literal union vs open registry with versioning

**Option A — Closed TS literal union, normalised at API boundary** (chosen). 12 named kinds + `unknown_kind` catch-all. DB stores raw string; API normalises unrecognised → `unknown_kind`. Adding a 13th kind = TS code change + concept-doc update.

**Option B — Open registry with version field.** Each kind ships a `{ id: string, version: number, renderer: ... }` registry entry. New kinds added by registering, no TS literal closure. More flexible.

**Costs.**
- **A:** type-safe everywhere; renderers exhaustive-checked by tsc; new kind = code PR. Concept-aligned (§4.5 commits to function-agnosticism, but the architect is asked to close the enum).
- **B:** dynamic; lookup table at runtime; no exhaustive type check; renderer fallback path always live; harder to reason about inside `ArtifactPreview` discriminated union (would force `unknown` payload type).

**Pick: A.** The concept doc commits to function-agnosticism (the *primitive* doesn't care about kind), not to the enum being open. The renderer engine ships with the closed list because the design (§6 of approved.md) prescribes per-kind renderers. An open registry buys flexibility we are not paying for and loses exhaustive-switch type safety. New kinds land via a follow-up story per concept §4.5 ("any future output kind") — a code PR is the right gate.

### 11.2 Fetch contract: 1 endpoint with discriminated `axis` body vs 4 sibling endpoints

**Option A — 1 endpoint, axis discriminant in query** (chosen). `GET /api/artifacts?axis=task&taskId=...` etc. One Hono handler, one Zod discriminated-union schema, one consumer hook (`useArtifacts({ axis, ... })`).

**Option B — 4 sibling endpoints.** `GET /api/artifacts/by-task/:taskId`, `/by-bet/:betId`, `/by-product/:productId`, `/by-portfolio`. Each handler is small and obvious.

**Costs.**
- **A:** consolidated query path; one cache key shape; one rate-limit bucket per principal; client hook is a single `useArtifacts` with a discriminant. Discoverability slightly worse (developers grep for the URL); error messaging requires care (axis-specific 400s).
- **B:** maximally REST-y; each route is grep-discoverable; route-checklist (§5.4) has 4 rows trivially. Duplication of join logic across handlers; 4 cache shapes; client needs 4 hooks or one wrapper. More surface area for the security-review.

**Pick: A.** Hono's discriminated-union zod validators (`z.discriminatedUnion`) are first-class and well-trodden. The 4 axes share 100% of the query plan except the WHERE clause; replicating handlers triples the test surface. Verified: the existing `tasks.ts` route uses Zod discriminated unions in the handoff schema (`schema-l-3` adversarial pattern is known good).

⚠️ Cite: Hono v4 documents the validator pattern at https://hono.dev/docs/guides/validation — verified during planning.

## 19. Deferred to follow-ups (post-review)

The following findings from the L3 reviews (architecture / adversary / security / design)
are intentionally deferred. Each entry names the finding, the rationale for not fixing in
L3, and the trigger that picks it up later.

### L3-FU-7 — Multi-tenancy / cross-tenant scoping

- **Source:** security-review HIGH-1 area; adversary M-cross-tenant.
- **Rationale:** No `tenant_id` column exists anywhere in the repo today.
  Authentication is a single shared API key (`HYPERIDLE_API_KEY`). Adding
  multi-tenant scoping in L3 alone would introduce a load-bearing concept
  with no producer, no enforcement surface elsewhere, and no test population.
- **Picked up by:** the future story that introduces `tenant_id` system-wide
  (likely a multi-tenant track yet to be planned). When that story lands, the
  artifact routes must add `tenant_id` filtering everywhere (`get`, `getById`,
  `post`, `patch /preview`, `patch /cost`).

### L3-FU-8 — Role-based access control

- **Source:** security-review (writer endpoints accept any authenticated caller).
- **Rationale:** No role concept exists today. There is no `requireRole("agent")`
  middleware, no role column on the API key, no role assignment surface.
- **Picked up by:** the authn/authz story that introduces roles. At that point
  POST `/api/artifacts` and the two PATCH endpoints should require `agent`.

### L3-FU-9 — ESLint rules `closed-view-family` + `no-embed-chrome`

- **Source:** architecture-review M-lint; AC-3, AC-12.
- **Rationale:** The export-boundary vitest at `packages/design-system/src/__tests__/closed-view-family.test.ts` already enforces the eight-export rule programmatically. The chrome-less embed assertion lives in the protected test at `packages/design-system/src/__tests__/ArtifactEmbed.test.tsx:47-58` (DOM-absence check). ESLint rules are belt-and-suspenders; the existing tests are the load-bearing guard.
- **Picked up by:** a focused `eslint-plugin-design` story (K6 follow-up).

### L3-FU-10 — Service layer `createArtifact` / `settleArtifactPreview` / `settleArtifactCost`

- **Source:** architecture-review M-service-layer.
- **Rationale:** The route handlers contain the logic inline. A premature
  service-layer extraction commits to a shape before the actual downstream
  consumers (L11 review messages, L12 work surfaces, agent harness) reveal
  what they need. Per CLAUDE.md "Search Before Building".
- **Picked up by:** the first downstream consumer that needs to invoke the
  same logic outside the HTTP route.

### L3-FU-11 — Event-bus emissions on artifact lifecycle

- **Source:** architecture-review M-events.
- **Rationale:** The harness / Task-handoff is not yet wired to consume
  artifact events. Emitting events with no consumer creates a contract that
  the first consumer must then conform to rather than shape. Notifications,
  observability, and WebSocket push each have different shape needs.
- **Picked up by:** the first consumer (likely the notification queue
  integration or the agent harness final wire-up).

### L3-FU-12 — Storybook `cost-pending` arg-toggle

- **Source:** design-review m-stories ergonomics.
- **Rationale:** The `cost-pending` state is currently rendered as a separate
  named story export. Converting it to a Storybook arg toggle is an ergonomics
  tweak with no behavioural effect and no acceptance criterion.
- **Picked up by:** any future Storybook polish pass.
