### WARNING

- **[plan §Q3 / Hole 1 (WS) / R4] The `session:<id>` host-scope resolution is under-specified and the current authorizer returns `true` unconditionally.** Today `canSubscribe` (`ws-broadcaster.ts:226`) returns `sessionId.length > 0` — no session→task→host lookup at all. The plan says it will "resolve the session→task host and apply host-scope" (Q3, task 8), and R4 acknowledges the added DB lookup. But host-scope `canRead` returns `true` for any authenticated principal anyway (the `HOST_SCOPE` map makes `task` → `host` → `true`). So resolving session→task→host and then applying host-scope yields **exactly the same result as today** (`true` for any authenticated principal) at the cost of a new DB round-trip and a new failure mode (session not found → deny). The plan does not justify *why* the round-trip earns its keep: the only behavioral change is that a `session:` topic for a **non-existent** session now returns `forbidden` instead of `ok`. That is defensible (Hard Rule 1 read-parity: route it through the chokepoint rather than bypass), but the plan should state explicitly that the *observable* authz outcome is unchanged for valid sessions and the value is purely "no accidental bypass + closes the non-existent-session case," so `/write-code` does not over-build a participant filter the model doesn't ask for. Also specify the deny behavior when the session row is missing or its task host can't be resolved (deny vs. allow), since that is a new error path not in the failure-mode table.

- **[plan §The chokepoint / Hole 2] The `participants` membership check for participant-scope is a plain string-array `includes` — confirm it matches the list-endpoint AD1 semantics exactly, including the assistant-thread agent-id case.** `canRead` does `(participants ?? []).includes(principal)`. The list AD1 guard (`threads.ts:448`) compares `q.participant_id` to `c.get("userId")`, and `rowToThread` parses `participants` via `threadParticipantsSchema`. For the assistant soul route the principal is the *user*, and the assistant thread participants are `[userId, "ast-{userId}"]` — so the user is a participant and passes. Fine. But the plan's Hole 1 says participant-scope threads are "`user`/`agent` host (i.e. assistant/DM threads)" and a non-participant gets 403 "parity with the list AD1 guard." The list guard returns 403 when `participant_id !== userId` — it does *not* actually check `userId ∈ participants`, it checks the *query param* matches the principal. These are different predicates. The detail check (`userId ∈ participants`) is the *correct* one and is stricter, but the plan claims "parity" — they are not the same predicate. **Fix:** state that detail enforcement is `principal ∈ participants` (the correct read-parity check), and that this is *stronger* than the list's query-param guard, not identical to it — so the AC1 test asserts the right thing (a principal who is genuinely not in `participants` gets 403, not merely a mismatched query param).

- **[plan §Three custom ESLint rules / R5] `no-header-identity-in-authz` precision vs. the legitimate attribution paths is asserted but the discriminating heuristic is hand-wavy.** The valid cases the rule must NOT flag are real and adjacent to the invalid ones: `threads.ts` `readSenderId` (header → `senderId` insert, attribution), `readInitialSenderId`, and `/ws-token` mint feeding `store.issue`. The invalid case is `assistant.ts` `readSenderId` feeding the `authenticatedUserId !== targetUserId` comparison. Both start with `c.req.header("X-Identity")`. The plan's heuristic — "a `header(...)` result used in a `BinaryExpression` whose other side is a path param, or passed as `principal` arg" — is reasonable but AST-fragile: after Hole 2, `assistant.ts` won't call `header(...)` for authz at all (it'll use `c.get("userId")`), so the rule's *job* is to prevent *regression*. The plan should state the rule's true target is **future** code (a new route wiring a header into authz), make the RuleTester invalid fixture model that future shape directly, and confirm the rule does not depend on the soon-deleted `readSenderId` existing. As written, R5's mitigation ("fixture covers the valid case") is necessary but the plan doesn't commit to a *closed* set of authz-sink function names (`canRead/canWrite/authorizeRead/authorizeWrite`) the rule keys on — without that closed list the heuristic will either over- or under-fire. **Fix:** enumerate the exact sink-function allowlist the rule treats as "authz comparison" and base detection on a call flowing into one of those, not on generic `BinaryExpression` shape.

- **[plan §R1 / §Boundary declaration mechanism] The "best-effort in prod" runtime deny IS a real residual gap, correctly flagged but worth sharpening the closure argument.** The probe in the task brief is valid: once a handler has produced a body, the global assertion can only log — it cannot retroactively fail closed. So for a *new, undeclared* data route shipped to prod, the global default is effectively **open** at runtime until someone reads the log. The plan's answer is "lint is the real gate; runtime is a dev safety net" — and that matches the locked model (§60: static property → lint). This is an *accepted* posture, not a bug, **provided** the lint rule `require-boundary-declaration` genuinely fires on every undeclared data-route handler at build time, i.e. the lint is the closed gate and the runtime is belt-and-suspenders. The risk: the lint rule has an **exempt allowlist** (R2) — so a new route added to a *new* file not yet in the lint's glob, or matching an over-broad exempt pattern, escapes both the lint AND the runtime deny. **Fix:** the plan must state that the lint glob (`packages/server/src/routes/**/*.ts`) is closed and any new route file is in-scope by default (allowlist is per-route-pattern, not per-file opt-in), and that the exempt allowlist is a *positive* enumeration (deny-by-default in the lint too), so "fail closed" holds statically. Without that, R1 + R2 together leave the global default open for genuinely new surfaces — which is the exact failure mode this WP exists to kill.

### SUGGESTION

- **[plan §Hole 4 / R3] Idempotency of the boot migration: define the ciphertext-detection contract precisely.** R3 says "attempt `decryptCredentialValue`; if it returns null AND non-empty → plaintext → encrypt." `decryptCredentialValue` returns `string | null` (confirmed export). Two edge cases the plan should nail: (1) a plaintext value that *happens* to be valid base64 of the right length could mis-decrypt to garbage rather than null — confirm the GCM auth tag makes `decrypt` return null (not garbage) on any non-ciphertext input, so detection is sound; the AES-256-GCM tag verification does give this property, but the plan should assert it as the load-bearing invariant. (2) Idempotency: running the migration twice must not double-encrypt — after the first pass every `apiKey` is ciphertext, so `decrypt` succeeds and the value is left alone. State this explicitly as the idempotency proof, and add it to the AC4 migration test (run migration twice → stable).

- **[plan §Hole 4] Specify whether `readServerConfig` returning still-encrypted `apiKey` breaks any *existing* consumer other than `sessions-routes.ts:249`.** The plan changes `readServerConfig` to return ciphertext and adds `resolveTierApiKey` as the single decrypt seam. If any other caller of `readServerConfig` today reads `apiKey` expecting plaintext (e.g. a validator, a different gateway path), it silently breaks. **Fix:** the plan should grep-enumerate all `readServerConfig` consumers and confirm `sessions-routes.ts` provisioning is the only one that needs plaintext (the GET path already strips via `stripApiKey`). This is a 1-line addition to the reconciliation table; without it the "single decrypt point" claim is unproven.

- **[plan §Worker confinement / Hole 3] The duplicate-active-id rejection closes the hijack, but spell out the reconnect/race window.** `pool.register` silently overwrites (`entries.set(id, …)` confirmed) and `onClose` unregisters. The plan's fix rejects `register` when `pool.has(id)` and active. Edge: a worker drops without a clean `onClose` (network partition) — its entry lingers, and its legitimate reconnect is now *rejected* as "id_in_use" until some cleanup evicts the stale entry. The plan should name the eviction/liveness mechanism (heartbeat TTL, or accept-and-replace-if-stale) so a flaky worker isn't permanently locked out — otherwise the confinement fix introduces a self-DoS. At minimum, document this as an accepted limitation with the existing reconnect behavior.

- **[plan §Verification / AC3] The "no credential reachable with only the worker token" test should assert the *negative space*, which is hard to test exhaustively.** AC3 says "assert there is no route reachable with only the worker token that returns any credential value." A test can only check the routes it enumerates. Reframe as: (a) positive — worker token rejected by `/api/credentials*` and `/api/workers` (different secret, confirmed `HYPERIDLE_API_KEY`); (b) structural — the worker WS handler never receives the credential store reference (assert by construction/types, not by probing every route). This is closer to a static guarantee than a runtime test; consider whether a lint/type assertion fits better per CLAUDE.md.

### What's Working Well

- **The declaration-vs-enforcement split is the right shape.** Centralizing *declaration* at mount (`requireBoundary`) while keeping *enforcement* local where the resource is already loaded (`authorizeRead` on the loaded row) avoids the N+1 re-query that the rejected registry Option A would force. The design-it-twice is genuine, not theatre — Option A's reject reason (middleware must re-load each resource, route patterns drift from handlers) is a real defect, not a straw man.

- **Host-scope returns `true` by design, loudly documented.** The `@lore` on `HOST_SCOPE` ("host-scope deliberately returns `true`; tightening is the future hook, NOT a bug; never widen participant-scope to `true`") directly encodes Hard Rule 5 (no over-restriction) and pre-empts a future agent "fixing" the apparent open door. This is exactly the load-bearing decision that needs a comment at its site. The crux note (most domain routes are host-scope = P, default-deny is about *declaration* not *restriction*) correctly frames the whole retrofit so nobody over-tightens bet/task/knowledge reads.

- **The flip-last ordering is correct and the rationale holds.** Stage 3 step 10 (warn → throw) gated on "only after every checklist route declares" honors the concept's Contract ("flipping the global default to deny is the *last* step"). Given the checklist is the closure set, the ordering is sound — *contingent on the CRITICAL being fixed* (the `/team-members` miss means "every route declares" is currently false, so the flip would be premature against the real surface).
