### CRITICAL

- **[plan §Decision 1 + §Protected tests] StatusChip uppercases the label in JS — BetCard's protected tests assert Title-Case text and will fail.** Verified: `StatusChip.tsx:101` renders `{safeStatus.toUpperCase()}` (JS string transform, not just the CSS `uppercase` class on `CHIP_BASE:85`). Decision 1 states the `label` path is "still uppercased + tracking," i.e. `(label ?? safeStatus).toUpperCase()` → DOM `textContent` becomes `"ACTIVE"`. But `BetCard.test.tsx` asserts `screen.getByText("Active")` (lines 40, 57, 63, 69, 75) and `expectedLabels = ["Draft","Active","Completed","Killed"]` (117-120) via exact textContent match. `.toUpperCase()` makes every one of these fail. The plan's protected-tests section claims these "stay green … update only the *mechanism* assumption" — that is false as written. **Fix:** the plan must decide explicitly: either (a) the `label` path renders the label *without* JS `.toUpperCase()`, relying on the CSS `uppercase` class for presentation so `textContent` stays Title-Case (then BetCard tests pass unchanged and the chip still reads uppercase visually) — recommended, since CSS `text-transform` is the correct layer for casing and keeps the registry strings canonical; or (b) accept the text change and rewrite the BetCard assertions to `"ACTIVE"` etc. Pick (a) and state it in Decision 1 ("`label` renders verbatim into the DOM; uppercase is CSS-only — `status.toUpperCase()` stays only on the default/status-name path"). Note this also resolves the casing for `shortLabel` ("Review" → visually "REVIEW", `getByText("REVIEW")` only passes if you keep JS uppercase on that path — so the two paths need a deliberate, documented casing contract, not a hand-wave).

- **[plan §Task 9 / §Note A] KnowledgeList status swap silently changes which rows show a badge — behavior change the scope rule forbids.** Verified: `KnowledgeList.tsx:240` `statusBadgeStyle` returns a style for `active`/`archived` only and **`null` for every other status**; the render site (`status && sStyle &&`, line 314) means today *most* knowledge statuses render NO status badge, and `archived` renders the label **"Stale"** not "Archived" (line 321). Task 9 ("delete `statusBadgeStyle` → `StatusChip status={knowledgeStatusToStatus(status)}`") would render a chip for *all 7* statuses and lose the "Stale" relabel — a visible behavior change. The track scope rule is explicit: "every replaced call site keeps its existing data and interaction behavior." **Fix:** Task 9 must preserve the current visible contract — either render the StatusChip only for the statuses that render a badge today (gate on the same condition), or justify+document the expansion as intended and add it to the proof set. Either way the plan must name the `archived→"Stale"` label and decide where it lives (it is a knowledge-status *label* — if knowledge gets no label registry per Task 9's "omit label," the "Stale" relabel is dropped unless handled). Currently the plan drops it.

### Designer open questions — verdicts

1. **StatusChip `label` prop (Option B) vs forcing presentation-status names.** **AGREE — Option B.** Option A loses domain information (`proposed`+`accepted`+`in_progress` all collapse to "HEALTHY") and breaks the BetCard human-label contract. The design-it-twice is honest, not theatre. Caveat: the casing contract must be nailed (see CRITICAL #1) — the prop is only safe once "label renders verbatim, uppercase is CSS-only" is written down.

2. **Verdict color: `partial`/`met_with_rework`/`partially_met` → `behind` (amber).** **APPROVE amber.** Verified `behind` = `--status-warning` (`StatusChip.tsx:49`), i.e. amber. "Not a clean win, look closer" is the right semantic and matches founder intent better than neutral gray (which is what AC5 explicitly calls out as the wrong status quo). No status semantics introduced — verdict enums unchanged. Ship it.

3. **AgentProfile VerdictDot + CapabilityBadge left local (NOT status-language).** **AGREE.** `VerdictDot` renders a thread `VerdictDecision` (approve/reject) — a conversational action, not an entity lifecycle status; no mapping exists and forcing one would misuse StatusChip. `CapabilityBadge` is a boolean capability, not status. Both are correctly out of scope. The spec's own constraint ("if a surface needs a rendering StatusChip cannot express, raise it, don't fork") supports leaving them — they are *not status forks*. Document the boundary in the plan risks (already done).

4. **Notification `shortLabel` registry field (B2) vs full strings (B1).** **APPROVE B2.** The popover row is a genuinely space-constrained 1-line meta-strip; full strings ("Review requests") risk overflow. B2 single-sources the vocabulary, kills the local `TYPE_LABELS` fork (AC4), and keeps `getByText("REVIEW")` satisfiable by deriving the expected literal from `NOTIFICATION_TYPES[…].shortLabel`. Verified `AF8-NotificationPopover.test.tsx:171` asserts `"REVIEW"` — keep the shortLabel uppercase (or uppercase it on that render path) so the test's updated-not-deleted assertion derives the same text. This intersects CRITICAL #1's casing contract: be explicit that the notification path uppercases.

5. **BetCard ≤5% pixel-diff risk.** **ESCALATE as the highest build risk — gate, don't assume.** Verified BetCard's current badge is a bespoke pill (`badgeClasses`, `px-[9px] py-[3px]`, `rounded-[var(--r-pill)]`, `text-[12px] font-[500]`, Title-Case, an 8px status dot rendered *separately*) — materially different chrome from StatusChip's `CHIP_BASE` (`px-[8px] py-[2px]`, `rounded-full`, `text-[11px]`, mono font, uppercase, a built-in 6px dot). These will **not** pixel-match without reconciliation. `BetCard.html` exists (design truth, never edit). Sequence BetCard last, gate on `npm run ds:sync` ≤5%, and if StatusChip's chrome can't match the HTML, the correct move per the spec is to raise the gap to the design system — NOT keep the fork and NOT loosen the threshold (`visual-parity.md`: 5% is non-negotiable). The plan handles this correctly; reinforce that a HTML-vs-StatusChip mismatch is a *hand-off to Claude-Design*, a possible blocker, not a silent TSX hack. Flag: this single task may not fit the M (~6h) estimate if reconciliation is needed.
