# Architecture Critique: AK1

Verdict: **APPROVED (≥7)** — but the builder MUST resolve the two CRITICAL classification gaps below before/at step 5, because they are silent behaviour-change risks, not style nits. They are narrow and concrete; they do not warrant a full Phase-2 restart.

This is a behaviour-preserving cross-cutting rename. The plan is unusually thorough for this class: it enumerates the surface by term, distinguishes the three retained `workspace` meanings, picks the right tool (static grep guard, not a runtime test) for the "no dangling references" AC, flags the migration drop+add hazard, and orders the work bottom-up to keep the tree compiling. The score is held back by two genuine mis-classifications in the `workspace` KEEP-list that I verified against the code, plus a thin spot in the guard's coverage of the bare run-unit identifiers.

### CRITICAL

- **[plan §Inventory Term-2 KEEP-list + §RISKS-2] `{{workspace}}` is mis-classified as an external third-party contract; it is HyperIdle's OWN template-variable name and the plan never decides whether to rename it.** The plan KEEPs `{{workspace}}` calling it "aider/goose/opencode's own flag names, not ours." Verified false: `packages/server/src/harness/cli-harness-adapter.ts:29` defines `type TemplateVar = "{{workspace}}" | "{{model}}" | ...` — this is our own substitution DSL, resolved by `resolveTemplates` (line 108) against `config.workspacePath` (line 170). The external contract is the bare flag `--workspace` (goose's own flag, line 235 of adapter-pool) — that one legitimately stays. But `{{workspace}}` is a HyperIdle token naming the run-unit; under the locked nouns it is exactly the kind of run-unit identifier the rename targets. The plan must explicitly DECIDE: either (a) rename `{{workspace}}`→`{{sandbox}}` across `cli-harness-adapter.ts` (the `TemplateVar` union + docstring), `adapter-pool.ts:225/235/244`, and the X5 tests, OR (b) KEEP it as a frozen config-DSL key and say so with a reason. Leaving it in the KEEP-list under a false rationale guarantees the builder freezes a token that should move (or, if the guard is later tightened, a false positive). Fix: move `{{workspace}}` out of "external CLI contracts," add a one-line decision (rename to `{{sandbox}}` is the behaviour-preserving choice since substitution is by string match — confirm the resolver replaces whatever key the args use).

- **[plan §Inventory Term-2 + §RISKS-2] A second, distinct `workspacePath` is unaccounted for: `CliHarnessConfig.workspacePath` / the `templateVars` field in `cli-harness-adapter.ts`.** The plan's inventory lists `ToolContext.workspacePath`→`sandboxPath` (tool-registry.ts:47) and the session-provisioning `workspacePath` family, but never names `cli-harness-adapter.ts`'s `config.workspacePath` (line 170) — a different field on a different type. The plan's bottom-up step 5 ("server/harness/ … rename adapter files + classes … leave `/workspace` cwd and flags untouched") does not enumerate `cli-harness-adapter.ts` at all, yet it carries `workspacePath`. If the builder renames the `ToolContext.workspacePath` but misses this one, the guard (which bans `/workspaceBasePath/`, `/workspaceSnapshot/`, `/workspaceHandle/` but NOT bare `workspacePath`) will NOT catch it — see WARNING-1. Fix: add `cli-harness-adapter.ts` to the Term-2 inventory and to step 5, explicitly listing `CliHarnessConfig.workspacePath`→`sandboxPath` and the `{{workspace}}` token together.

### WARNING

- **[plan §Guard] The two-tier guard deliberately does NOT ban bare `workspacePath` / `workspace` deps — but the plan's own argument that "after the rename they're gone" is unverifiable by the guard and is precisely where the two CRITICALs hide.** The plan bans the typed identifiers (`WorkspaceAdapter`, `workspaceSnapshot`, etc.) and argues the bare run-unit vars are "caught indirectly." That reasoning fails for `cli-harness-adapter.ts`'s `workspacePath` and any straggler bare-`workspace` field that isn't a typed member — the compiler is happy (it's just a string field), and the guard skips it. The guard's job for this AC is "no dangling references"; a bare `workspacePath` that survives IS a dangling reference. Fix: either (a) add a `/workspacePath/` ban with an explicit allowlist for the genuinely-kept cases, or (b) downgrade the AC claim — state plainly that bare-`workspace` run-unit residue is caught by code review + the route-checklist grep, not the guard, and add `workspacePath` to the §route-checklist / §architecture-review grep list. As written, the plan over-claims the guard's coverage.

- **[plan §AGENTS.md + §RISKS-5] The CLAUDE.md→AGENTS.md change is the one runtime-behaviour touch, and the plan's "dual-write fallback" is the correct instinct but the decision is deferred to the builder with no default.** Verified: `prompt-composition.ts:11-17` lore states the Claude Agent SDK and aider/goose/opencode auto-discover `CLAUDE.md` from the workspace root. Renaming the written file to `AGENTS.md` only is a behaviour change IF any harness does not also read `AGENTS.md`. The plan says "if any reads only CLAUDE.md, dual-write" — good — but a behaviour-preserving rename should DEFAULT to dual-write (write both `AGENTS.md` and `CLAUDE.md`) unless the builder positively verifies every adapter reads `AGENTS.md`. Fix: make dual-write the default in the plan, not the fallback. The AC ("system prompt + AGENTS.md") is satisfied by AGENTS.md existing; it does not forbid a compatibility CLAUDE.md. This removes the single largest behaviour-change risk in the WP and converts a "verify-then-decide" into a "ship-safe-then-optionally-simplify."

- **[plan §protectedTests] The protected-tests list names the harness/CLI security test corpus but omits the harness adapter + CLI-template tests that the rename touches most.** The list covers assistant/agents/db/fabric/session-provisioning. Missing: `packages/server/src/harness/__tests__/X5-cli-harness-adapter.test.ts` (asserts `{{workspace}}` resolution — directly affected by CRITICAL-1) and `docker-workspace-adapter.security.test.ts` (the S6 argv-not-shell-interpolation invariant — value semantics MUST NOT change while the file is renamed). Per the behaviour-equivalence AC, any test whose *value* assertion changes is a behaviour change. These two carry the harness security invariants and must be frozen-by-value. Fix: add both to §protectedTests.
