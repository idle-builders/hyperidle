## Observations

### Worked well

1. **Designer single-dispatch delivered all phases.** Phase 1 (e743c87) shipped concept.md + design/variants.md + design/approved.md + architecture.md in one turn. The design critique (dc5c3e9) flagged only minor addenda ("decide cascade" + "acknowledge EmptyState departure" + "add long-body story"), not a re-design. Architecture critique R1 had one blocker (security test cases), but the blocker was technical (add 6 XSS cases) not architectural. Pattern: /design and /architecture can ship in the same phase when the problem is well-scoped (a known component replacing a known surface, specs are tight). This compressed 2 serial phases into 1 parallel output.

2. **Security bar was found and fixed cleanly.** Architecture-critique R1 scored security at 6/10 (blocker: "no explicit XSS test cases, DOMPurify config implicit, `javascript:` URI handling unspecified"). Designer addressed all three in one round (R2: 075c6af). T-SEC-1 now has 6 concrete cases (script strip, onerror strip, iframe block, javascript: href strip, event-handler strip, markdown [click](javascript:…) regression). DOMPurify config is explicit ("default profile, no overrides, audited defaults > hand-rolled allowlist"). The fix took ~60 LOC added to architecture.md and was integrated into the write-tests phase without rework. **Signal:** security gate worked. The pipeline caught a real gap (test-optional thinking) and forced the producer to make the contract explicit.

3. **Protected-test contract was respected.** Architecture § H.2 noted that `LEGACY_DETAILS` data is still consumed by `findDetail()` to supply metadata; deleting it would break the protected `KnowledgeDetail.test.tsx` assertion on `"company"` / `"belief"` strings. The builder (cc94f51) kept LEGACY_DETAILS and added a @lore block explaining the deviation (KnowledgeDetail.tsx:18-24). The plan tracked the deferral to L25 in follow-ups.md. No surprise test failures post-ship; the deviation was bounded and documented upfront.

4. **Block-id stability was over-tested but correct.** T6 (`KnowledgeBody.id-stability.test.ts:54-127`) asserts byte-identical ids when editing one section. The test runs both as a pure `deriveBlocks` exercise AND as an RTL-rendered snapshot check. T7 covers round-trip losslessness (9 block kinds in a single fixture). The architecture-critique R1 called out the fixture body as "unspecified"; R2 accepted it as tractable at write-tests time. The result: stable keys for React reconciliation, proven by two layers of evidence. No flicker observed in visual proofs (k1-belief-body.png, k1-playbook-body.png, k1-empty-body.png).

5. **Cascade specificity was caught and resolved early.** Architecture-critique R1 R6 flagged that `[data-knowledge-body] :is(h*)` rules in `@layer components` would lose to `HeadingPayload`'s `leading-[1.2]` utility because `utilities` layer beats `components` in Tailwind cascade order. Designer chose the right call (R2): drop the `line-height` override and defer to L2's token. The rule set in index.css (cc94f51) omits the override, and the @lore block documents the decision rationale. No cascade surprises in the visual proofs.

### Didn't work / friction

1. **Architecture-critique R1 security blocker was discoverable upfront.** The blocker (T-SEC-1 missing) was not a design/architecture gap per se; it was a checklist item. The architect knew sanitisation was happening (DOMPurify.sanitize in KnowledgeBody) but did not enumerate test cases. The reviewer spotted this via the 9-dimension rubric (Security dim). **Signal:** `/architecture` skill should include a security-test-mandatory checklist for any surface rendering user-authored content (markdown, HTML, user links). T-SEC-1 should have been in the plan draft, not discovered in critique. The fix was fast (one round, 60 LOC), but it was rework.

2. **Empty-state design departure was stated twice.** Design-critique R1 flagged that using a bare `<p>` instead of the `EmptyState` primitive was a departure but was defensible. The architect documented the same rationale in architecture.md; the designer then re-stated it in approved.md R2 (ea60794). The concept was solid but the communication was serial (reviewer → architect → designer → review) when it could have been resolved in Phase 1. **Signal:** design-critique should surface multi-phase communication debt earlier. "If the architect will need to explain this, state it now" as a note to the designer.

3. **Multi-section-playbook fixture id was unspecified through Phase 2.** Architecture-critique R1 softly flagged "E1/E2 reference a 'multi-section-playbook' but the fixture id is not named." The builder (write-tests, 7471683) had to infer which fixture or add one. The test (l23-knowledge-body.spec.ts:45–90) ended up injecting a hard-coded multi-section body via the edit flow, which is correct but is not a proof that a persistent fixture exists. **Signal:** soft items in critique (fixture id specification, specific markdown payload for T7) should be tracked in follow-ups.md if not resolved, so the builder sees them. No blocker, but it was an ambiguity in the handoff.

4. **One-line vitest-toon.ts drift sneaked into the test commit.** The red-phase commit (7471683) flipped `!line || !file || existsSync(file)` to `!(line && file && existsSync(file))` at vitest-toon.ts:131. Logically equivalent, out of L23 scope, but harmless. **Signal:** test commits should be red-phase only (failing tests for AC requirements). Off-topic changes (linter fixes, refactors) should be separate commits or deferred. This was a tiny scope-creep (2 LOC) but it complicates blame/revert.

### Pattern candidates for /compound

1. **CC-008-protected-test-removal (recurrence count: 3+).** L15 retro flagged that `WorkTeam.test.tsx:73-90` (frozen I4 contract) was missed until architecture-critique. L23 shows the opposite: the architect correctly preserved LEGACY_DETAILS data to avoid breaking the protected test. Both cases show that protected-test contracts are not automatically surfaced. **New observation:** the current practice is manual (architect must read the test and understand its constraints). **Candidate:** add a `/architecture` checklist item "Do any existing tests import the files you're modifying? Read them. Are any protected?" This is a skill enhancement, not a new pattern.

2. **CC-###-security-test-mandatory (NEW pattern, L23 only so far).** The architecture-critique security blocker (T-SEC-1 missing) shows that security test cases are optional in the architect's mental model. For L23 specifically, the payload was `DOMPurify.sanitize(html)` on user-authored markdown — an XSS surface. The test cases should have been non-negotiable, not discovered-in-review. **Candidate:** add to `/architecture` skill: "For any surface rendering user-authored markdown/HTML: T-SEC-1 (explicit XSS test cases) is mandatory. Enumerate: script-tag strip, event-handler strip, javascript: URI strip, iframe block, data: URI handling, markup-in-markdown regression."

3. **CC-###-design-departure-communication (NEW pattern, L23 only so far).** The EmptyState departure (bare `<p>` vs EmptyState primitive) was flagged in design-critique R1, re-stated in architect-critique R2, re-stated in approved.md R2. The concept was solid but the handoff was serial. **Candidate:** design-critique should surface "implications for the next phase" notes. If a design departure will require architect explanation, note it so the next reviewer checks whether it was resolved.

## Specific suggestions for `/compound`

1. **Add T-SEC-1 (sanitization XSS test cases) to `/architecture` mandatory checklist for any UI surface that renders user-authored markdown/HTML/links.** Pattern match: `deriveBlocks`, `markdown`, `html`, `innerHTML`, `sanitize`. Required add: 6+ cases (script, event-handler, javascript: URI, iframe, data: URI, markup-in-markdown). Evidence: L23 architecture-critique R1 scored security 6/10 until these cases were enumerated.

2. **Add "protected tests" probe to `/architecture` skill.** If your files import from or export to test files, read those tests. Are any frozen by I4 or another contract? Document them as risks (R1, R2, etc.) if removal would break them. Evidence: L23 correctly preserved LEGACY_DETAILS data; L15 missed COLUMN_TO_STATE export until critique. One-line skill enhancement.

3. **Design-critique should surface "multi-phase implications" for design departures.** If you flagged a departure from an existing primitive (e.g., EmptyState), note it for the architect: "This will need explanation in your plan." Evidence: L23 EmptyState departure was stated 3 times across phases; earlier visibility saves serial re-statement.

4. **Specify fixture ids and markdown payloads in architecture-soft items.** If critique notes "E1 uses a 'multi-section-playbook' — specify the fixture" or "T7 needs a fixture covering supported kinds — pick the payload," make sure it's in follow-ups.md. Evidence: L23 builder had to infer / add the multi-section fixture; the test works but the specification was ambiguous.
