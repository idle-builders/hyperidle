## What worked

1. **Concept probed hard on the 1:1 invariant upfront.** The concept doc (§"Probes settled") enumerated seven specific tensions (merge tables?, when is Product ≠ Team?, legacy WorkTeam fate?, etc.) and locked answers before design touched them. This prevented speculative design variants and architecture hedging. The designer and architect could focus on the mechanics (endpoint shape, page layout) knowing the semantics were settled. The notebook-style probes + settled sections became a reference point all three critique phases cited.

2. **Phase 2 reviewer caught the L15 surface preservation gap early, before code.** The architecture initially claimed "re-route the L15 e2e through Bet detail; TaskSheet ships unchanged." Reviewer's grep verified this was false — TaskSheet exists only in deleted WorkTeam.tsx. Rather than surfacing at code-review (Round 1), the BLOCKING fix was injected into the architecture with task 6.5, executed in the build dispatch, and verified end-to-end before code-review. This eliminated a class of post-merge regressions. Cost: 30 min amendment + rebuild; benefit: caught a hard dependency that would have failed silently.

3. **Builder executed Phase 2 amendments faithfully before red phase.** Rather than treating architecture-critique amendments as "nice to have," the build dispatch incorporated task 6.5 (TaskSheet wiring) into the ordered task list, wrote tests first (TDD red), and verified the L15 e2e green before build completion. The L15 e2e test passed 4/4 even after the Phase 4 reviewer ran a fresh grep — proving the mitigation was real, not theater. This is the exact workflow CLAUDE.md prescribes ("Never skip architecture critiques; the critique exists because designs have blind spots").

4. **Code review Round 2 triage was honest about surface deletion vs. re-route.** The reviewer found 9 failing e2e tests and classified them: (a) Team Board describe block → delete (genuine surface gone, not a test re-route target), (b) PitchSelector flow → skip (surface gone, no corresponding Bet-detail flow exists), (c) L18 task-thread → re-route (surface evolved, integration point moved). Each path was justified with @lore documentation. The distinction between "test should run on the new surface" and "test was testing a deleted surface" prevented cargo-cult test migration. Contrast: L16 had to push a synthesis-ripple fix in Round 2; L13 handled the ripple ripple correctly the first time through because the reviewer was explicit about which specs were genuine failures vs. which were testing deleted surfaces.

5. **Concept lore about ProductSummary vs ProductDetail prevented scope creep.** The architecture proposed a composite endpoint (`GET /api/products/:id` returning ProductDetail with product + team + roster + burn + activeBets). The reviewer independently justified the composite (page renders all on first paint, no cascade of loading states, precedent in `/api/bets/canvas`). The alternative (three split endpoints) was rejected with citations. This clarity meant the builder had one target, not three variants to hedge between. The server implementation stayed lean (one endpoint, one query shape). If the endpoint needs to split later, the URL is stable — no revision needed.

## What missed

1. **AC#8 e2e regression slipped into Round 1, blocking the ship.** The spec says "the full e2e suite stays green." The code-review diff touched routing (router.tsx, AppShell.tsx) and would break any e2e that navigates to `/work/team`. The builder updated two accessibility specs (2709ffe) but missed five others (work.spec.ts, synthesis.spec.ts, task-thread.spec.ts, work-surface.spec.ts, touch-targets.spec.ts). These were untouched specs outside L13's "files I care about" silo. Root cause: no pre-review diff-scanning rule that flags "if you delete a route, find all e2e specs that navigate to it." The architecture named the risk (§"Legacy `/work/team` removal") but the mitigation ("run grep for `/work/team` in e2e specs, check them") was not explicit. Required a full Round 2. (Compare to L16's synthesis ripple: that also hit Round 2, but it was a single ripple site vs. L13's five.)

2. **BetRow re-implementation diverged from design's stated intent (BetCard).** The design doc said "each row reuses the existing `BetCard`" and noted the same component is used on Portfolio and Canvas. Builder shipped a custom `BetRow` single-use component instead, re-implementing pitch + status + appetite + progress. This caused design bug D1 (committed bet mapped to "behind" status) and meant the progress numerals lost the tabular-numerals style from BetCard. The architecture didn't catch this (it just said "uses BetCard") and code review had to flag it. Cost: Round 2 rework. This points to a gap: when an architecture says "reuse X primitive," the builder should cite the exact import in the code commit message, not wait for review to enforce it.

3. **Empty-state copy about "team's Canvas" persisted through two critique rounds.** The design-critique Round 1 flagged the copy as dishonest (Canvas no longer renders on Product page; it was on deleted WorkTeam). The recommendation was to drop the Canvas reference. The architecture inherited the copy verbatim without revision. Code review Round 1 re-flagged it as a nit. The builder fixed it in Round 2 (commit 757443b). A tighter design→architecture handoff (architecture rewrites copy per critique notes, builder inherits the revised copy) would have prevented this three-cite path.

4. **N+1 query pattern in products-list endpoint was accepted without a follow-up entry.** The architecture named the risk: "for each product, two count queries plus an inner loop." The risk mitigation said "v0 implementation is a single SELECT with subquery counters using Drizzle sql template — one round-trip total." Builder shipped the per-row loop instead (acceptable for the demo seed). The architecture committed to logging this as a follow-up in `follow-ups.md` (§"Future work"), but the file wasn't updated. The code reviewer noted this as residual concern A1 (deferred). This pattern—"defer as a follow-up" without actually writing the follow-up—leaves cruft in the code with no tracking mechanism. The follow-up should have been written synchronously.

5. **Test ID hooks were added but not all were used by the Playwright e2e.** The architecture defined 10 testid hooks. The e2e spec steps use most of them, but `product-roster-row` (per-agent hook) is defined but the e2e assertion is a higher-level "at least one `[data-testid='product-roster-row']` exists." Fine for the e2e, but it means a future Playwright writer extending the e2e could miss that the granular hooks exist. This is a documentation/discovery gap, not a functional gap. (Contrast: L16 explicitly called out the fixture-boundary ESLint rule in the architecture, making it discoverable.)

## Compounding signal

**Single most important signal for `/compound`:**

**Phase 2 architectural critique found a load-bearing false claim ("TaskSheet ships unchanged on Bet detail") that would have surfaced as a Round 2+ blocker if not caught before code.** The audit method was brute-force (grep the codebase, verify the claim directly). This validated the principle: **require Phase 2 reviewers to independently audit claimed facts with citations.** When the architecture says "TaskSheet is mounted in X and Y," the reviewer should grep and cite file:line. When the architecture says "the endpoint works like Z precedent," the reviewer should check Z's actual shape. When the architecture says "schema permits one row per X," the reviewer should look at the schema definition.

This is what happened here: the architecture made a claim about L15 surface preservation; the reviewer verified it cold (grep output + file inspection); the claim was wrong; the architecture was amended before code wrote code. Cost: 30 minutes; benefit: prevented a post-merge regression that would have left L15's e2e broken.

**Secondary patterns:**

1. **E2E test migration after a surface deletion requires a classification step, not a mechanical re-route.** L13's Round 2 review distinguished "test was testing a deleted surface (delete it)" from "test navigates to the deleted surface but is testing an evolved feature (re-route it)." L16 didn't have this distinction and ended up with a synthesis mock ripple. Proposal for `/compound`: add a decision-tree to the architecture-critique template: "if you delete a route, for each e2e spec that uses it, classify as (a) surface-specific test [delete], (b) feature still exists on new surface [re-route], (c) unsure [flag for reviewer]."

2. **Design-critique nits on copy/naming should trigger architecture rewrites, not get inherited verbatim.** The "Canvas" reference in empty-state copy was flagged in design-critique Round 1 and appeared again in the architecture unchanged. It took code review Round 1 to kill it. A tighter handoff would have the architecture apply critique recommendations and cite the application in the architecture diff ("per design-critique note X, changed empty-state copy from A to B").
