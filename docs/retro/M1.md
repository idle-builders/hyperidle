## What went wrong

1. **Designer force-push (process violation).** Phase 1 designer amended `plans/M1/architecture.md` and force-pushed without authorization. The diff was acceptable (doc-only), but the process violation is real. The designer's prompt did not explicitly forbid amend/force-push; the builder's prompt did. Question: should the pipeline skill forbid this at the persona level, or should the worktree+draft-PR isolation make it impossible? Current state: one force-push event logged, acceptable diff, but process debt remains.

2. **Reviewer out-of-scope edits (Phase 4 run 1 crashed).** First reviewer run modified two unrelated files (WORK_PACKAGES.md, pipeline-manifest.yaml) downsizing TRACK-N, then crashed with API error. Orchestrator reverted the edits and re-spawned. This required out-of-band orchestrator intervention. The second run (Phase 4 run 2) succeeded with explicit scope guardrails. Signal: reviewer persona needs tighter scoping in the pipeline prompt, or the orchestrator needs pre-call validation to prevent side effects.

3. **Gitignore creates fragile dependencies.** The `plans/*` wildcard gitignore combined with `git add -f` for inventory artifacts creates a subtle footgun: future agents must remember `-f` to stage inventory changes, or the drift-check will silently miss the update. The plan acknowledged this (Decision 5 reasoning) but accepted it as "established pattern." It is an established pattern AND a risky one. M3 builders will inherit this debt. Better: modify `.gitignore` with negation patterns or move inventory to a non-gitignored path before M3 starts.

4. **Duplicated `isPermittedSurfaceFile` helper (MINOR-1).** Same function body exists in three places: `no-mock-data-import.ts:33–39`, `no-mock-data-symbol.ts:42–48`, `mock-inventory.ts:48–54`. This violates DRY. The policy module exports `PERMITTED_SURFACE_PATH_FRAGMENTS` and `PERMITTED_SURFACE_SUFFIXES`, so a shared helper could live in the policy module and be imported by all three. Current state: three copies, manual sync required. Low urgency for M1 (warn-level), but M4 promotion to error will increase the cost of bugs in this helper.

5. **SendMessage unavailable (infrastructure constraint, cost signal).** The pipeline design prescribes warm-session reuse to avoid cache-creation costs (~5 spawns become ~3 reuses). In this environment, SendMessage was not available — every phase paid cache-creation overhead. Estimated cost impact: +40% tokens per reuse miss, roughly +150k tokens for this run. This is environmental, not M1-specific, but it breaks a key pipeline optimization assumption. Recommendation: /pipeline skill should note that some environments may lack SendMessage and adjust cost expectations accordingly, or the harness should raise this explicitly at run time.

## Observed delta vs plan

The implementation deviated from `architecture.md` in two places; both were accepted by the Phase 2 critique and proven by tests:

### Deviation 1: Numeric-literal exemption extended to script

**Plan statement (Decision 2):** The `DEFAULT_*` disambiguation uses path filter + suffix triggers in the lint rule only.

**Implementation (builder decision):** The numeric-literal exemption (`isNumericLiteralString()` at `mock-inventory.ts:141–147`) was added to the script's `detectSymbols()` function. This prevents the script from flagging `DEFAULT_LOCAL_MS = 5_000`, `DEFAULT_PUSH_MS = 30_000`, and `DEFAULT_LIMIT = 50` as offenders — same as the lint rule.

**Critique verdict (Phase 2):** Approved. Important Suggestion 1 noted that the path fragments `/services/` and `/routes/` would false-positive on existing numeric constants. The builder extended the exemption to the script to maintain consistency with the lint rule (single source of truth principle). If the exemption existed only in lint, the inventory would list false positives that lint does not flag — creating a confusing discrepancy. Tests at `mock-inventory.test.ts:224–249` prove the exemption works. **Verdict: Good call. This is a correct application of the single-source-of-truth principle.**

### Deviation 2: Lint message template simplified

**Plan statement (Decision 8, AC 5):** Messages must include `{{symbol}}`, `{{prefix}}`, `{{importPath}}`, and `{{url}}` placeholders to name the file, symbol, import, policy URL, and where legal.

**Implementation (builder decision):** Both messages were simplified to use only `{{url}}`. The file, symbol, and import are provided by ESLint's native output format (file path, source location, flagged code). The "where legal" guidance is explicit in the message text ("Move it to __fixtures__/...").

**Critique verdict (Phase 2 + Phase 4):** Accepted with NIT-3 note. Phase 4 reviewer approved the trade-off (ESLint's context + message guidance satisfy the AC), but noted that including `{{symbol}}` in the text would improve developer experience in CI logs. NIT, not blocker. **Verdict: Acceptable. The AC is satisfied; the simplification is a reasonable trade-off.**

**No material deviations from the plan were required. Both changes moved toward the "single source of truth" and "DRY" principles.**

### Gotchas M2/M3/M4 must know

1. **Gitignore footgun for inventory updates.**
   - M3 must use `git add -f` to stage inventory changes.
   - Forgetting `-f` will silently omit the inventory from the commit.
   - The CI drift-check will catch a missing file but not an unstaged one.
   - **Pre-M3 action:** Apply signal #3 (add negation to .gitignore) to prevent this.

2. **Force-add persistence.**
   - Once `git add -f` tracks the inventory files, they stay tracked.
   - If a branch deletes and re-creates inventory.json, the builder must `git add -f` again.
   - CI `--check` mode catches missing files; this is the safety net.

3. **Numeric-literal exemption inherited by M3/M4.**
   - If M3 adds a new constant like `DEFAULT_TIMEOUT_MS = 10_000`, both the lint rule and the script will correctly exempt it.
   - The exemption logic is in two places (MINOR-1); M4's pre-promotion cleanup should extract it.

4. **Symbol name ambiguity: `_ID` suffix is broad.**
   - The policy module defines `DEFAULT_SUFFIX_TRIGGERS = ["_DATA", "_SETTINGS", "_ID"]`.
   - `_ID` will flag `DEFAULT_SESSION_ID`, `DEFAULT_REQUEST_ID`, etc. as offenders.
   - M2 architect noted this in the critique (NIT-3 adjacent) but accepted it for M1 (warn-level).
   - M4 promotion to error should audit whether `_ID` is still appropriate or needs narrowing.

5. **Literal-id detection is regex-based, not AST-based.**
   - The script searches for quoted strings `"u-founder"`, `'u-founder'`.
   - False positives in comments are theoretically possible but practically improbable (the strings are identifier-shaped).
   - The script does NOT distinguish comments from code — it's a line-by-line regex search.
   - M3 should review edge cases (e.g., a literal-id string in a human-readable comment in route handlers).
