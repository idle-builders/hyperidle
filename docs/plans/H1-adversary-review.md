# H1 Git Export — Adversary Review

Read-only adversarial review of the Git Export implementation against TRACK-H.md §H1 acceptance criteria. Scope: `git-export.ts`, `git-export-runner.ts`, `git-export-config.ts`, `git-export-routes.ts`, and the three test files.

### Findings

- [CRITICAL] `packages/server/src/app.ts:80` — `registerGitExportHandler(options.db, eventBus)` is called with **no `runner` option**. Inside `git-export.ts:345-349`, if `opts.runner` is missing the handler logs a warning and returns without running. Net effect: AC1 ("Human edit to L4 PRINCIPLES → Git export runs, commits new PRINCIPLES.md") **does not work in production**. It only works in the unit tests where a FakeGitRunner is injected. Any human-edit-triggered export is silently a no-op. Fix: build a runner in app.ts from `loadGitExportConfig(db)?.repoPath` (lazily, inside `fire()`), or pass a factory (`createRunner: (repoPath) => createGitRunner(repoPath)`) through to the handler and call it with the fresh `cfg.repoPath` at fire time. This must be a factory, not a fixed runner, because `repoPath` can change via PATCH /config between events.

- [CRITICAL] `packages/server/src/services/git-export.ts:218-224` — `writePlanToDisk` only writes entries whose body byte-differs from what is on disk. **Deletions are never propagated.** If a knowledge item is archived (`status='archived'`) or its kind/layer/scopeId changes so it no longer maps to the same path, the stale markdown file stays on disk forever, gets re-committed as "present", and diverges from the DB truth. AC4 ("exported markdown matches item body exactly") is violated the moment any item is archived or renamed. Fix: materialize the full set of expected paths from the plan, enumerate the tracked files git knows about, and remove any tracked path not in the plan before `git add -A`.

- [CRITICAL] `packages/server/src/services/git-export.ts:280-283` — The "no changes" decision is made via `runner.diff()`, which runs `git diff --quiet HEAD`. That command does **not detect newly-staged (previously untracked) files** — it only compares the working tree to HEAD. After `git add -A` on a brand-new file, `git diff --quiet HEAD` returns 0 (clean), so `runGitExport` returns `{status:"noop"}` and never commits. This breaks AC1 on the very first export for any new item. The integration tests don't catch it because `ensureRepo` runs against a fresh `git init`, and the first export happens to have an unborn HEAD — which the runner short-circuits by returning `false` (dirty). The second export (after one commit exists and a new L2 item is added) is the failure mode nobody tested. Fix: use `git diff --quiet --cached HEAD` (or `git status --porcelain` length) after `add` to detect staged newness.

- [CRITICAL] `packages/server/src/services/git-export-runner.ts:152-159` — `diff()` returns `true` (clean) on HEAD when `rev-parse --verify HEAD` succeeds and `diff --quiet HEAD` exits 0. But **before the diff check, `runGitExport` calls `add([])` which stages everything**. On an already-initialized repo with existing tracked files, a new untracked file becomes staged and indexed but working tree == HEAD for the other files. `git diff --quiet HEAD` with a purely newly-indexed-only path is actually 1 (not clean) in modern git — OK — but for a modification to an existing file already reflected in the index, `--quiet HEAD` does compare index+worktree vs HEAD so it does catch it. Mixed together this is correct by accident. The right check is `git diff --cached --quiet HEAD` which is explicit about "did anything change relative to HEAD counting the index". The current ordering (`add` then `diff`) only works because `--quiet HEAD` includes the index implicitly. This is a subtle invariant that is not asserted by any test and will break if someone moves the `add` call. Fix: switch to `--cached` semantics and pin the behavior with a test.

- [CRITICAL] `packages/server/src/services/git-export.ts:205-207` — `absolutePath` uses `path.posix.join`. On Windows hosts this is wrong (backslash vs forward slash). The plan lists repoPath as "absolute path" but the sanitizer only rejects non-`/`-prefixed paths, so Windows is silently unsupported yet never advertised. Either (a) reject non-POSIX hosts in `sanitizeRepoPath`, (b) use `path.join`, or (c) add `@lore` making the Linux/Mac-only stance explicit. Right now it's a latent platform bug with no test.

- [WARNING] `packages/server/src/services/git-export.ts:300-303` — Push-phase error still calls `writeLastExport` before returning `{status:"error", phase:"push"}`. The rationale ("commit still succeeded locally") is defensible, but `last_export_at` as surfaced in `GET /status` now claims a successful export when the remote has nothing. Operators monitoring "when did I last export to origin" will be lied to. Fix: either rename the field to `lastCommitAt` vs `lastPushAt` and track both, or do not update `last_export_at` on push failure.

- [WARNING] `packages/server/src/services/git-export.ts:87-93` — `buildCommitMessage` does **not handle `entries = []`**. Header says "export 0 item(s)", bullets list is empty, and then bullets are joined with two blank lines above the footer → a commit message that is technically valid but useless. The code path is unreachable today because `diff()==true` short-circuits above — but the function is exported and tested independently, so callers will treat it as pure. Add an explicit guard / test asserting behavior on empty array, or document the precondition.

- [WARNING] `packages/server/src/services/git-export.ts:104-114` — `mapRowToEntry` uses `row.topic` and `row.id` **unsanitized** as a filesystem path segment for L4 REFLECTION: `factory/REFLECTIONS/${topic}.md`. A `topic` containing `/`, `..`, a NUL byte, or a Windows-reserved name (`CON`, `PRN`) will happily write to an attacker-chosen location inside `repoPath`. Because `topic` is database-resident and originates from L4 reflection writes (system or human), this is a stored-path-injection with the write confined to `repoPath`. Fix: whitelist `[A-Za-z0-9._-]` for topic, or slugify. Similarly `scopeId` is used directly (`products/<scopeId>/...`). Scope-id with slashes would silently create nested dirs. No test covers this.

- [WARNING] `packages/server/src/services/git-export-config.ts:156-169` — `sanitizeRepoPath` rejects `..` **segments** but allows `/etc`, `/root`, `/var/run/docker.sock` parent, `/proc/self/...`, symlinks, and any path the server can write to. AC5 says "configurable repo path" but the route accepts a patch with `repoPath: "/etc"` and the orchestrator will happily `mkdir -p /etc` (no-op), `git init /etc`, and scatter files. Since the route is behind `authMiddleware` the risk is limited to an authenticated caller, but any leaked API key becomes a "write arbitrary files" primitive. Fix: require repoPath to live under a configured `GIT_EXPORT_ROOT` or a workspace-owned dir, and reject paths containing a `.git` segment unless the dir already exists.

- [WARNING] `packages/server/src/services/git-export.ts:173-179` — The module-level `exportMutex` is **process-global**, shared across *all* test `createTestDb()` instances in the same Vitest worker. Two describe blocks that each call `runGitExport` concurrently will serialize even though they use different DBs — and worse, a hang in one test's mock runner will starve the queue for subsequent tests in the same file/worker. This also means the "concurrent calls serialize" test at git-export.test.ts:481 contaminates mutex state for whatever runs after it. Fix: scope the mutex per-db or per-repoPath (Map-keyed), or reset between tests.

- [WARNING] `packages/server/src/services/git-export.ts:325-372` — Race in the handler: between `clearPending()` and `setTimeout(fire, debounceMs)`, a second event can clobber the timer after `fire()` has already begun executing (pending set back to null inside `fire` at line 341). Timeline: event A fires timer → timer callback starts → sets `pending=null`, starts `await loadGitExportConfig(db)` → event B arrives → `clearPending()` sees null (no-op) → schedules B's timer → A's `runGitExport` continues to completion → B's timer fires and runs *another* export. That's fine unless B's event was meant to be *coalesced into A's run* (which it was, because they came during the same burst). This causes redundant commits in a burst that straddles the fire window. Not catastrophic (each would noop on diff) but doubles the git load. Fix: track "in-flight" state and coalesce.

- [WARNING] `packages/server/src/services/git-export.ts:340-357` — `fire()` is `void`-returned from `setTimeout`, so any throw escapes as an unhandled promise rejection. `runGitExport` itself never throws (it catches everything), but `loadGitExportConfig(db)` can — if the DB is closed or locked, node crashes the process. Wrap `fire` in try/catch.

- [WARNING] `packages/server/src/services/git-export-runner.ts:132-148` — `commit` uses `--allow-empty-message`. Combined with `buildCommitMessage([], ...)` producing a stub-with-no-bullets, an operator-forced export with an empty plan would create a commit with garbage message. Current flow prevents this (noop branch above) but this is a latent footgun when `force=true` and a plan has zero entries.

- [WARNING] `packages/server/src/services/git-export-runner.ts:149-151` — `push` always uses `--set-upstream`. Subsequent pushes do not need `-u` and the flag is harmless, but first-push error handling is missing: if the remote already has divergent history (bare remote seeded by someone else), the push fails and we lose it to the `phase:"push"` branch. No `--force-with-lease` semantics, no conflict detection — plan §5 should state "we own the remote; non-fast-forward = hard failure". Add `@lore`.

- [WARNING] `packages/server/src/services/git-export.ts:280` — `diff()` is called **even when the plan was empty** (no entries → `writePlanToDisk` wrote nothing → `add -A` stages only pre-existing drift in the working tree). If someone has edited `repoPath` manually (AC scenario: "uncommitted changes in the target repo from a human edit"), those human edits will get committed under the bot's identity with the bot's "export" message. That is silent theft of human work into a machine-authored commit. Fix: before `add`, run `git status --porcelain` and bail if there are unstaged modifications to paths **not** in the plan.

- [WARNING] `packages/server/src/routes/git-export-routes.ts:89-107` — `POST /run` does not enforce a timeout. A hung `git push` against a slow remote (30s timeout per spawn, but multiple calls accumulate) will hold the HTTP connection. Combined with the global mutex, two `POST /run` calls queue but each request blocks its own Hono handler for the full duration. No `AbortSignal` plumbed.

- [WARNING] `packages/server/src/routes/git-export-routes.ts:74-83` — `repoPath` validation via `sanitizeRepoPath` runs **only on PATCH**. If an operator seeds the `git_export.repo_path` row directly (migrations, CLI, bypass), the orchestrator trusts it. `runGitExport` should re-validate at load-time — defense in depth.

- [WARNING] `packages/server/src/__tests__/git-export.test.ts:481-522` — The "concurrent calls serialize" test is **tautological on the strict AC**. It asserts `[a.status, b.status]).toContain("committed")` — only one of the two must be committed; the other could be anything. Then it checks add/commit interleaving. But with the current implementation, run A writes the only pending entry and run B's `writePlanToDisk` finds every file byte-equal → `filesChanged=[]` → `add -A` → `diff --quiet` on an unchanged worktree → **B should return noop, not commit**. Yet the test FakeRunner returns `diffClean: false` (default) so diff always says dirty → B commits an empty-delta commit. This is exactly the scenario Fix [CRITICAL] above describes: the test passes for the wrong reason.

- [WARNING] `packages/server/src/__tests__/git-export.test.ts:410-416` — "noop" test uses `diffClean: true` to force the branch, but does **not seed any knowledge**. It cannot distinguish "orchestrator saw no plan entries and early-returned" from "orchestrator wrote entries but diff said clean" because both paths land on the same return value. Add a variant with seeded items and `diffClean: true` to prove the logic order.

- [WARNING] `packages/server/src/__tests__/git-export.test.ts:427-430` — `expect(runner.calls.some((c) => c.cmd === "add"))` asserts presence but not shape. The `add` API takes `paths` — current implementation passes `[]` (meaning `-A`). A regression that passes only `filesChanged` (empty) would still "add" (no-op) and every subsequent test about commit messages would still pass. Assert `paths.length === 0` and that `add` comes before `commit` in call order.

- [WARNING] `packages/server/src/__tests__/git-export.test.ts:459-469` — Push-fails test asserts `phase === "push"` but does **not assert `writeLastExport` was called with the commit sha** nor that the local commit call happened. The finding above notes that this code path writes `last_export_at` on push failure — that behavior is not locked down by a test, so a future refactor that "fixes" it would silently break observable state.

- [OBSERVATION] `packages/server/src/__tests__/git-export-routes.test.ts:268-284` — "returns a GitExportResult shape when disabled" asserts `body.status === "disabled"` and `runner.calls.length === 0`. That's good. But the file never exercises the `phase:"init"` error path, `phase:"write"` error path, or concurrent POST /run. Route coverage is shallow relative to the contract.

- [OBSERVATION] `packages/server/src/__tests__/git-export.integration.test.ts` — No test covers: (a) detached HEAD in an existing repo, (b) uncommitted human changes in `repoPath`, (c) pre-existing files at the target path not managed by the exporter, (d) push to an unreachable remote (file://`non-existent`.git), (e) write failure (readonly dir). These were explicitly flagged in the review brief and are not in the suite.

- [OBSERVATION] `packages/server/src/services/git-export.ts:96-127` — `mapRowToEntry` silently drops L2 items with empty `scopeId`. Silent drops during export are audit-invisible: the operator sees a commit with N items but has no way to know "you have 3 other items we skipped". Log a warning per dropped row, or emit a metric.

- [OBSERVATION] `packages/server/src/services/git-export.ts:123` — For L4 items, `scopeId` in the entry is forced to `"factory"` when null. The commit-message `[factory]` label is thus ambiguous between "factory-level item" and "item with scopeId='factory'". Minor.

- [OBSERVATION] `packages/server/src/services/git-export-config.ts:15-20` — `GIT_EXPORT_CONFIG_DEFAULTS` omits `enabled` and `repoPath` on purpose. This split (some defaults, some sentinels) is non-obvious; `readGitExportConfig` returns `repoPath: ""` which is then pattern-matched as sentinel. Prefer `null` + `Option` types.

- [OBSERVATION] `packages/server/src/services/git-export.ts:62-68` — `GitExportResult` union is fine but `phase` is untyped free string in the error case relative to the caller. Route consumers have no discriminated access to `phase`. This is a DX wart, not a bug.

- [OBSERVATION] `packages/server/src/services/git-export-runner.ts:68-72` — Env sets `GIT_ASKPASS=/bin/true`. On Windows hosts this path does not exist. If this code ever runs on Windows the spawn still works (env var just isn't resolvable) but the intent is Linux/Mac-specific. `@lore` this.

- [OBSERVATION] `packages/server/src/services/git-export.ts:318-323` — The `@lore` comment claims "last pending export is dropped" on restart and calls the upgrade path "a persistent outbox row" — but the acceptance criteria require that human edits to L4 PRINCIPLES DO produce an exported commit. A restart in the middle of a 2-second debounce loses that export silently. Either shorten the debounce to near-zero or add a startup reconciliation pass that runs an export unconditionally once the app is healthy.

- [OBSERVATION] Missing `@lore` where decisions are non-obvious:
  - `git-export.ts:218-219` — "pre-write pruning: skip byte-equal entries". Non-obvious given we also then rely on `diff --quiet HEAD` below. Add `@lore` explaining why pruning exists (avoids touching mtime unnecessarily) and why the second check is still needed.
  - `git-export.ts:123` — The L4 scopeId defaulting to "factory" in the ExportPlanEntry. Visible in commit message output; reader will not know the difference.
  - `git-export-routes.ts:74-83` — Why sanitizeRepoPath only runs on PATCH and not on /run.
  - `git-export-runner.ts:149-151` — Why `--set-upstream` every time.
  - `git-export-config.ts:74-83` — The three-valued "enabled/disabled/null" return contract. Documented in the JSDoc but a `@lore` would help tooling.

### OK

- `buildCommitMessage` structure matches AC2 for the non-empty-entries case.
- `computeExportPlan` correctly filters archived rows and non-exported layers, and is covered by AC4's byte-exact unit test at `git-export.test.ts:387-392`.
- `sanitizeRepoPath` rejects `..` segments and relative paths (covered at `git-export-routes.test.ts:204-222`).
- The GitRunner interface is narrow and whitelisted; argv is never user-supplied string concat. The `GIT_TERMINAL_PROMPT=0` env lockdown is the correct call.
- Auth is enforced on all four routes (`git-export-routes.test.ts:149, 262, 378`).
- `force:true` override for initial setup is correctly wired (`git-export-routes.test.ts:299-364`).
- The integration test at `git-export.integration.test.ts:173-192` is a real end-to-end proof of AC1 (with the caveat that it bypasses the event handler and calls `runGitExport` directly).
- AC5 parametrization (branch + repoPath + remoteUrl) is proven at `git-export.integration.test.ts:235-253`.
- Unicode/large-body byte-exact roundtrip is proven at `git-export.integration.test.ts:255-286`.

---

### Verdict

**STOP.** Three CRITICAL findings block shipping:

1. Event-triggered export is dead in production (`app.ts:80` passes no runner → handler always no-ops). AC1 is not met in the integrated system, only in the unit-test-with-fakes.
2. Deletions and archived items are never removed from the exported repo. AC4 is violated the moment any item is archived or renamed — the exported tree diverges from DB truth.
3. Newly-added files after the first commit may be classified as "no-op" because `git diff --quiet HEAD` interaction with staged-new files is relied on implicitly and not asserted by any test.

Additionally the test suite contains at least one tautological pass (`concurrent calls serialize`) and is missing the failure-mode tests called out in the brief (push to unreachable remote over the integration harness, write failure, uncommitted human changes in target repo, detached HEAD, scopeId/topic path injection). Fix the three CRITICAL items, add the missing failure-path tests, and re-review.
