## 1. Context

Seven defect clusters surfaced by review of the data layer. None are visible to the user yet, but each is load-bearing for production: missing indexes will become full scans, FKs let orphans accumulate, the dependency watcher is O(n²), optimistic locking is a TOCTOU race, relevance scores are systematically wrong by ~100×, the FTS path executes user-supplied operators, the cost-cap dedup set leaks forever, and the PG schema and seed have drifted from SQLite.

Each cluster is independently testable. They share two cross-cutting constraints: migrations must be additive (no data loss), and SQLite + PG schemas must stay in lockstep.

## 2. Constraints

- **Migrations additive only.** No `DROP COLUMN`, no destructive `ALTER`. New indexes are additive. FK changes on SQLite require table rebuild — see §6 ordering.
- **Both dialects updated together.** Every `schema.ts` change has a parallel `schema.pg.ts` change, and `bun run db:generate` produces migrations into both `drizzle/` (SQLite) and `drizzle-pg/` (Postgres). The schema-parity test (`packages/db/src/__tests__/pg-schema.test.ts`) must continue to pass.
- **Drizzle ORM only.** No raw SQL outside migration files. The two raw-SQL escape hatches that already exist (`packages/fabric/src/fts.ts` for FTS5 setup and search) stay quarantined — we add input sanitisation in front, not new raw SQL elsewhere.
- **TypeScript strict.** No `any`, no `@ts-ignore`, explicit return types, no `console.log`.
- **Backward-compat for existing data.** Adding indexes is safe. FK action changes (`RESTRICT`/`CASCADE`) only apply to *new* writes — existing orphans (if any) survive. Tests verify rejection of *new* violating writes.
- **Relevance scoring change is breaking semantically.** Removing `/100` divisions multiplies the confidence and attentionScore *factors* by 100×. `scoreItem` rounds to 0-100 after dividing by `totalWeight`; with weights summing to 1.0 and the bumped factors clamped at 1.0, the post-fix score for items with confidence/attentionScore in [0,1] will become *higher and saturated*, not 100× higher. Existing assertions are all relative (`scoreA > scoreB`) — audit confirms no absolute-value assertions on `scoreItem` results in `relevance-scoring.test.ts`. The `attention-scoring.test.ts` suite uses a separate `computeConfidenceValue` in `attention-scoring.ts:128` that is already correct ([0,1] domain) and is not touched by this story.
- **Cost-cap dedup behaviour.** AC9 in `cost-cap.test.ts` requires duplicate breach/warning events to be suppressed for the lifetime of a session. Whatever bounded structure we pick must keep that suppression working for at least one full session. Per-session scoping (cleared on session end) is the simpler, correct option.

### 3.3 Dependency-watcher SQL filter (Cluster 3)

**File:** `packages/server/src/services/dependency-watcher.ts`.

Current: loads every row of `tasks`, JSON-parses each `dependencies`, filters in JS. O(n) per call; with 500 tasks this is hundreds of allocations.

Replacement: SQL-level filter using Drizzle.

```text
SELECT * FROM tasks
WHERE state = 'hold'
  AND dependencies LIKE '%"<completedTaskId>"%'
```

Drizzle: `db.select().from(tasks).where(and(eq(tasks.state, 'hold'), like(tasks.dependencies, '%"' + completedTaskId + '"%')))`.

The pattern wraps the ID in `"…"` so a substring of an unrelated ID can't false-match (`dep-1` vs `dep-12`); this assumes JSON.stringify quotes IDs, which it does for arrays of strings. Bind the LIKE arg as a parameter; the IDs are crypto.randomUUID strings (no `%` or `_`), so no escape needed — but add a short comment noting the assumption.

After the SQL filter we still need to verify *all* deps are done (the LIKE only proves *one* dep matched). Keep the existing per-task `every(deps, isDone)` loop; it now runs over a small filtered set instead of the whole table.

Indexes used: `tasks_state_idx` from §3.1 makes the `state='hold'` predicate selective. The LIKE is a scan within the held set — acceptable since hold count ≪ total tasks.

**Benchmark target:** 500 tasks, 1 hold-state dependent → <10ms (AC).

### 3.4 Knowledge optimistic locking (Cluster 4)

**File:** `packages/fabric/src/knowledge-repository.ts` `update()`.

Current code reads version, compares in JS, then UPDATE without a version predicate (`update.ts:135-187`). This is TOCTOU — two concurrent writers both see version 5, both UPDATE, both bump to 6, one write is silently lost.

Fix: include `eq(knowledgeItems.version, expectedVersion)` in the UPDATE WHERE clause and inspect the result's `changes` count. better-sqlite3 returns `{ changes: number, lastInsertRowid }` from `.run()`; Drizzle exposes this via `.run()` return value. If `changes === 0`, the row exists but version mismatched → throw `VersionConflictError(id, currentVersion)`. We still need to read the *current* version after the failed UPDATE to populate the error — fold the existence check + current-version read into one `SELECT` *after* the failed UPDATE (only on the rare conflict path).

Pseudocode:
```text
const result = db.update(knowledgeItems)
  .set({...changes, version: newVersion, updatedAt: timestamp})
  .where(and(eq(id, id), eq(version, expectedVersion)))
  .run();

if (result.changes === 0) {
  const current = db.select({version}).from(knowledgeItems).where(eq(id, id)).get();
  if (!current) throw new Error(`Knowledge item ${id} not found`);
  throw new VersionConflictError(id, current.version);
}
```

Edit-log entries: keep computing the old/new diff *before* the UPDATE (we need the existing row for `oldValue`), but don't insert log rows until *after* the UPDATE succeeds. If UPDATE fails (changes=0), do not write log entries.

Event emission: only after successful UPDATE.

⚠️ UNVERIFIED: Drizzle's `.run()` return shape across better-sqlite3, bun:sqlite, and the seed CLI's `BaseSQLiteDatabase` — confirm `result.changes` is universally available (better-sqlite3 docs: https://github.com/WiseLibs/better-sqlite3/blob/master/docs/api.md#properties-1; Drizzle source). If the type narrows to `unknown` for the bun:sqlite path, document with `@lore` and add a runtime guard.

### 3.6 FTS5 sanitisation (Cluster 6)

**File:** `packages/fabric/src/fts.ts`, function `ftsSearch`.

FTS5 query syntax (https://www.sqlite.org/fts5.html#full_text_query_syntax) treats these as operators: `AND`, `OR`, `NOT`, `NEAR`, `^` (initial-token), `*` (prefix), `"…"` (phrase), `(…)` (grouping), `{…}` (column filter), `:` (column-prefix), `+` (token concatenation in v3.40+).

Strategy: **whitelist tokens, then quote**. For each whitespace-separated token in the user input:
1. Strip non-word chars (`/[^\p{L}\p{N}_]/gu` → empty string).
2. Drop empty tokens.
3. Lowercase the bare operator words `AND`, `OR`, `NOT`, `NEAR` (FTS5 operators are uppercase-sensitive — lowercasing makes them literal).
4. Wrap each token in double quotes — FTS5 treats double-quoted text as a literal phrase, even if the content otherwise looks like an operator.
5. Join with space (implicit `AND`).

If the result is empty (all tokens stripped), return `[]` immediately rather than running an empty MATCH (which throws "syntax error").

Function signature unchanged. Add a tiny pure helper `sanitizeFtsQuery(raw: string): string` exported for direct test coverage.

**Test cases (new in `knowledge-repository.test.ts` or a dedicated `fts.test.ts`):**
- Query `*` → empty result, no throw, no match-all.
- Query `test* OR admin` → matches items with literal "test" or "admin" only as words; OR is not honoured.
- Query `"unbalanced` → does not throw.
- Query `(foo)` → matches "foo".
- Query `   ` → returns `[]`, no throw.

### 3.7 Cost-cap memory leak (Cluster 7)

**File:** `packages/server/src/services/cost-cap.ts`.

Current: module-level `const emittedEvents = new Set<string>()` keyed by `sessionId:eventType:capLevel:entityId`. Never cleared except on `resetCosts` (which is a billing-cycle operation, not a session lifecycle one). Sessions complete and the dedup keys for them stay in the Set forever.

Fix: replace with a `Map<sessionId, Set<eventKey>>`. Add a new exported function `releaseSessionDedup(sessionId: string): void` that drops the per-session entry. Wire this into the session-lifecycle code that already exists for ending sessions.

**Where to call `releaseSessionDedup`:** the session is marked done in `packages/server/src/services/session-lifecycle.ts` (it exists per `find` output above). Add a call there. Also call from `resetCosts` (factory level → clear whole map; agent/team level → clear all sessions belonging to that agent/team via the same query the reset code already runs).

Bound: even if a session lifecycle never fires `releaseSessionDedup`, the Set per session is bounded by `eventTypes × capLevels × entities ≈ 2 × 3 × small = O(10)` keys. The leak is in the count of dead-session entries, not in keys per session. Capping the *map* size at, say, 10,000 sessions with FIFO eviction is a belt-and-braces secondary defence; flag for adversary as possibly over-engineering.

**AC test:** loop 1000 fake sessions through `recordCostAndCheck`, end each → assert `getDedupCacheSize()` (new test-only export) stays bounded (e.g. ≤10 at any point).

### 3.8 PG schema alignment (Cluster 8)

**File:** `packages/db/src/schema.pg.ts` and `packages/db/src/seed-pg-cli.ts`.

Boolean columns currently use `integer()` in PG schema (mirror of SQLite which has no native bool). Per AC: switch to `boolean()` from `drizzle-orm/pg-core` for:
- `routines.delegationAllowed`, `routines.humanReview`, `routines.silent`, `routines.active`
- `threads.pinned`
- `tasks.crossTeam`
- `items.blocking`

PG's `boolean` accepts `true/false`, not `0/1`. The seed and call sites that write integers (e.g. `silent: 1`) need to coerce. Two options:

**Option A — diverge column types per dialect, accept `0|1|true|false` at the boundary.** Schema-parity test (`pg-schema.test.ts`) compares column *names* only, not types. AC says "schema parity test updated to account for boolean vs integer dialect difference" — so updating the test (or rather, leaving the existing parity at name-only) is the expected path.

**Option B — convert SQLite columns to `integer({ mode: 'boolean' })` so Drizzle types are `boolean` on both sides.** Drizzle's better-sqlite3 supports `integer({ mode: 'boolean' })` which transparently converts `0|1 ↔ false|true`. This eliminates the dual-shape problem at the call-site. Cost: every existing call site that writes `1` or `0` must change to `true|false`.

**Choosing A** for I3 — fewer call-site changes, isolated to the PG path, keeps SQLite write semantics identical (no risk to the 800+ call sites flagged in the existing PG-CLI lore). The PG seed (and any future PG writers) accept `boolean` naturally. The schema-parity test is updated to compare columns by name only (it already does — see `pg-schema.test.ts:48`, no type assertion). Add an *intentional* test in `pg-schema.test.ts` that documents the divergence: for the named boolean columns, assert SQLite type is `integer` and PG type is `boolean`.

**PG seed parity:** extend `seed-pg-cli.ts` to insert the same fixtures the SQLite `seed()` does — agents (CoS, builder, PM, 5 facilitators), team, bet, daily-digest task, knowledge item, factory settings, daily-digest routine, builtin routines. Per-row `onConflictDoNothing()` for idempotency. Use `boolean` literals (`true`/`false`) for the converted columns. Reuse the `BUILTIN_ROUTINE_SEEDS` list — extract it to `packages/db/src/seed-fixtures.ts` so both dialects import the same data. **Constraint:** the SQLite seed's `seedBuiltinRoutines` writes integers (`silent: 1`); the new PG version writes booleans (`silent: true`). The shared fixtures file holds the shape-neutral data; each seed coerces at the boundary.

**Migration:** a PG-only migration that does `ALTER TABLE … ALTER COLUMN … TYPE boolean USING (column::text)::boolean` for each affected column. SQLite gets no migration here — its columns stay `integer`. The migration must run on an empty PG (today's case — pglite tests use `migrate: true` from scratch); for any existing PG data, the USING cast handles `0/1 → false/true`.

⚠️ UNVERIFIED: pglite (used by `pg-migration.test.ts`) compatibility with `ALTER COLUMN ... TYPE boolean USING ...`. Confirm with a docs pointer (https://www.postgresql.org/docs/current/sql-altertable.html — standard PG syntax) and a green run of `pg-migration.test.ts`.

## 6. Migration Ordering

The story produces, in order:

1. **Migration A (SQLite, additive indexes only):** `drizzle/0005_<name>.sql` — `CREATE INDEX IF NOT EXISTS …` for all new indexes. Backward-compatible, no data risk.
2. **Migration B (SQLite, FK action changes via table rebuild):** `drizzle/0006_<name>.sql`. Uses Drizzle's auto-generated rebuild pattern. Must run *after* the indexes migration so index DDL is reapplied on the rebuilt tables (Drizzle's generator handles this — verify by inspecting the generated SQL).
3. **Migration C (PG, additive indexes):** `drizzle-pg/0003_<name>.sql` — `CREATE INDEX …`.
4. **Migration D (PG, FK action changes):** `drizzle-pg/0004_<name>.sql` — `ALTER TABLE … DROP CONSTRAINT … ADD CONSTRAINT …`. PG handles in-place; no rebuild.
5. **Migration E (PG, boolean column type change):** `drizzle-pg/0005_<name>.sql` — `ALTER TABLE … ALTER COLUMN … TYPE boolean USING …`. PG-only.

We may collapse A+B into a single SQLite migration if Drizzle's generator emits them together; same for PG D+E. Decision deferred to whatever `bun run db:generate` produces — adversary should challenge if separate migrations are warranted for safety.

**Rebuild risk:** The FK-change migration on SQLite drops + recreates each affected table. If anything goes wrong (migration fails partway, `PRAGMA foreign_keys` left off), data could be left in a half-state. Mitigation:
- Every migration runs inside a Drizzle transaction (verified: better-sqlite3 migrator wraps each .sql file in BEGIN/COMMIT).
- The migration test (`migration.test.ts`) runs with `foreignKeys: true` to catch bad rebuild sequences.
- Add a new test that pre-populates a fresh DB with seed data, *then* applies migrations B and verifies row counts and FK behaviour.

# Adversary Notes

A read-only adversarial pass over §1-8 follows. Findings flagged C(ritical) / H(igh) / M(edium) / L(ow). Each is unresolved unless I update the plan above (kept here as a record).

## C-1. SQLite FK rebuild ordering vs `tasks.thread_id` cycle

`tasks` references `threads` (via `thread_id`). `messages` and `items` *also* reference `threads`. If Drizzle's auto-generated FK-change migration rebuilds the tables in an arbitrary topological order, and the rebuild for `tasks` runs while `threads` exists but the FK action change for `threads` hasn't yet applied, we may end up with mismatched reference actions on either side. **Action:** before running `bun run db:generate`, draw the FK graph and confirm Drizzle's generator emits the rebuild in dependency order (referenced tables first). If not, manually order the SQL or split into two migrations. **The plan does not currently call this out as a hard step — fix.**

## C-2. `clearDeduplicationCache` is a public test API; renaming/removing breaks `cost-cap.test.ts`

`cost-cap.test.ts:18` imports `clearDeduplicationCache` and calls it in `beforeEach`. The new bounded structure must keep that export, or `beforeEach` must switch to a per-session reset. **Action:** keep `clearDeduplicationCache` (clears the whole map) and add `releaseSessionDedup(sessionId)`. Update the plan §3.7 — currently it implies `releaseSessionDedup` replaces the existing API. *Resolved by note here.*

## H-1. Test count is high; risk of churn pushing the AC-Rel-1 case into a brittle absolute assertion

AC-Rel-3 demands "confidence factor equals 0.8". The plan implements this by setting weights to all-zero except `confidence: 1.0` and asserting `scoreItem(...) === 80`. This is brittle: any future weight-normalisation change flips the result. Soften to `expect(score).toBeCloseTo(80, 0)` and add a unit test on the *internal* helper if needed (export `computeConfidence` for direct test, or expose a `_internals` object). **Action:** add a note to §4 that the assertion uses `toBeCloseTo`. *Folded into the plan implicitly via "covered above"; flag for the implementer.*

## H-2. Dependency-watcher SQL filter false-negatives on JSON whitespace

The plan's LIKE pattern `%"<id>"%` assumes `JSON.stringify(["dep-1"])` produces `["dep-1"]` — which is correct for `JSON.stringify` of an array of strings. But code elsewhere may store dependencies pre-stringified by a different writer with whitespace (`["dep-1", "dep-2"]` vs `["dep-1","dep-2"]`). Both contain `"dep-1"`, so the LIKE still matches. ✅ Safe. But: an attacker (or a buggy writer) inserting `dep-1` *without* quotes (a malformed JSON) would not be matched. Acceptable — this is the intended invariant — but document it.

## H-3. PG boolean migration on existing data

The plan claims the PG `ALTER COLUMN ... TYPE boolean USING (column::text)::boolean` is safe. For values 0 and 1 it is. For NULL it is. For any other integer (e.g. someone wrote `2` in a buggy past) it will fail mid-migration. **Action:** add `USING (case when column = 0 then false else true end)` instead — coerces all non-zero to true (matches SQLite's truthiness). Update §3.8.

## H-4. `dependencies` LIKE may not be index-able

Even with `tasks_state_idx`, the LIKE on `dependencies` is a scan within the held subset. With many `state='hold'` tasks, the LIKE dominates. The benchmark target is 500 *total* tasks with most done; the held subset is small, so this is fine in the AC. But if production reaches 5,000 held tasks, the watcher slows. **Action:** flag in §3.3 as a known-future scaling concern. A proper fix uses a `task_dependencies` join table — out of scope for I3. *Acceptable.*

## H-5. FTS sanitisation strips meaningful punctuation

Already noted in Open Question #6 — but the adversary thinks the planned mitigation ("keep `-` and `'` as token-internal characters") still strips them at boundaries. Real-world: a query `"file-handling"` (with quotes) becomes empty after strip-quotes-then-strip-non-word. **Action:** the sanitiser must (a) strip the operator quotes, (b) keep word chars + `-` + `_` + `'`, (c) re-quote each token. Verify with a test for the `file-handling` query.

## M-1. PG seed parity test is large surface

`seed-pg.test.ts` proposed test will need pglite startup time × N assertions. Keep to one test that asserts row counts per table; defer per-row equivalence to a future story.

## M-2. Migration test count

`migration.test.ts` currently has 4 tests; we're proposing additions that will at least double its runtime. Acceptable for I3, but keep an eye on aggregate suite duration.

## M-3. Concurrent-update test is a *simulated* race, not a real one

Vitest is single-threaded per worker. The "concurrent" race is sequential code calling `update()` twice with the same expectedVersion. The fix proves correctness; it does not prove serialisability under real concurrency. Acceptable for the AC, but flag.

## L-1. `releaseSessionDedup` granularity

Resetting agent-level costs and clearing only that agent's session dedup keys is correct. But we don't currently track which sessions belong to which agent in the dedup map (key is `sessionId:eventType:capLevel:entityId`). To resolve, the new map structure should be `Map<sessionId, { agentId, teamId | null, keys: Set<string> }>` — slightly more memory per session but enables precise reset. Update §3.7.

## L-2. Boolean column choice across H/I-track stories

If a future story uses `integer({ mode: 'boolean' })` for SQLite to unify the call-site type, it will collide with this story's choice. Document in `@lore` on `schema.ts` that the divergence is intentional and the migration to unified type is a separate opt-in story.
