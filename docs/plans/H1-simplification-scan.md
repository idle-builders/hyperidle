# H1 Simplification Scan

Scope: `packages/server/src/services/git-export.ts`, `git-export-runner.ts`, `git-export-config.ts`, `packages/server/src/routes/git-export-routes.ts`, and H1-related lines in `packages/server/src/app.ts`.

Mode: read-only. Findings only.

### Findings

- [major] `git-export.ts:226-253` — `AsyncFsAdapter` interface and `createNodeAsyncFsAdapter()` factory have zero consumers in-repo. The implementer already flagged this. The comment "unused by H1 but exported for future adapters" is YAGNI masquerading as forward planning — Delete both the interface and the factory. If a future story needs async fs, it can be added then.
- [major] `git-export-runner.ts:35-38` — `status(): string` and `log(opts: Record<string, unknown>): string` on `GitRunner` are never called by the orchestrator, by routes, or by tests-of-record (they exist purely to mirror git). Delete both methods from the interface and the implementation. The `Record<string, unknown>` parameter on `log` is itself a smell (untyped pass-through) — another reason to remove.
- [major] `git-export-runner.ts:40-45` — `fetch()`, `resetHard()`, and `revParseHead()` are declared on `GitRunner` but `ensureRepo()` in git-export.ts never fetches or resets. The plan §3.11 described fetch+reset on first run, but the implementation in `ensureRepo` (git-export.ts:290-313) skipped that branch entirely. Either wire the first-run clone semantics in (plan compliance) or drop the three methods. As currently shipped they're dead code.
- [major] `git-export-runner.ts:29-31` — `symbolicRefHead()` and `remoteV()` have no callers in production code. If only used by tests to assert git state, they should live in the test harness, not on the production interface. Remove from `GitRunner`; have tests spawn git directly or expose a separate `GitInspector` only in tests.
- [major] `git-export.ts:60-67` + `git-export.ts:212-223` — `FsAdapter` exists primarily as a test seam. With 4 synchronous methods against `node:fs`, it pulls its weight only if tests actually swap it. Confirm a `createMemFs` exists in the test file before keeping — if tests use a tmpdir instead, delete the adapter and call `nodeFs` directly from `writePlanToDisk` / `ensureRepo`. (The comment at line 61 references `createMemFs` in `git-export.test.ts`, so this is likely justified — but verify. If memFs exists this finding is a nit.)
- [major] `git-export.ts:20-22` — Re-export barrel at the top of the orchestrator file re-exports `GitExportConfig`, `loadGitExportConfig`, `readGitExportConfig`, `updateGitExportConfig`, `sanitizeRepoPath`, `writeLastExport`, and `GitRunner` from sibling modules. Callers (the route file) import the functions directly from `git-export-config.js` and `git-export-runner.js` (routes lines 7-19). These re-exports are dead — delete them. TypeScript rules also forbid barrel files except `packages/*/src/index.ts`.
- [major] `git-export.ts:122-132` — Local `KnowledgeRow` interface duplicates the Drizzle row shape. `db.select().from(knowledgeItems).all()` already returns a strongly-typed row — just pass it straight into `mapRowToEntry`. Delete the interface and the field-by-field copy at lines 187-197.
- [major] `git-export-config.ts:86-100` — `readGitExportConfig` duplicates 80% of `loadGitExportConfig`. Two functions that diverge only on "treat enabled as gate vs. ignore enabled" invite drift. Collapse into one: `loadGitExportConfig(db, { includeDisabled?: boolean })`, or better, always return the shape and let the caller check `.enabled`.
- [major] `git-export-config.ts:157-173` — `getLastExportAt` and `getLastCommitSha` each do their own single-row SELECT. Both are called together in routes `/status` (git-export-routes.ts:97-98). Either fold into a single `getLastExport(db): { at: string|null; sha: string|null }` or have callers read from `readGitExportConfig` (if the shape were extended). Two near-identical one-liners are over-factoring.
- [major] `git-export-routes.ts:40-45` + `git-export-routes.ts:53-54` — `CreateGitExportRoutesOptions` exists but has no caller passing options. `app.ts:77` calls `createGitExportRoutes(options.db, eventBus)` with no third argument. Tests might use it, but if not, delete the options object and inline `createGitRunner` / `createNodeFsAdapter`. If tests do use it, fine — keep but verify.
- [major] `git-export-routes.ts:49` — `_eventBus: EventBus` parameter is unused (leading underscore concedes this). If it has no purpose, remove it from the signature and from the call site in app.ts. Carrying an unused bus parameter "because we might need it" is premature API design.
- [major] `git-export.ts:438-446` — `RegisterGitExportHandlerOptions` exposes `runner`, `fs`, `createRunnerFor`, `debounceMs`, `now`, `logger`. `app.ts:80` passes none of them. This is a 6-field options bag for a call site that passes zero options. Collapse to what tests actually inject; the rest is speculative surface.
- [major] `git-export-routes.ts:81` — `createRunner(cfg.repoPath || "/tmp")` silently falls back to `/tmp` when repoPath is unset. The orchestrator then returns `{status:"disabled"}` or `{status:"error", phase:"init"}` anyway. The `"/tmp"` default is a code smell that makes the runner initialization look safe when it's not — either fail fast with a 400 when `repoPath` is empty, or rely on `runGitExport` to handle the empty-path case without creating a bogus runner against `/tmp`.
- [minor] `git-export.ts:96-98` — `normalizeKind` is a one-liner wrapping `String.prototype.toUpperCase`. Two usages. Consider inlining `.toUpperCase()` at call sites; the helper adds a name to look up without saving keystrokes.
- [minor] `git-export.ts:100-102` — `scopeLabel` is a one-liner used once (in `buildCommitMessage`). Inline.
- [minor] `git-export.ts:167-176` — `compareEntries` has three tuple-break comparisons. Consider `sort((a,b) => a.relPath.localeCompare(b.relPath))` if `relPath` alone is sufficient (layer+scope+kind are encoded in the path). Likely equivalent for stability; simpler code.
- [minor] `git-export.ts:268-280` — `queueMutex` hand-rolls a promise chain with manual `release` assignment and a `() => {}` placeholder. Works, but `async` + a simple `let queue = Promise.resolve(); queue = queue.then(fn, fn)` achieves the same thing in ~3 lines without the placeholder dance. Readability win.
- [minor] `git-export.ts:319-341` — `writePlanToDisk` silently swallows read errors (`catch { prior = null }`) so a transient filesystem error masquerades as "no prior content, write it." Log the swallowed error at debug, or at least document why it's being eaten.
- [minor] `git-export-runner.ts:156-177` — Inline `.then()` on the commit spawn result, inside an `async` function. Mixing `.then()` and `await` in one function is a tell of incremental refactoring; rewrite as `const r = await spawnGit(...); if (r.exitCode !== 0) throw ...`.
- [minor] `git-export-runner.ts:147-150` — `add(paths)` branches on `paths.length === 0` to pick between `-A` and `-- <paths>`. The orchestrator only ever calls `add([])` (git-export.ts:395). The non-empty branch is dead. Either simplify the signature to `add(): Promise<void>` hard-coded to `-A`, or keep the branch and add a test that exercises it.
  DEFERRED: Changing the GitRunner interface signature ripples through every FakeGitRunner + test in scope; the non-empty branch is narrow and future-friendly. Low value vs. change footprint.
- [minor] `git-export-routes.ts:61` + `:79` — `c.req.valid("json" as never) as z.infer<typeof schema>` uses `as never` twice. This is the project's validate-middleware pattern, but the double-cast is a type-safety hole that every route file inherits. If this pattern is shared across routes, it's a codebase-level simplification, not a local one — flag for the middleware author.
  ADDRESSED: Routes now call `zValidator("json", schema, validationErrorHandler)` directly with a typed handler, so `c.req.valid("json")` returns `z.infer<schema>` without casts.
- [minor] `git-export-config.ts:179-193` — `sanitizeRepoPath` returns a discriminated union `{ok:true,value} | {ok:false,reason}` but the only caller (routes line 64) throws away `.value` and re-uses the raw input from the body. The `value` field is dead — either drop it (return `{ok:true} | {ok:false,reason}`) or have the caller use it.
- [minor] `git-export-config.ts:195` — `export const GIT_EXPORT_SETTING_KEYS = KEYS` re-exports the internal `KEYS` const with a different name. No external caller imports `GIT_EXPORT_SETTING_KEYS`. Delete.
- [minor] `git-export.ts:107-120` — `buildCommitMessage` takes `_now: Date` (prefixed underscore = unused). The plan's example message doesn't include a timestamp — the parameter is dead. Delete it from the signature and the RunGitExport call site (git-export.ts:407).
- [nit] `git-export.ts:258-280` — `exportMutex` is a module-level mutable. Correct for the design but makes the module non-reentrant across test instances. If tests share the module, concurrent test cases serialize globally. Acceptable given @lore comment; note for test isolation.
  DEFERRED: Intentional per @lore (single-process guarantee). Fixing requires API change (pass mutex through deps) with no benefit to current callers.
- [nit] `git-export-runner.ts:58-62` — `SpawnResult` interface duplicates the basic shape of Node's `ChildProcess` exit data. Could be a type alias but interface is fine.
  DEFERRED: Finding concedes `interface is fine`.
- [nit] `git-export.ts:39` — `EXPORTED_LAYERS` is a `Set<string>` of size 2. For a 2-element membership check, `(row.layer === "L2" || row.layer === "L4")` is clearer and narrows the type.

### Summary

Strongest smells: (1) `AsyncFsAdapter` is dead code the implementer already called out — delete it; (2) `GitRunner` has ~5 methods that are never called by production code (`status`, `log`, `fetch`, `resetHard`, `revParseHead`, and arguably `symbolicRefHead` + `remoteV`) — most traceable to plan §3.11 first-run-clone semantics that never got wired; (3) top-of-file re-export barrel in `git-export.ts` violates the no-barrel rule and has no consumers; (4) `readGitExportConfig` vs. `loadGitExportConfig` duplicate logic that will drift; (5) several options-bag interfaces (`CreateGitExportRoutesOptions`, `RegisterGitExportHandlerOptions`) have zero production callers passing options. Collectively, removing these would cut ~80-100 lines without behavior change.
