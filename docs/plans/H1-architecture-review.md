# H1 Architecture Review

Scope: `git-export.ts`, `git-export-runner.ts`, `git-export-config.ts`, `git-export-routes.ts`, `app.ts` (H1 wiring only). Read-only. Measured against `docs/ARCHITECTURE.md`, `docs/KNOWLEDGE_ARCHITECTURE.md`, `docs/work-packages/TRACK-H.md` §H1, and `docs/plans/H1-plan.md`.

---

### Findings

- [critical] `packages/server/src/app.ts:80` — `registerGitExportHandler(options.db, eventBus)` is called with no `runner` / `fs` options, and `registerGitExportHandler`'s `fire()` at `git-export.ts:345–349` hard-returns with `logger.warn("no runner available for event-triggered export")` when `opts.runner` is undefined. Net effect: in production, the event-triggered path (AC1 — "Human edit to L4 PRINCIPLES -> Git export runs, commits new PRINCIPLES.md") never actually runs. Only the manual `POST /api/git-export/run` path exports. — Fix: wire a runner factory into the handler that instantiates `createGitRunner(cfg.repoPath)` at fire time (so config changes are honoured), not at boot. Signature change: `RegisterGitExportHandlerOptions.runnerFactory?: (repoPath: string) => GitRunner` with a default of `createGitRunner`; inside `fire()` build the runner lazily after `loadGitExportConfig(db)` succeeds. Unit test with FakeGitRunner factory; integration test asserts AC1 end-to-end via the event bus, not via a direct `runGitExport` call.

- [high] `packages/server/src/app.ts:78–80` — the three `register*` calls discard their returned unsubscribe functions. Siblings (`registerPolicyEngine`, `registerSessionReviewCreator`, `registerGitExportHandler`) all return `() => void` by design for test teardown and graceful shutdown, but `createApp()` throws them away. Each call to `createApp({db, eventBus})` in tests (and in prod if the app is ever torn down) permanently leaks handlers onto the shared `eventBus`. Cross-test contamination risk is real: creating an app twice in the same suite fires git-export twice per event. Test file `git-export.test.ts` only works because it passes `new EventBus()` per test. — Fix: return the disposers from `createApp` (or collect into a `Disposable` bag stored on the app), mirroring the pattern already established in `session-review-creator.test.ts:72`. Document shutdown order: clear debounce timers → unsubscribe handlers → drain in-flight `runGitExport` via `exportMutex`.

- [high] `packages/server/src/services/git-export.ts:173–179` — `exportMutex` is a module-level singleton. Two `HyperIdleDb` instances in the same process (e.g. parallel integration tests or a future multi-tenant factory) serialize against each other and, worse, share fate across DBs. This also couples test isolation: a stuck call in one suite blocks the next. — Fix: move the mutex into the closure returned by a factory (e.g. `createGitExporter(db)` returns `{ run, registerHandler }` each with their own mutex), or key it by `cfg.repoPath`. A `Map<string, Promise<unknown>>` per-repo-path mutex is the minimal change.

- [high] `packages/server/src/services/git-export.ts:137–147` — `computeExportPlan` filters only `status === "archived"`, exporting every other status including `captured`, `provisional`, and `needs_human` (the pre-validation statuses from `KNOWLEDGE_ARCHITECTURE.md §9`). The L4 export is supposed to be "humans live here" — publishing `captured`/`provisional` drafts into the Git repo leaks half-baked items and contradicts the Information → Knowledge state machine. — Fix: whitelist `status IN ('validated', 'active')` (and optionally `stale` — operator choice). Add a test pinning which statuses export. Coordinate the canonical status vocabulary with G-track facilitator work; flag open question in §10.

- [high] `packages/server/src/services/git-export.ts:137–147` — `computeExportPlan` pulls `SELECT * FROM knowledge_items` (every row, every layer). The filter is client-side in JS. With a healthy L0/L1/L3 corpus (thousands of rows) this is wasteful on every event-triggered export and grows unbounded. — Fix: push the filter into the query: `where(and(inArray(knowledgeItems.layer, ['L2','L4']), inArray(knowledgeItems.kind, [...]), notEq(knowledgeItems.status, 'archived')))`. Use the `ki_layer_idx` already defined (`schema.ts:249`).

- [high] `packages/server/src/services/git-export-runner.ts:1,64` — uses `node:child_process` `spawn`, contradicting `docs/plans/H1-plan.md §7` which explicitly mandates `Bun.spawn` ("Spawn native `git` via `Bun.spawn`. Do NOT add `isomorphic-git`"). In Bun runtime `node:child_process` works but goes through the Node compat shim; production runs on Bun. Bun.spawn gives a typed exit code, a Promise-based `exited`, and native abort-signal support — the rationale the plan called out. — Fix: either (a) switch to `Bun.spawn` per plan and keep a node-compat fallback guarded by `typeof Bun !== 'undefined'`, or (b) amend the plan with the rationale for choosing `node:child_process` (Vitest-in-Node test portability is the plausible reason). Pick one and make the plan and the code agree.
  - DEFERRED: plan amended (H1-plan.md §7) to pick `node:child_process.spawn` with the Vitest-portability rationale. Code + plan now agree. `@lore` comment added to the runner pointing at the decision.

- [medium] `packages/server/src/routes/git-export-routes.ts:60–121` — diverges from sibling-route validation style. Siblings (`bets.ts`, `tasks.ts`, `sessions-routes.ts`, `knowledge.ts`) use `validateBody(schema)` from `packages/server/src/middleware/validate.ts:10`; git-export-routes re-implements a private `validationErrorHandler` inline and uses `zValidator("json", ..., handler)` directly. Same semantics, different shape — raises cognitive load and invites drift. — Fix: import `validateBody` and replace both call sites. Removes 16 lines. Matches the existing pattern.
  - FIXED: routes now use `validateBody` for both PATCH and POST. Inline helper removed.

- [medium] `packages/server/src/services/git-export-config.ts:156–169` — `sanitizeRepoPath` rejects segments containing `".."` but does not reject the path escaping the operator's intended root. "/srv/../etc/shadow" would still be rejected (it has `..`), which is correct, but `/tmp` or `/etc` are accepted. There is no allow-list root configured (e.g. `git_export.repo_root`) and no `realpath` normalization. Any operator with `X-API-Key` can point the export at any absolute path writeable by the server process. — Fix: (a) resolve `path.resolve(cfg.repoPath)` and reject if it does not start with a configured root; or (b) document explicitly in the threat model that `git_export.repo_path` is operator-trust-level input, and restrict `PATCH /config` to a distinct admin role. Today the threat model implicitly assumes operator==admin but there is no role separation in `authMiddleware`.

- [medium] `packages/server/src/services/git-export.ts:218–223` — `writePlanToDisk` writes the plan but never *removes* files for items that disappeared (archived, deleted, or re-scoped). A L2 PRINCIPLES that gets archived will remain in the repo forever, and `git diff --quiet HEAD` will still report clean because nothing changed on disk. AC says "no commit if no changes", but the architecture intent is that Git mirrors the canonical store. The plan §10 Q1 flags this as a deferred question ("Deletion semantics — v1: no `git rm`"), so it's intentional, but the code has no test pinning it and no comment anchoring the decision. — Fix: add a test asserting "archived item stays on disk in v1" (contract lock) and an `@lore` comment at `writePlanToDisk` citing plan §10 Q1. When deletion lands, this is the pivot point.

- [medium] `packages/server/src/services/git-export.ts:205–207` — uses `path.posix.join`. On Windows dev machines this produces forward-slash paths that will not match what `node:fs` returns from `existsSync`/`readFileSync`. Not a blocker (production is Linux per H4), but will fail integration tests on a Windows contributor laptop. — Fix: use `path.join` (the platform default) — forward slashes are what git consumes in commit messages anyway, and `node:fs` handles both on Win32.

- [medium] `packages/server/src/services/git-export.ts:96–127` — `mapRowToEntry` uppercases `kind` before checking `EXPORTED_KINDS`. This works (plan §3.6 CONFUSION chose case-insensitive), but the derived `relPath` always uses the upper-case form (`factory/PRINCIPLES.md`). If a later facilitator writes `kind='Principles'`, the exported filename will be `PRINCIPLES.md` and the on-disk file will change casing across commits if existing repos have lower-case. — Fix: pick one canonical casing *now* (plan CONFUSION option B) and enforce at write time via a knowledge-kind constants module in `@hyperidle/shared`. The cost of kicking the can further is a breaking rename commit on every existing deployment.

- [medium] `packages/server/src/services/git-export.ts:96–127` — `mapRowToEntry` silently drops L2 rows where `scopeId` is null or empty (`if (!row.scopeId || row.scopeId.length === 0) return null`). No logging, no error path, no surface in `GitExportResult`. A misconfigured product will have its BRIEF.md silently unexported forever. — Fix: log a warn-level event with the item id and layer, and surface a counter in `GitExportResult` (`skipped: number; reasons: Record<string, number>`) so operators can detect the condition.

- [medium] `packages/server/src/services/git-export-runner.ts:132–148` — `commit` uses `--allow-empty-message` alongside a `-m <message>` arg. `buildCommitMessage` always produces a non-empty message, so the flag never triggers. Either defensive noise or a leftover from an earlier draft. — Fix: remove the flag; add a `buildCommitMessage` invariant test that asserts the result is non-empty.

- [medium] `packages/server/src/services/git-export.ts:294–308` — On push failure the code calls `writeLastExport(db, sha, nowFn())` *before* returning the error. This persists a "success" marker (last_commit_sha + last_export_at) for a commit that never reached the remote. `GET /status` will then happily report the commit as exported. — Fix: either (a) split the marker into `last_commit_sha` (local) + `last_push_sha` (remote), updating each independently, or (b) only write `last_export_at`/`last_commit_sha` on a successful push when `remoteUrl` is set. Document semantics: "last_export_at = last successful write to the authoritative destination (local if no remote, remote if configured)".

- [low] `packages/server/src/services/git-export.ts:263` — `computeExportPlan(db)` is called inside the mutex but outside the try/catch for `writePlanToDisk`. A DB read error would reject out of `runGitExport` as an uncaught exception, contradicting the "every call returns its own result object (never throws)" comment at line 171. — Fix: wrap `computeExportPlan` in try/catch and return `{ status: "error", phase: "init" }` (or introduce a `"plan"` phase).

- [low] `packages/server/src/routes/git-export-routes.ts:89–107` — `POST /run` creates a new `GitRunner` per request, even when `enabled=false` (only `repoPath` presence is checked). Wasted work and, if the repo dir doesn't exist, a spawn failure before the service gets a chance to run. — Fix: short-circuit on `!cfg.enabled && !body.force` with a `{status:"disabled"}` return, matching `runGitExport`'s own behaviour.

- [low] `packages/server/src/routes/git-export-routes.ts:36–51` — the local `validationErrorHandler` types `result` with both `success: true | false` branches each carrying `data`. When `success: false`, Zod returns `data: undefined` in practice; the declared type is misleading. Using `validateBody` avoids this entirely (see medium finding above).

- [low] `packages/server/src/services/git-export.ts:360–372` — the event handler reads `loadGitExportConfig(db)` twice per event (once for the debounce-ms, again inside `fire()`). Cheap but redundant — and subtly wrong: if the operator disables the export between the event and the fire, the pending timer still fires (fire() then no-ops, logging the warn). — Fix: either accept the race and comment it, or check `cfg.enabled` again after debounce and drop silently.

- [low] `packages/server/src/services/git-export-config.ts:95–104` — `upsert` constructs a new `updatedAt` inside the helper, so every field in a single PATCH gets a different `updatedAt`. Not user-visible but breaks the convention that one logical patch has one timestamp. — Fix: accept `updatedAt` as a parameter, computed once in `updateGitExportConfig`.

- [info] `packages/server/src/services/git-export-runner.ts:64–72` — env spread `{ ...process.env, GIT_TERMINAL_PROMPT: "0", ... }` propagates every server env var into `git`. `GH_TOKEN` propagation is intentional (plan §7), but `HYPERIDLE_API_KEY` and any future secret also leak into git hooks and credential helpers. — Fix: allow-list the env: start from `{}` and add `PATH`, `HOME`, `GIT_*`, `SSH_*`, `GH_TOKEN`. Matches the "typed + whitelisted" discipline the `@lore` claims.

- [info] `packages/server/src/services/git-export.ts:194–203` — `ensureRepo` does not honour the plan's §3.11 "if `remoteUrl` set: `git fetch origin`; if `origin/<branch>` exists, `git reset --hard origin/<branch>`". The current first-run path initialises an empty repo and then pushes. If the remote already has history, the first push fails (non-fast-forward) and stays in that state across restarts. — Fix: on first-run with a remote, attempt a clone/fetch-reset before falling back to init; or document explicitly that remote must be empty on first run.

- [info] Deployment/H4 — the `HyperIdleDb` type alias (`packages/db/src/connection.ts:5`) is bound to `drizzle-orm/better-sqlite3`, and every call site here (and in the sibling services) uses the synchronous terminal methods `.get()`/`.all()`/`.run()`. Postgres Drizzle uses an async API (`await db.select()...` returns promises, terminal methods differ). This is a codebase-wide H4 concern, not H1-specific, but note that H1 does nothing to make the swap easier: `git-export-config.ts:37,103,122,142` all assume sync. — Fix: tracking issue against H4; introduce a `KvStore` repository shape in the db package that both drivers implement, and let services depend on that.

---

### OK

- Layer compliance. Git export lives in `packages/server/src/services/` (Meta Layer). It is triggered by the Event Bus and by a Meta-Layer HTTP route. The Human Interface never calls git directly; the Agent Runtime never imports git-export. No reach-through.
- Event-bus subscription shape. `registerGitExportHandler` subscribes with `eventBus.on("knowledge_updated", handler)` and returns an unsubscribe — identical to `registerPolicyEngine` (`policy-engine.ts:36`) and `registerSessionReviewCreator` (`session-review-creator.ts:69`). The contract is consistent. (The app-level misuse of that return value is separate — see high finding above.)
- Emit ordering. `knowledge_updated` is emitted in `knowledge.ts:185/276/…` *after* the Drizzle `.run()` commits, so the event handler's `db.select().from(knowledgeItems).where(eq(..., event.itemId)).get()` is guaranteed to see the row. Matches the "emit after durability" contract in `event-bus.ts:73`.
- `factory_settings` schema usage. Keys follow a single `git_export.` prefix, read via `readAllSettings` which filters by prefix, written via UPSERT on the same key set. No silent drift — every produced key appears in `KEYS`, every consumed key goes through `buildConfig`. `writeLastExport` only touches `git_export.last_export_at` / `git_export.last_commit_sha`. Parity with sibling usage in `policy-engine.ts:109–144` (flat keys) is good.
- Drizzle schema parity for `factory_settings` and `knowledge_items` across `schema.ts` and `schema.pg.ts` (both declare the same columns; see `schema.ts:220` vs `schema.pg.ts:220`). The DDL-level swap H4 needs is in place.
- Config flow and disabled semantics. `loadGitExportConfig` returns `null` when disabled *or* when `repoPath` is empty; `readGitExportConfig` always returns the shape for read/status APIs. This split is clean and matches the plan §3.5.
- Optimistic concurrency. No contention on `knowledge_items` in the export path — export only reads; writes go through `knowledge.ts` with the version check already established there. No duplicate concurrency path.
- Commit author identity. Uses `-c user.name=… -c user.email=…` per-commit, overriding ambient git config — correct; does not leak the developer's local identity into operator commits.
- `GIT_TERMINAL_PROMPT=0` / `GIT_ASKPASS=/bin/true` / `GIT_OPTIONAL_LOCKS=0`. All three are well chosen: fail fast on missing credentials, suppress lock files on reads. Matches plan §7.
- Debounce closure shape. The handler carries `pending: NodeJS.Timeout | null` and `disposed: boolean` in closure, with a single `clearPending()` on dispose. No timer leaks on unsubscribe. `@lore` at line 318–323 correctly anchors the known limitation.
- `buildCommitMessage` is pure and unit-testable, sorted entries (`compareEntries` at line 129), deterministic output. Meets plan §3.7.
- HTTP contracts. All four routes (`GET /config`, `PATCH /config`, `POST /run`, `GET /status`) sit under `/api/git-export` and therefore inherit `authMiddleware` (`app.ts:58`). 401 for missing `X-API-Key` is consistent with other routes.
- Idempotence on quiet rerun. The "no commit if unchanged" check goes through `git diff --quiet HEAD` after `git add -A` (`git-export-runner.ts:152–160`) — the authoritative check the plan §3.8 called for, catching line-ending and permission-bit normalization that a byte-compare would miss.
- Crash survivability. Because writeback always runs through `git add -A && git diff --quiet HEAD` before committing, a crash mid-export leaves at most an uncommitted working tree; the next invocation reconciles. No need for a crash-recovery flag in `factory_settings`.
- Export layout on disk. `factory/PRINCIPLES.md`, `factory/FOCUS.md`, `factory/PORTFOLIO.md`, `factory/REFLECTIONS/<topic>.md`, `products/<scopeId>/{BRIEF,ARCHITECTURE,BRAND,PRINCIPLES}.md` — matches `KNOWLEDGE_ARCHITECTURE.md §L2/§L4` and the exports convention in §9 "file structure reflects this". Scope-id keyed product subdirs align with the `scope_id` column semantics.
- Single-node mutex scope. The `@lore` at line 166–172 explicitly marks multi-node as out of scope for v1. Matches plan §3.10. (Call it out in H4 planning: two instances pointing at the same `repoPath` will race on `git add`/`git commit`/`git push` — the mutex is process-local only.)
