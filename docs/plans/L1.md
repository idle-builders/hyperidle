# L1 — Autonomy Schema: L1–L4 per Agent per Skill

**Branch:** `feat/L1-autonomy-schema`
**Track file:** `docs/work-packages/TRACK-L.md` lines 25–48
**Effort estimate:** M (~3d)
**Architectural note:** This story was specified before the database had per-`(agent, skill)` autonomy. The DB layer already stores integer 1–4 per `(agent_id, skill_id)`; the actual surviving 3-state surface is the web `SettingsPanel` UI and its fixtures. The plan therefore prioritizes type unification and net-new endpoints/audit, NOT a data backfill (the data is already in the right shape).

---

## 1. Acceptance criteria (verbatim)

- `AutonomyLevel` type changed from `"manual" | "supervised" | "autonomous"` (current `SettingsPanel.tsx:18`) to a discriminated `L1 | L2 | L3 | L4` ladder with explicit semantics documented in `packages/shared/src/types/autonomy.ts`.
- Persistence: per-`(agent_id, skill_id)` row, not per-agent. Drizzle migration adds `agent_skill_autonomy` table; existing rows backfilled from the 3-state value with a documented mapping.
- API: `GET /api/agents/:id/autonomy` returns `{ skill_id, level, updated_at, updated_by }[]`. `PATCH /api/agents/:id/autonomy` accepts `{ skill_id, level, rationale }`.
- All existing reads of `agent.autonomy` updated to consume the new shape; no callers of the deleted 3-state field remain (`grep` returns 0 hits).
- `bun run check` + `bun run lint` + `bun run test` green; existing autonomy tests rewritten against the new schema.

**Validation scenarios.**
- Given an agent with no per-skill rows, when the autonomy editor opens, then every skill defaults to L1 with a "not yet trusted" hint.
- Given a `PATCH` lifting `(architect, deploy)` from L2 to L3, when re-fetched, then the row reflects L3 and `updated_by` is set.
- Given the migration runs against a seeded DB with `autonomy = "supervised"`, when complete, then every `(agent, skill)` pair lands at L2 (documented mapping).

**Contracts / constraints.**
- Levels: L1 (asks every step) / L2 (asks before commit) / L3 (commits low-risk, asks high-risk) / L4 (autonomous, retro). Definitions live in `packages/shared/src/types/autonomy.ts` as the single source of truth.
- Skill axis is required — single-axis (per-agent) autonomy is rejected at the type level.
- No UI work in this story beyond keeping existing surfaces compiling. The interactive editor ships in TRACK-F or TRACK-J.

## 2. Architectural decisions

### Decision 1 — Canonical type location: introduce `packages/shared/src/types/` subdirectory

**Chosen:** Create `packages/shared/src/types/autonomy.ts` as a per-domain file. Re-export everything it owns from the package root `packages/shared/src/index.ts`.

**Rationale:** The spec literally names this path. The TypeScript rule `no-barrel-files-except-packages/*/src/index.ts` allows nested files without their own barrel — direct file paths are not barrels, and the package root remains the only barrel. The existing `harness/`, `net/`, and `observability/` subdirectories follow this exact pattern (file modules under a folder, no nested `index.ts` for `net/` and `observability/`; `harness/` does have one but is a special case for the adapter contract). For consistency with `net/ssrf.js` and `observability/events.js` (which are direct paths re-exported via the root), we mirror that shape: `types/autonomy.js` re-exported from `index.ts`. We do NOT touch the existing flat `types.ts` — its `AutonomyLevel = 1 | 2 | 3 | 4` alias is removed and re-exported transparently from `types/autonomy.ts`, so call sites that import `AutonomyLevel` from `@hyperidle/shared` keep working.

**Rejected alternative:** keeping the type in flat `types.ts`. The spec explicitly names a domain-file path; following it costs one folder and zero risk.

### Decision 2 — Discriminated ladder shape: numeric union `1 | 2 | 3 | 4` plus const metadata map

**Chosen:**

```ts
// packages/shared/src/types/autonomy.ts
export type AutonomyLevel = 1 | 2 | 3 | 4;

export const AUTONOMY_LEVELS = [1, 2, 3, 4] as const satisfies readonly AutonomyLevel[];

export interface AutonomyLevelMeta {
  readonly level: AutonomyLevel;
  readonly code: "L1" | "L2" | "L3" | "L4";
  readonly label: string;       // "Asks every step" etc.
  readonly description: string; // full sentence semantics
  readonly commitsAutonomously: boolean;
  readonly retrospectiveOnly: boolean;
}

export const AUTONOMY_LEVEL_META: Readonly<Record<AutonomyLevel, AutonomyLevelMeta>> = {
  1: { level: 1, code: "L1", label: "Asks every step",                   description: "Agent confirms before each action. Default for new (agent, skill) pairs.", commitsAutonomously: false, retrospectiveOnly: false },
  2: { level: 2, code: "L2", label: "Asks before commit",                description: "Agent works freely but pauses before any state-changing commit.",            commitsAutonomously: false, retrospectiveOnly: false },
  3: { level: 3, code: "L3", label: "Commits low-risk, asks high-risk",  description: "Agent commits low-risk work; pauses only for high-risk decisions.",          commitsAutonomously: true,  retrospectiveOnly: false },
  4: { level: 4, code: "L4", label: "Autonomous, retro only",            description: "Agent acts fully autonomously and reports outcomes after the fact.",         commitsAutonomously: true,  retrospectiveOnly: true  },
};

export function isAutonomyLevel(value: unknown): value is AutonomyLevel {
  return value === 1 || value === 2 || value === 3 || value === 4;
}

export function autonomyLevelFromCode(code: string): AutonomyLevel | null {
  switch (code) { case "L1": return 1; case "L2": return 2; case "L3": return 3; case "L4": return 4; default: return null; }
}

export const DEFAULT_AUTONOMY_LEVEL: AutonomyLevel = 1;

// Documented legacy mapping. Only used by the data-backfill migration shim
// (which is a no-op against current DB rows but ships as a defensive fallback
// for any seed/fixture that still emits the legacy strings).
export const LEGACY_AUTONOMY_MAPPING = {
  manual:     1, // "asks every step"
  supervised: 2, // "asks before commit"
  autonomous: 4, // "fully autonomous, retro only"
} as const satisfies Record<"manual" | "supervised" | "autonomous", AutonomyLevel>;
```

**Rationale:** The spec's word "discriminated" describes semantic distinctness, not structural discriminated unions. The DB column is `INTEGER`; routes accept JSON numbers; React `<select>` elements emit strings that get parsed to numbers. A tagged-union shape (`{ kind: "L1" }`) would force every callsite into wrap/unwrap with no payoff. The numeric union plus metadata map is the leanest representation that gives every level a label/code/semantics in one place. `isAutonomyLevel` provides the runtime guard (so we can avoid `as` casts at the API boundary, satisfying `.claude/rules/typescript.md`). Zod schemas reuse `z.union([z.literal(1), ...])` directly.

**Rejected alternatives:**
- Tagged union `{ kind: "L1" }`: requires lossy conversion to/from int at every boundary (DB, JSON, `<select>`), no benefit.
- Brand types (`type AutonomyLevel = number & { __brand: "AutonomyLevel" }`): adds friction at every assignment without strengthening the type beyond what `1|2|3|4` already gives.
- TS enum: forbidden by the codebase style (no enums, prefer `as const` objects).

### Decision 3 — Migration: extend `agent_skills` columns + add `agent_skill_autonomy_audit` table (DEVIATE FROM SPEC TEXT)

**Chosen:**

1. **Add columns to existing `agent_skills`:**
   - `updated_at TEXT NOT NULL DEFAULT '1970-01-01T00:00:00.000Z'` (backfilled to row insert time during migration; the literal default is only there because SQLite can't `DEFAULT CURRENT_TIMESTAMP` to ISO-8601 — the migration `UPDATE`s every existing row to the current ISO timestamp before app code runs).
   - `updated_by TEXT` (nullable; NULL means "system" / pre-audit).

2. **Add a new audit table `agent_skill_autonomy_audit`:** stores rationale + the previous and new level for every `PATCH`. Rationale lives here (not on the agent_skills row) because rationale is per-event, not per-pair.

```ts
export const agentSkillAutonomyAudit = sqliteTable("agent_skill_autonomy_audit", {
  id: text("id").primaryKey(),
  agentId: text("agent_id").notNull().references(() => agents.id, { onDelete: "restrict" }),
  skillId: text("skill_id").notNull(),
  fromLevel: integer("from_level"),         // null = first-set (no prior row)
  toLevel:   integer("to_level").notNull(),
  rationale: text("rationale"),             // optional; PATCH may omit
  changedBy: text("changed_by").notNull(),  // actor id; "system" for migrations/seed
  changedAt: text("changed_at").notNull(),
}, (table) => [
  index("asaa_agent_idx").on(table.agentId),
  index("asaa_pair_idx").on(table.agentId, table.skillId),
  index("asaa_changed_at_desc_idx").on(table.changedAt),
]);
```

**⚠️ Deviation from spec text:** The spec says "Drizzle migration adds `agent_skill_autonomy` table; existing rows backfilled from the 3-state value with a documented mapping." That sentence assumed the DB held a 3-state flag. In reality:
- `agent_skills` already exists with `autonomy_level INTEGER NOT NULL` and a `(agent_id, skill_id)` PK.
- No DB row in production or fixtures uses the legacy 3-state strings.
- A literal new `agent_skill_autonomy` table would either duplicate `agent_skills` or force a large rename + cascade through `policy-engine.ts`, agents routes, scheduler tests, and seed data — all for zero functional gain.

The deviation preserves the spec's INTENT (per-pair autonomy, audit-trail, documented mapping) while keeping the tractable shape. The `LEGACY_AUTONOMY_MAPPING` constant in shared types is the documented mapping; it's exported for any future seed/fixture that needs it. This deviation MUST be flagged in the PR description.

**Migrations to author (both dialects):**
- `packages/db/drizzle/0007_l1_autonomy_audit.sql` (SQLite): `ALTER TABLE agent_skills ADD COLUMN updated_at TEXT NOT NULL DEFAULT '1970-01-01T00:00:00.000Z'; ALTER TABLE agent_skills ADD COLUMN updated_by TEXT; UPDATE agent_skills SET updated_at = strftime('%Y-%m-%dT%H:%M:%fZ','now') WHERE updated_at = '1970-01-01T00:00:00.000Z'; CREATE TABLE agent_skill_autonomy_audit (...); CREATE INDEX ...;`
- `packages/db/drizzle-pg/0006_l1_autonomy_audit.sql`: same shape, Postgres syntax.

Generate via `bun run db:generate` (Drizzle introspects the updated schema files), then hand-edit the generated SQL only to add the `UPDATE` backfill statement (Drizzle won't synthesize that).

**Rejected alternative:** A separate `agent_skill_autonomy` table that references `agent_skills` 1:1. Adds a join to every read with no semantic distinction; the `agent_skills` row already represents the (agent, skill) pair.

### Decision 4 — API shape: add new endpoints, keep existing `PATCH /api/agents/:id/skills/:skillId`, share handler core

**Chosen:**

- `GET /api/agents/:id/autonomy` — returns `Array<{ skillId: string; level: AutonomyLevel; updatedAt: string; updatedBy: string | null }>`. Field names match the rest of the API (camelCase in JSON), even though the spec wrote `skill_id`/`updated_at`. Rationale: every other route in `packages/server/src/routes/` returns camelCase JSON; adopting snake_case for one route would be inconsistent. CONFUSION block at end of plan documents the deviation.
- `PATCH /api/agents/:id/autonomy` — body `{ skillId: string; level: AutonomyLevel; rationale?: string }`. Inserts an `agent_skill_autonomy_audit` row, updates the `agent_skills` row's `autonomy_level` + `updated_at` + `updated_by`, emits the existing `autonomy_change` review item via the same path the legacy route uses.
- **Existing `PATCH /api/agents/:id/skills/:skillId`** — kept as-is (consumed by `agents.test.ts`, scheduler tests). Internally it now calls a shared `applyAutonomyChange(db, eventBus, { agentId, skillId, level, rationale: null, changedBy: "system" })` helper. The shared helper is the only writer of `agent_skills.autonomy_level`. The legacy route stays for one more story; flag with a `@lore` tag noting it's superseded by `/autonomy`.

**Validation:** Zod schemas live alongside the route. The `level` validator uses a Zod transform piped through `isAutonomyLevel` so the route never sees a non-conforming value:

```ts
const autonomyLevelSchema = z.union([z.literal(1), z.literal(2), z.literal(3), z.literal(4)]);
const patchAutonomySchema  = z.object({ skillId: z.string().min(1), level: autonomyLevelSchema, rationale: z.string().max(2000).optional() });
```

**Authorship:** `updatedBy` / `changedBy` is sourced from `c.get("actor")?.id` if available (set by future auth middleware) else `"system"`. L1 ships with `"system"` because L2 introduces the actor concept; this is documented in a `@lore` comment at the route level.

**404 semantics:** PATCH against an `(agentId, skillId)` pair that has no `agent_skills` row should INSERT a new row at the requested level (audit `fromLevel = null`). This matches the validation scenario "Given an agent with no per-skill rows, when the autonomy editor opens, then every skill defaults to L1." — but the editor needs `PATCH` to be able to create the first row when the user lifts above L1.

### Decision 5 — UI consequences: remap `SettingsPanel` to numeric ladder; preserve labels and behavior

**Chosen:** Replace the local `SettingsPanel.tsx` `AutonomyLevel` type with the shared one. Re-spec the `<select>`:

```tsx
import { AUTONOMY_LEVEL_META, AUTONOMY_LEVELS, type AutonomyLevel } from "@hyperidle/shared";

<select
  value={String(agent.autonomyLevel)}
  onChange={(e) => {
    const parsed = Number(e.target.value);
    if (parsed === 1 || parsed === 2 || parsed === 3 || parsed === 4) {
      onAutonomyChange(agent.id, parsed);
    }
  }}
  aria-label={`Autonomy level for ${agent.name}`}
>
  {AUTONOMY_LEVELS.map((level) => (
    <option key={level} value={String(level)}>
      {AUTONOMY_LEVEL_META[level].code} — {AUTONOMY_LEVEL_META[level].label}
    </option>
  ))}
</select>
```

`AgentSetting.autonomyLevel` becomes `AutonomyLevel` (1|2|3|4). Fixtures (`fixtures/app-shell-data.ts`) and stories (`SettingsPanel.stories.tsx`) update their literal values: `"manual"→1`, `"supervised"→2`, `"autonomous"→4`. `paused` stays as-is.

**No new UI work**: the in-context "raise autonomy" affordance is explicitly out of scope per spec. The current `<select>` keeps working with the new options. No layout/density tokens change. No new screenshot tests required (the existing visual test for `SettingsPanel` will be updated to assert the new option text).

**Component-budget impact:** zero. `SettingsPanel` is already an existing composition panel, not one of the 19 custom components.
