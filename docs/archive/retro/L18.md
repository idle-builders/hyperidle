# L18 Retrospective — Thread Primitive Attached to Bets, Tasks, Knowledge, and Artifacts

## What Shipped

L18 delivered the Thread surface across four host kinds (bet, task, knowledge_item, artifact) by mounting a unified `HostThreadSection` component that renders the L1 ThreadShell contract with message posting, block-anchored comments, and per-bet artifact-thread summaries. The architecture introduced four new pieces:

- **HostThreadSection** (`packages/web/src/shell/HostThreadSection.tsx`): a single component adapting `useHostThread` to render messages, accept composer input, and optionally display a "Re: <block>" prefill chip with dismiss, scroll-into-view, and focus affordances.
- **ArtifactThreadsSummary** (`packages/web/src/components/ArtifactThreadsSummary.tsx`): a bet-level aggregate that fetches the new `GET /api/bets/:id/artifact-thread-summary` endpoint, displays top 10 artifact threads with last-message snippets, and links to the full artifact view.
- **host-threads service** (`packages/web/src/services/host-threads.ts`): a generalized fetch-and-post service for threads on any host kind, replacing the task-specific patterns with a `resolveOrCreateHostThread(hostKind, hostId, ...)` function and `postPlainHostMessage(threadId, text, clientKey, blockId?)` that threads `blockId` through the message payload.
- **Block popover + block-anchor flow**: `BlockActionsPopover` gained a "Discuss" action; Bet and Knowledge detail pages capture that action, open a popover, and pass the chosen `blockId` into the composer via the prefill chip, which the HostThreadSection forwards to the posting service.

All nine ACs from the spec passed after Round 2 code review fixed eight must-fix findings (1 critical + 7 major). AC §625 (Playwright e2e) carries a note: specs exist but do not run under `bun run test` — they are in CI scope.

**Spec compliance:** 8/9 ACs fully pass; 1 with-finding (m9: Playwright runner integration).

## What Went Well

**Reviewer caught architectural fiction early (F1, F3).** The first architecture claimed React Query integration (`@tanstack/react-query`) without citing a file or verifying the package existed. Round 1 critique (dim 9 score 4) surfaced this; Round 2 rewrote the hook spec against the real `useFetch` primitive with URL-fragment version-bumping (verified at `packages/web/src/hooks/useFetch.ts:46` — the `[url]` dep fires re-fetch on URL string change). This prevented an unbuildable plan shipping to builder.

**Verification-by-source saved a ref-forwarding redesign.** Architecture's Open Question §12 proposed threading a ref callback through the Block primitive to anchor the popover. Reviewer read `packages/design-system/src/Block.tsx:104-124` and discovered Block is not a forwardRef; proposed three alternatives and recommended the smallest-diff path: query `document.querySelector('[data-block-id="<id>"]')` at click time (inside `onOpenActions`). This resolution cost the reviewer 2 minutes of reading; it saved the builder from proposing a Block API change. The builder applied the resolution on read without re-discovering.

**Builder caught hook-sequencing bug (M5) and surfaced it explicitly.** The test for `useHostThread` required five mocked responses to pass because the version-fragment bump was applied to both list and detail URLs, causing a cascade of re-fetches. Builder marked this as NOTICED #1 (potential bug) but did not fix it (deferred for reviewer triage). Reviewer confirmed it as a real bug (M5): removed `version` from `detailUrl`, cut the test's mock count from 5 to 2, and documented the fix. Builder applied. Cost signal: explicit triage of suspected issues before shipping.

**Architecture's mandatory file citations prevented silent mismatches.** Every API claim in the architecture included a line number or file path. During R1 critique, the reviewer cross-checked every claim by reading the source (15 files verified in `architecture-critique.md`, "Verifications I ran"). This caught the React Query fiction and the Block ref-forwarding gap. The designer's quotes were honest; the one minor imprecision (`useBet` "wraps `useFetch`" — it predates the extraction) did not affect L18. **Process signal:** cite the file and line for every primitive / API / hook you reference; don't claim it exists without proof.

## What Didn't

**Designer's first architecture had two verified blockers (F1 React Query, F3 Block wiring).** Round 1 scored dims 8 and 9 at 5 and 4 respectively — both blockers. The designer's initial plan relied on libraries and hooks that didn't exist in the codebase (`@tanstack/react-query`, a hypothetical ref-forwarding Block). Neither was grounded by reading the actual files. Reviewer reading source caught both before builder started. **Process signal:** "It should exist" is not the same as "It does exist." Architect must verify every claim by file cite, not by assumption.

**Round 1 code review found 1 critical + 7 major: the prefill chip bug (C1) drove by test mocking.** WorkBet rendered the "Re: <block>" chip at the page level instead of passing `prefill` to HostThreadSection. The test mocked HostThreadSection to render the chip when the prop arrived — so the test passed with *two* chips in the test DOM but only one in production, and the production one was wired to the wrong handler. **Root cause:** the page-level chip was a workaround to placate the test mock (see comment at `WorkBet.tsx:411-416`). The test-driven workaround bled into production code and broke AC §623 (block-anchored messages). Builder fixed by deleting the page-level chip, passing the real `prefill` prop, and rewriting the test to exercise the production wiring. **Process signal:** test-driven workarounds that live in production are a debt. Reviewer's lens: if the test path differs from the production path, the test is validating a lie.

**M6 — service direction was inverted from the architecture.** The architect said: move `PLACEHOLDER_AGENT_PARTICIPANT_ID` to `host-threads.ts`, reduce `task-threads.ts` to re-export shims. Builder did the opposite: kept `task-threads.ts` as the "real" implementation and had `host-threads.ts` import from it. The architecture's prescribed dependency direction (legacy → new, not new ← legacy) was not honored. Reviewer caught this as M6; builder fixed by swapping the import direction so the shim really delegates. **Process signal:** semantic drift between designer intent and builder implementation. The architecture text said one thing; the code did the inverse. Verification via code read caught it; pre-ship hand-off from architect to builder didn't.

**M7 — incomplete cleanup of observationLog.** Architecture said: delete the `observationLog` field from `DetailItem`, its fixture data, and supporting types. Builder deleted the `ObservationLog` *component* but left the data field, type, and mock entries in `KnowledgeDetail.tsx` and `fixtures/knowledge-data.ts`. The dead field remained, inviting future readers to assume it's rendered. Reviewer found 4 residual occurrences across 3 files; builder cleaned all of them. **Process signal:** "delete X" in an architecture document must specify the scope — field, type, fixture, component, all of the above. Ambiguous delete commands are easy to partially execute.

**Designer-to-builder semantic drift on the summary endpoint.** M6 and M7 are both cases where the architecture's intent and implementation diverged. The pipeline did not have a gate to verify that the builder's code matches the architecture's semantics before code review. Round 1 code review caught both; they were fixed in the fix phase. **Cost:** 2 major findings that could have been caught 1 phase earlier with a "does the diff match the architecture?" semantic scan.

## Patterns Worth Compounding

**Designer fiction — libraries / hooks that don't exist.** F1 claimed React Query in the architecture. The fix: "Cite a file path and line number for every primitive you reference. If you can't cite it, don't claim it exists." Preventive gate: architecture skill should flag any claim without a source file. Reactive gate: reviewer's verification checklist must include "grepping each API claim."

**Test-driven workarounds in production code.** C1 was born when the test mocked a component's behavior to be different from production; the workaround to make the test pass leaked into the production code. Preventive: code review rubric should flag "test path ≠ production path" as a smell. Reactive: when a test involves a mock, pair it with an end-to-end test that exercises the unmocked flow.

**Incomplete cleanup of dead fields.** M7 left residual data after deleting the rendering code. Pattern: "delete X" at the architecture level must name the exact locations (interfaces, fixtures, routes, etc.). Process: architect and builder agree on the scope in writing before implementation begins.

**Unverified items resolved by reviewer reading source — policy gap.** The architecture flagged two Open Questions for "builder-resolves-on-read": the Block.slots API and the ref-forwarding shape. Reviewer resolved them directly by reading source, saving the builder the discovery work. This is efficient, but it raises a design question: when should the architect resolve unknowns before shipping, and when is it OK to defer to the builder's source-reading? Current project posture: if it doesn't change the public API or task list, reviewer-resolves-on-read is acceptable. This should be explicit in the architecture critiqu rubric.

## Lore Worth Saving

**Block primitive does NOT forwardRef.** Capture anchors via data-attribute query at interaction time: `document.querySelector('[data-block-id="<id>"]')`. See `packages/design-system/src/Block.tsx:104-124` for the element structure. The `data-block-id` attribute is on the outer `<article>` (line 109); `data-block-gutter` div is a sibling (line 117). Popover anchor is closest to the click event; no ref-callback needed. (Resolver: reviewer; builder applied on read.)

**Block.slots.inlineAfterPayload exists and works.** `packages/design-system/src/Block.tsx:55-58` exports `BlockSlots` interface with `inlineAfterPayload?: ReactNode`. Page-level code can derive `messagesByBlockId` and pass per-block message slices into `<Block slots={{ inlineAfterPayload: <AnchoredMessages messages={...} /> }} />`. No API change needed. (Resolver: reviewer; cited as ⚠️ UNVERIFIED item §11, resolved by source read.)

**useFetch for cache invalidation uses a version-fragment trick.** `packages/web/src/hooks/useFetch.ts:46` declares a `[url]` dependency on the useEffect. Callers can bump cache by changing the URL string: `useFetch(${url}#v=${version})`. Fragment is stripped by the browser before the network request, so the server sees the same URL; client-side console and middleware see the `#v=N` fragment if they log the full URL (benign). Effect re-fires when the URL string changes, invalidating the previous fetch. This is the cache-buster pattern in L18; it's consistent with useFetch's design. (Lore: cost signal for future hooks — URL-keyed effects enable version-fragment tricks.)

**host-threads service generalization and task-threads shim.** The new pattern: move shared logic to `host-threads.ts`, keep `task-threads.ts` as a thin re-export shim. `task-threads.ts:25-29` re-exports `PLACEHOLDER_AGENT_PARTICIPANT_ID` and `postPlainHostMessage as postRequestMessage`; `resolveOrCreateTaskThread` is a 4-line delegate. `@deprecated` marking on task-threads prevents new callers. Round-trip test `task-threads-shim.test.ts` asserts legacy names still resolve. (Lore: shim-and-deprecate pattern for gradual migration of legacy service APIs.)

## Open Follow-ups (Out of Scope for L18)

- **TaskSheet block popover wiring.** `TaskSheet.tsx:262` mounts `<HostThreadSection inline>` without `prefill`/`onClearPrefill` props. No block-discuss flow exists on TaskSheet today (no Block popover wired to the task body). When the flow extends to TaskSheet, wire the full prefill chain.
- **useHostThread dual-fetch optimization.** Pages call `useHostThread` twice (page-level for inline messages + section-level for the full thread). With M5 fixed, each page load makes 2 list + 2 detail fetches; could drop to 1 of each with a context provider. Captured as m2; not gating L18 ship.
- **IDOR generalization.** L18 reuses `assertBetReadable` for auth on the summary endpoint (consistent with existing GET /api/bets/:id posture). Cross-cutting endpoint-level IDOR checks for all host kinds should be a follow-up (tracked as L8 lore reference).

## Summary

L18 delivered a unified Thread surface across four host kinds with block-anchored message posting. The architecture critique (2 rounds) caught 2 blockers (React Query fiction, Block ref-forwarding unknowns) via source-reading verification. Builder's TDD cycle (1 round) produced 8 must-fix findings in code review; all were closed by fix commits. The retro surfaces a pattern: designer fiction (uncited primitives) and test-driven workarounds (C1) are preventable with stronger process gates. The shipped code adheres to the locked architecture; cost per phase is within expected ranges for a 5-day workpackage involving 4 new surfaces and 1 service generalization.
