User auth flow

Current auth is hand-rolled and leaks session on reload. Migrating to JWT with refresh rotation closes the gap and aligns with the auth-v2 rabbit-hole policy. See RFC-217 for the precedent. 2

Problem

Sessions persist server-side but the browser holds a pointer that is never invalidated on re-mount, so a refresh duplicates the session. Detection runs blind because the session.id never rotates. We have two reproductions in the staging logs from this week.

Constraints

  • Token lifetime stays at 15min; refresh rotation handles renewal.
  • No sticky sessions on the load-balancer.
    • nested: edge-cache stays per-region.
    • nested: session migration is out-of-scope.
  • Telemetry must continue to emit auth.token.rotated.
  1. Land migrations on canary.
  2. Promote on green for 2 hours.
  3. Bake a rollback marker.

The previous incident was caused by an idle session being garbage-collected by the LB before the refresh path was wired up. We do not want a repeat.

// rotateRefreshToken — pure function, no I/O
export function rotateRefreshToken(
  current: RefreshToken,
  now: Date,
): Result<RefreshToken, RotationError> {
  if (current.expiresAt < now) {
    return err({ kind: "expired" });
  }
  if (current.revokedAt !== null) {
    return err({ kind: "revoked" });
  }
  const next = {
    id: randomToken(32),
    parentId: current.id,
    issuedAt: now,
    expiresAt: addMinutes(now, 15),
    revokedAt: null,
  };
  return ok(next);
}

Refresh rotation

A refresh-rotation pattern issues a new refresh token on every access-token renewal, with the parent token revoked after a 60s grace window. See primary source.

When to use

  • Public clients with a non-secret-keeping context (SPAs, mobile).
  • Token lifetimes ≤ 1 hour.
  • Theft-detection requires re-use detection of revoked tokens.
