## 1. Context

`packages/server` is one workspace package holding `routes/ services/ harness/ knowledge/ notifications/ config/ tools/ mcp/ middleware/ auth/ filesystem/`. Core App and Agent Layer both live inside `services/` (82 prod files), distinguished only by hand-typed allowlists in `scripts/au9-direct-handoff-guard.ts` (`AU9_AGENT_FILES`, 9 files) and `scripts/au11-runtime-ownership-guard.ts` (`AU11_AGENT_FILES` 14 + `AU11_EXTRA_AGENT_FILES` 3 + `AU16_AGENT_FILES` 1). `packages/server/package.json` `exports` deep-exports ~15 individual internal files.

AU17 makes the Core/Agent boundary a **build-time fact**: two real workspace packages with a `tsc`-enforced import boundary (an unauthorized cross-package deep import fails to resolve at typecheck), replacing the hand-maintained allowlists. Pure structural migration — **zero behavior change**. Not a place to fix bugs, decouple domains, or refactor logic; only relocate files and add package boundaries.

Target boundary (from `docs/architecture/runtime-simplification.md` + `plans/strategy-kernel-plugin-split/as-should-dependency-graph.md`): Core App owns Work, Conversation, Knowledge, Users, Settings, Routine records/scheduling, Notifications, durable records, domain events, editable config. Agent Layer owns every LLM-capable run: trigger resolution, session requests, provisioning, harness execution, tools, MCP, context assembly, capture/writeback, cost/limits, session lifecycle.

## 2. Constraints

- No change to deployment/build output — the same one process boots and serves in every topology (laptop-solo, shared-backend, remote worker). Confirmed by the WP's topology research: only harness execution crosses a process/machine boundary (`worker-ws.ts`/`remote-harness-adapter.ts`) and that boundary already has zero DB coupling.
- Zero behavior change of any kind. Import-path and file-location changes only. The one allowed code edit beyond relocation is deleting **dead** re-export/barrel lines that the split surfaces (AC-5); no logic edits.
- The boundary must fail at **typecheck**, not merely a guard script (AC-2).
- Newly-visible dead code is **deleted**, never suppressed with a new knip ignore entry (AC-5).
- Monorepo already uses TS project references + root-`tsconfig.json` `paths` + `references`; `check` (package.json:31) = `scripts/typecheck-gate.ts` (per-package `tsc --noEmit` fan-out, auto-discovers `packages/*/tsconfig.json`). The ownership/vocab guards (au6/au7/au9/au10/au11/au12/au13/au14/au18) run in the `lint` npm script (package.json:32), not `check`. Workspaces = `packages/*` (auto-discovered). Vitest uses a root `vitest.config.ts` with a **hardcoded** `projects: [...]` array; each package supplies its own `vitest.config.ts` (`defineProject`). New packages must slot into workspaces, tsconfig paths+references, the `lint` guards, and both vitest configs.

## 3. Target shape — three tiers, acyclic DAG

The migration produces **two new packages plus a slimmed composition root**, not two. Dependency direction (strictly acyclic — required for TS project references):

```
@hyperidle/db, @hyperidle/shared
        ▲
@hyperidle/core-app        (domains, knowledge, notifications, config — imports only db/shared)
        ▲
@hyperidle/agent-layer     (harness/mcp/tools/execution — imports core-app + db/shared)
        ▲
@hyperidle/server          (composition root: HTTP routes + app assembly + process wiring — imports BOTH)
```

**Why routes/app stay in a slimmed `packages/server` (composition root), not split into the two packages.** The WP allows "a thin bootstrap layer (could remain inside a slimmed `packages/server`)." The HTTP route layer is the app's *API surface* — the should-graph's "Core API Surface" node fans out to **both** Core domain services and the Agent Run Read Model. Four core-domain route files (`routes/users.ts`, `routes/teams-routes.ts`, `routes/agents.ts`, `routes/artifacts.ts`) read agent-layer data (`harness-capability-read-model`, `agent-defaults/resolvers`, `cost-cap`) alongside core data. Splitting these route files by ownership would require severing live edges (behavior risk) or would create a core↔agent package cycle. Parking the whole HTTP surface + process wiring in the composition root above both packages is the only acyclic option that needs **zero logic changes**. `packages/server` "slims" by exporting its 84+86 service/domain files out to the two new packages; it keeps the routes, middleware, auth, filesystem-mounter, app assembly, and `createServer` wiring that compose them. This is verified below to have **zero** core→agent, core→boot, and agent→boot back-edges.

**Classification method (reproducible, allowlist-authoritative).** Agent-layer = the conceptual agent set `{AU9_AGENT_FILES ∪ AU11_AGENT_FILES ∪ AU11_EXTRA ∪ AU16_AGENT_FILES ∪ harness/ ∪ mcp/ ∪ tools/ ∪ services/agent-context/ ∪ services/agent-defaults/}`, **grown by import-closure**: any non-composition-root file that imports an agent file must itself be agent-layer (it cannot live in core-app, which is forbidden from importing agent-layer). Core-app = every remaining domain/knowledge/notification/config file. Composition root = routes/middleware/auth/filesystem + app/index/server-factory/session + `schemas/index.ts` + the two inbound-transport handlers (`worker-ws.ts`, `mcp-route.ts`). This closure was computed against the real import graph; it produces **exactly one** required code edit (a dead re-export sever, §5.1) to keep the domain files clean, and otherwise assigns every file to exactly one tier with zero back-edges.

## 5. Required code edits (the only non-relocation changes)

### 5.1 Sever the dead `drainAgentWorkIntents` re-export (enables clean core-app)

`services/agent-work-intents.ts` line ~160 is `export { drainAgentWorkIntents } from "./agent-work-intent-worker.js";`. This single re-export is the *only* thing that makes the intent-recording module (and, transitively, its core-domain callers `task-state-machine.ts` → `bet-kill-cascade.ts`/`dependency-watcher.ts`) reach agent execution. **Delete the line.** No real call site imports `drainAgentWorkIntents` *via* `agent-work-intents`: `agent-layer-boot.ts` already imports it directly from `./agent-work-intent-worker.js`; `agent-work-assistant.ts` only names it in a comment. So this is pure dead re-export surface (exactly what AC-5/knip target). After the sever, `agent-work-intents.ts` imports only `@hyperidle/db` → clean core-app; `recordAgentWorkIntent` (called by core `knowledge-repository.ts`, routes, `task-state-machine.ts`) stays core, matching the should-graph ("Core actions first persist an `agent_work_intents` row"). Zero behavior change.

### 5.2 Rewrite intra-`services/` relative imports to package specifiers

Every surviving relative import that now crosses a package boundary becomes a package import. Two mechanical classes:
- **agent-layer → core-app**: 91 edges across ~40 core files (agent files reading domain data, config, credentials, model-gateway, work/routine services). Rewrite `../services/x` / `../../work-service` → `@hyperidle/core-app`.

- **within a package**: relative imports stay relative (unchanged).

Do this with automated import rewrites, batched per source directory, re-running `au17-ownership.mjs` + `tsc` after each batch. **Note:** this rewrite changes the *specifier* several ownership guards assert on (e.g. au14 checks that `routes/knowledge.ts` routes through `knowledge-repository`, which is now imported as `@hyperidle/core-app`, not a relative path) — see §7b.

## 8. Open questions / risks for architecture-critique

- **D1 — `routine-scheduler.ts` placement (frame deviation).** The should-graph explicitly calls the routine scheduler **Core** ("it stays Core; cron/due-eval is a core domain concern"), but it statically imports agent execution (`runBuiltinRoutine`, `getFactoryCostActual` from `cost-cap`) *and* is imported by agent files (`builtin-routine-handlers`, `tools/create-routine`) — mutual entanglement with agent-layer. A strict acyclic 2-package split with core-app forbidden from importing agent-layer forces it into **agent-layer**. Severing the edge (moving fire-time selection to drain-time) is the documented AU8 residual and a **behavior change AU17 must not make**. Flagged: is agent-layer placement acceptable as an interim, with a note that AU8 relocates it to core-app once the edge is severed? (Recommended: yes.) Consequence tracked in §7b (au6 `ROUTINE_SCHEDULER_FILE` repoint).
- **D2 — `connection-provisioning.ts` core vs agent.** Lands in core-app by import-closure (imports no agent execution) but is conceptually connection *provisioning*. Confirm core placement is acceptable (it is a pure record/resolver; agent-layer imports it — agent→core, fine).
- **D3 — `filesystem/` (8 files) + the mounter.** Placed in composition root because only `server-factory.ts` imports them (constructs `RegistryFilesystemMounter`, injects it). Conceptually they are agent-run workspace provisioning. Boot placement is safe (no coupling either way); alternative is agent-layer. Confirm boot is acceptable.
- **D4 — Guard integrity after the move (RESOLVED in §7b/§7c).** Round-1 + round-2 critique flagged that surviving guards go green-by-absence unless re-rooted, and that they run in `lint`, not `check`. §7b now re-roots **all 9** affected guards (au3, au6, au7, au10, au12, au13, au14, au18-notification, honest-harness) with a sanity-break proof; §7c retires au9/au11. - **D5 — Barrel surface size.** core-app's `index.ts` re-exports ~40 modules' public symbols (the real agent→core coupling); agent-layer's ~30. This is a single curated barrel (on-convention: `packages/*/src/index.ts` is the one allowed barrel) and is vastly better than today's per-file deep exports, but it is not "tiny." Is one barrel per package the right granularity, or should a few domain subpath exports (`@hyperidle/core-app/knowledge`) be introduced? Recommend single barrel for AU17 (subpath granularity is a later concern; introducing it now widens scope).
- **D6 — Is a 68-file composition root "thin"?** It is the HTTP host + wiring, which is the natural composition root, but it is larger than "thin bootstrap" suggests. Justified by the routes-can't-split-without-cycles analysis (§3). Flag for the reviewer to confirm the framing.
- **D7 — Circular runtime import risk.** agent-layer→core-app is a one-way package edge, but several core-app modules subscribe to events that agent-layer publishes at runtime (event bus, not import). Confirm no *static* import cycle is introduced by the barrels (the DAG script proves import-graph acyclicity; barrels must not re-export across the boundary).

## 12. Trade-offs

- **Three tiers, not two.** Adds a composition-root layer (slimmed `packages/server`) the WP framed as "thin bootstrap." Cost: `packages/server` keeps 68 files (routes/wiring). Benefit: the only acyclic split needing zero logic changes; the two *ownership* packages (core-app, agent-layer) are the real deliverable and are cleanly separated.
- **Single curated barrel per package** vs per-file subpath exports. Cost: large re-export lists (D5). Benefit: on-convention, one deliberate surface, unexported internals are unreachable across the boundary (satisfies AC-2/AC-4). Alternative (domain subpath exports) deferred as scope.
- **`routine-scheduler` in agent-layer** contradicts the frame's "Core" label (D1). Cost: a documented interim deviation + an au6 guard repoint (§7b). Benefit: no behavior change; AU8 corrects it when it severs the fire-time edge.
- **Guards re-rooted, not retired** (except au9/au11). Cost: nine guards touched (au3, au6, au7, au10, au12, au13, au14, au18-notification, honest-harness). Benefit: domain-ownership + forbidden-vocab + harness-honesty enforcement (which the package boundary does NOT subsume — same-tier cross-domain writes, Strategy/Fabric vocab, stubbed harness tests) survives the move instead of going green-by-absence, keeping validation-scenario-1 honest and unblocking AU8.
