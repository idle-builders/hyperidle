# AU26 — Challenge core-api's Service boundary: relocate agent-orchestration domain out of core (connections first, then every remaining Service)

## Work package

**Work package.** As a maintainer, I want every core-api Service individually challenged against the domain-only cut bar established during AU21 ("domain is the only accepted reason for such a cut — everything else has to engineer properly around it"), with any Service that is actually agent-session/agent-execution domain — not core product domain — relocated into agent-orchestration, so that core-api's Service list matches what it actually is, not what history left behind. `service_connections` is the fully-investigated, locked case that anchors this WP: a real domain audit (AU21's Decision J) already traced every dependent and concluded it belongs in agent-orchestration, in full — the table, the CRUD service, the crypto decrypt primitive, and the `/api/connections` HTTP surface's backend delegation — not a partial move. That full relocation is built here, replacing the throwaway bake-at-emit mechanism AU21's Decision K1 was forced to ship as an interim boundary patch while connections still sat in the wrong layer. The rest of core-api's Service list (13 more packages — `conversation`, `filesystems`, `git-export`, `knowledge`, `model-gateway`, `notifications`, `org`, `policy`, `review`, `routine`, `settings`, `users`, `work`, plus the smaller `realtime`/`observability` cross-cutting packages) gets the same challenge, not a rubber stamp — each needs an evidenced verdict (stays core / relocates), and anything the audit concludes should move, moves in this WP.

**Why this matters.** AU21 built and shipped a real "orchestration reads zero core-api state" boundary — but that boundary is only as clean as the domain model underneath it. AU21's own Decision K1 had to bake connections metadata onto an emitted request specifically because connections still lived in the wrong layer at the time — a real, if narrow, staleness cost (a connection added or removed between an intent's emit and its drain isn't reflected at spawn) and genuinely throwaway engineering (a new resolver, 8 wired call sites, several tests — all deleted by this WP). Decision J also flagged `model-gateway`'s own core-api placement as an open, unresolved question, never re-examined. Without a systematic per-service challenge, the exact same pattern — a boundary read gets patched with a bake instead of a move, because nobody ever asked whether the *table* was in the right layer — can recur service by service. The maintainer directly confirmed this track's whole point during AU21's build; this WP is that challenge run for real, not just documented.

**Type.** backend.

**What exists today.** core-api holds 14 Service packages today (`packages/core-api/*`): `connections`, `conversation`, `filesystems`, `git-export`, `knowledge`, `model-gateway`, `notifications`, `org`, `policy`, `review`, `routine`, `settings`, `users`, `work` (plus `observability`/`realtime`, smaller cross-cutting concerns). Exactly two have ever been individually challenged against the domain-only bar: `connections` (Decision J — should move, full investigation done, four-increment breakdown locked: extract the AES-GCM primitive to `@hyperidle/shared`, rename the core package to `@hyperidle/credentials` stripped to just the LLM-key catalog, stand up a new SQL-owning `packages/agent-orchestration/connections/` Service, re-host `/api/connections`'s backend delegation + extend `AgentOrchestrationPort` with a read family) and `filesystems` (challenged during AU21's own build — found to be genuinely core-owned as a whole, with one leftover live seam call fixed in place, not a relocation). AU21's Decision K1 (already shipped, CI-green) bakes the held-connection list onto every emitted request as an interim mechanism — `resolveInjectedConnectionsForAgent`, `BakedConnectionsForProvisioning`/`HeldConnectionsForProvisioning`, and 8 composition-root call sites — precisely because the full move hadn't happened yet; this entire mechanism is now known-throwaway. `AgentOrchestrationPort` (a read-only seam, core-ui → agent-orchestration) already shipped in AU21 Increment 6/7, serving per-session cost — the exact re-hosting precedent the connections move and any other relocation reuse. AU20 (a sibling, still-planned WP) already established the "challenge, don't just document" pattern for a *different* axis — reducing each Service's over-broad exposed method surface; this WP runs the same discipline on the *domain-ownership* axis instead.

**What's genuinely missing.** The connections FULL move (not the K1 interim patch) — a new agent-orchestration-owned SQL Service, the crypto/rename split, the deleted throwaway bake mechanism, the `AgentOrchestrationPort` read family. And a real, evidenced domain-ownership verdict for the other 13+ core-api Service packages, run against the same bar Decision J used — not asserted, traced — with any Service that fails the "is this core product domain" test actually relocated, not just flagged.

**Depends on.**
- **AU21** — this WP relocates code AU21 built/touched (`CoreApiPort`, `AgentOrchestrationPort`, the K1 bake mechanism this WP deletes) and reuses patterns AU21 established (the seam, the anti-regrowth guard, the per-Service ACL discipline); it cannot be meaningfully scoped or built until AU21 has shipped those doors.

**Complexity.** L

**Engineering tier.** production (matches AU21's own tier).

**Pre-build gates.**
- **Refinement:** Not required for the connections relocation — the goal, the domain ruling, and the increment breakdown are already settled via AU21's Decision J investigation. Required, implicitly, for each of the other 13 Services' own audit — but that per-Service challenge IS the architecture work itself (see Plan calls), not a separate goal-sharpening pass; there is no fuzzy user-facing goal to refine, only a domain question to answer per Service.
- **Design:** Not required — backend/infra, no new UI surface. Connections' Settings UI frontend is unchanged (only its backend delegation re-points); if the per-Service audit surfaces a Service with a genuine UI-facing consequence, that gets scoped at architecture time, not assumed here.

**Human review gates.** Yes — mandatory for every work package, and load-bearing here specifically: which Services beyond `connections` the audit concludes should relocate is a real, consequential domain call the founder must confirm before those relocations are built, not accepted from an agent's audit alone.

**Plan calls.** Fan out a planner per Service (mirroring AU20's own established "challenge, don't just document" pattern) — one architecture sub-pass per remaining core-api Service package, applying the exact domain-only bar Decision J used (traced dependents, real layer-model reasoning, no "convenience"/"UI owns it"/security-shaped arguments accepted as domain arguments), producing an evidenced stays/relocates verdict per Service. `filesystems` does not need re-challenging (already done, during AU21). For `connections`, do NOT re-derive the design from scratch — Decision J's four-increment breakdown is locked; build it (extract crypto → rename/split the core package → stand up the agent-orchestration Service + delete K1's bake mechanism → re-host the management surface + extend `AgentOrchestrationPort`). For every Service whose audit concludes "relocate," architecture then plans that specific move using the connections relocation as the structural precedent (new SQL-owning agent-orchestration Service, ACL-enforced by a guard, `AgentOrchestrationPort`-style read door back to core-ui if core-ui needs one). Given the number of Services and the likely mix of "trivially stays core" (e.g. `work`, `users`, `settings` — already fixed as core app domains by this track's own charter) versus genuinely-worth-challenging (`model-gateway`'s already-flagged open question; anything else the audit turns up), expect this WP to fan out into several independently-shippable increments, one per relocating Service, the same way AU21 itself did.

**Contracts / constraints.**
- No data migration for any relocation: table *definitions* stay in `packages/db/src/schema.ts`; only the ACL-holder (which Service package is the sole importer of a given table object) changes.
- `Work`, `Conversation`, `Knowledge`, `Users`, `Settings` are fixed as core app domains by this track's own charter (`.pipeline/AU.md`'s own header) — the audit does not re-open whether these five belong in core; it challenges the remaining Service packages, including ones that live inside/adjacent to those domains only incidentally (e.g. a sub-concern of `work` that turns out to be agent-provisioning-shaped, if the audit finds one).
- `server_credentials` / `@hyperidle/credentials` (the LLM-key catalog) stays core-api-owned — Decision J already ruled this on a consumer-locus argument (`model-gateway`, a core-api package, is its dual consumer), not a domain argument; this WP does not re-litigate that specific ruling without new evidence, but DOES re-examine `model-gateway` itself (see below).
- `model-gateway`'s own core-api placement — explicitly flagged as open by Decision J, never resolved — IS in scope for this WP's audit. Re-examine it with real evidence; conclude stays or relocates, don't leave it open again.
- `AgentOrchestrationPort` stays strictly read-only (its existing, already-shipped contract) for every relocation that needs a core-ui-facing read door — mutations stay HTTP-hosted in core-api, delegating to the relocated Service, never routed through a read-only seam.
- Must not attempt to give `agent-execution` any Service/DB access for any relocation — that Layer is structurally disqualified (zero DB credentials, may run on a separate machine) and is not a candidate destination for anything this WP moves.
- Every relocation this WP performs must delete its own throwaway boundary-patch precedent where one exists (connections: delete K1's bake mechanism entirely) rather than leaving both the old patch and the new home coexisting.
- Every Service audit verdict (stays or relocates) must be evidenced — real dependents traced, real layer-model reasoning cited — not asserted from a plausible-sounding narrative.

**Out of scope.**
- Re-opening whether `Work`/`Conversation`/`Knowledge`/`Users`/`Settings` themselves are core domains — that's this track's own settled charter, not an open question.
- Any UI redesign of the Settings connections/filesystems pages — connections' frontend is unchanged; behavior only.
- `filesystems`' own record/routes/UI beyond what AU21 already resolved (mostly stays core; one seam call already fixed) — not re-audited here.
- Moving or renaming the LLM-key catalog (`server_credentials`/`@hyperidle/credentials`) itself, unless the `model-gateway` re-examination produces new evidence that changes Decision J's consumer-locus ruling.
- AU21's assistant-turn output/execution de-specialization (Decision K2) — that is AU27's scope, unrelated to this WP's domain-ownership axis.

**Effort.** L (~2-3 weeks) — the connections full relocation alone is ~4-6d (package relocation + rename + crypto-primitive move + route re-hosting + a new `AgentOrchestrationPort` read family, independently testable per Decision J's four-increment breakdown); the remaining 13-Service audit + any relocations it concludes are the larger, more open-ended remainder, expected to fan out per Service during architecture.

## Acceptance criteria

- `service_connections` (table, CRUD, crypto decrypt path, and the AN2 provisioning operation) has exactly one Service importer — a new SQL-owning agent-orchestration `connections` Service — with zero core-api Service reaching the table directly, enforced by a real guard (mirroring AU21's own anti-regrowth guard pattern), not just documentation.
- AU21 Decision K1's bake-at-emit mechanism (`resolveInjectedConnectionsForAgent`, the `injectedConnections`/`BakedConnectionsForProvisioning` payload field, its 8 composition-root call sites) is deleted entirely; session-launch provisioning resolves an agent's held connections by reading the relocated Service in-layer, at spawn time — a test proves a connection added or removed after an intent's emit but before its drain is correctly reflected at spawn (the staleness regression K1 accepted is gone).
- Every one of core-api's remaining Service packages (`conversation`, `filesystems` excluded as already-audited, `git-export`, `knowledge`, `model-gateway`, `notifications`, `org`, `policy`, `review`, `routine`, `settings`, `users`, `work`, `realtime`, `observability`) has a documented, evidenced domain-ownership verdict against the same bar Decision J used for connections — real dependents traced, not asserted.
- `model-gateway`'s open domain-placement question (flagged, unresolved, by Decision J) is explicitly re-examined and ruled on with real evidence — resolved one way or the other, not left open again.
- Every Service the audit concludes should relocate is actually moved into agent-orchestration in this WP (not deferred to yet another follow-up), with the same rigor as the connections move: a real SQL-owning Service, ACL-enforced by a guard, an `AgentOrchestrationPort`-style read door back to core-ui only where core-ui genuinely needs one.
- The Settings UI's connections page (list, add, delete, validate) works identically end-to-end through the relocated Service, with zero frontend changes required; `model-gateway`'s LLM-provider credential resolution works identically to before the connections split (a real test proves the resolved key/behavior is unchanged).

## Validation scenarios

- Given a user adds a new held connection after a task_run intent has already been emitted but before it has drained, when the session spawns, then the newly-added connection is provisioned into the sandbox — proving the relocation reads live, in-layer, not from a stale emit-time bake.
- Given a core-api Service attempts to import the `serviceConnections` table object directly (a regression attempt), when the guard runs, then it fails the build — the ACL is enforced, not just documented.
- Given the per-Service audit concludes a Service (e.g. a candidate surfaced by the `model-gateway` re-examination) should relocate, when that Service's move ships, then it follows the same guard-enforced, `AgentOrchestrationPort`-fronted pattern as connections — no bespoke one-off mechanism per Service.
- Given `model-gateway` needs to resolve an LLM provider's API key after the connections split, when it calls its existing credential resolution path, then it succeeds identically to before — proving the core-side `@hyperidle/credentials` catalog still works for its consumers regardless of the audit's verdict on `model-gateway` itself.
