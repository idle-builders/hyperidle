# AU26 — Challenge every agent/agent-environment domain sitting in core: relocate what core only administers but never itself works with

## Work package

**Work package.** As a maintainer, I want every domain in core-api that is about an agent or an agent's execution environment challenged with one precise test — **does core ever operationally consume this data/capability for its own purpose, or does core only (a) let a human administer/configure it and/or (b) hold an implementation that is ONLY ever exercised on behalf of an agent's session, never for core's own use?** — with anything that fails that test (core administers but doesn't work with it) relocated into agent-orchestration. Four concrete candidates already surface from real investigation, not assumption: `service_connections` (the fully-investigated, locked case — AU21's Decision J traced every dependent and concluded a full move: table, CRUD, crypto decrypt, HTTP delegation); `filesystems` (its mounting engine, `RegistryFilesystemMounter` in `packages/core-api/filesystems/src/mounter-registry.ts`, contains real `fs.symlinkSync`/`fs.cpSync`/git-worktree mounting logic that core-api holds but NEVER calls for its own purpose — only an agent's session ever gets a filesystem mounted, exactly the same "administers but doesn't work with it" shape as connections, which AU21's own earlier build wrongly waved through as "mostly stays core" without applying this sharper test); `model-gateway` (Decision J flagged its own core-api placement as open, never resolved — it exists purely to resolve models/credentials *for agent runs*, core itself never calls it for anything else); and the `users` table's agent-execution columns (`kind` ai/human, `harnessType`, `modelId`, `modelProvider`, `maxConcurrentSessions` — agent-execution configuration living on the same row as human identity, never challenged). `connections` is built whole in this WP, replacing AU21 Decision K1's throwaway bake-at-emit patch; `filesystems`' mounting engine, `model-gateway`, and the `users` agent-config columns each get the same test applied for real, with an evidenced verdict and (where the verdict is "relocate") an actual move.

**Why this matters.** AU21 built and shipped a real "orchestration reads zero core-api state" boundary — but that boundary is only as clean as the domain model underneath it, and the domain model has never been challenged with a precise, general test — only case-by-case, sometimes hastily (filesystems got waved through during AU21's own build without this test being applied). AU21's own Decision K1 had to bake connections metadata onto an emitted request specifically because connections still lived in the wrong layer — a real staleness cost and genuinely throwaway engineering (a new resolver, 8 wired call sites, several tests — all deleted by this WP). The exact same shape of problem sits, unexamined, in filesystems' mounting engine, `model-gateway`, and `users`' agent columns. Without applying one consistent test across all of them, the codebase will keep discovering these one at a time, each time only after a boundary read forces a throwaway patch instead of a real move.

**Type.** backend.

**What exists today.** `service_connections`: see AU21's Decision J (`.pipeline/work/AU21/architecture.md`) — locked four-increment design (extract the AES-GCM primitive to `@hyperidle/shared`, rename the core package to `@hyperidle/credentials` stripped to just the LLM-key catalog, stand up a new SQL-owning `packages/agent-orchestration/connections/` Service, re-host `/api/connections`'s backend delegation + extend `AgentOrchestrationPort` with a read family). AU21's Decision K1 (shipped, CI-green) bakes the held-connection list onto every emitted request as an interim mechanism — precisely because the full move hadn't happened yet; now known-throwaway. `filesystems` (`packages/core-api/filesystems/src/`): `filesystem-registry.ts` (the record — team-registered repo/doc-set locations), `mounter-registry.ts` (`RegistryFilesystemMounter` and its per-source adapters — the actual mounting engine: symlink/copy/git-worktree-detect logic, composed ONCE at boot in `packages/core-api/src/server-factory.ts:1027` as `new RegistryFilesystemMounter(...)` and injected into `run-orchestration`'s `provisioner.ts`/`filesystem-provisioning.ts` as a same-process `FilesystemMounter` dependency — core-api itself never calls `.mount()`). AU21's own build already fixed the one live seam-call bug (the injected-filesystems LIST is now baked at emit) but left the mounting ENGINE itself sitting in core-api, unchallenged. `model-gateway` (`packages/core-api/model-gateway/src/`) resolves the model + credential for every agent run; owns zero tables itself (confirmed absent from `TABLE_OWNER`) but is core-api-owned today on a dual-consumer argument never re-tested. `users` (`packages/db/src/schema.ts`) carries `kind` (`"ai"`/human), `harnessType`, `modelId`, `modelProvider`, `maxConcurrentSessions` directly on the same table as human identity/team-membership columns — confirmed by direct schema read, never individually challenged. `AgentOrchestrationPort` (a read-only seam, core-ui → agent-orchestration) already shipped in AU21 Increment 6/7, serving per-session cost — the re-hosting precedent every relocation here reuses. AU20 (a sibling, still-planned WP) already established the "challenge, don't just document" pattern for a *different* axis (exposed-method-surface reduction); this WP runs one consistent domain-ownership test instead.

**What's genuinely missing.** The connections FULL move (not the K1 interim patch). A real, evidenced re-application of the "administers vs. works with" test to `filesystems`' mounting engine specifically (distinct from the filesystem *record*, which may genuinely stay core as team-configured data — the engine and the record are not automatically the same verdict). A real, evidenced verdict on `model-gateway`'s own core-api placement. A real, evidenced verdict on whether `users`' agent-execution columns should split out into an agent-orchestration-owned config table (the same "identity stays, operational config moves" shape already applied to credentials vs. connections). Anything the test concludes should relocate, actually relocated — not deferred again. And the test itself stated precisely enough that a future WP can re-apply it to a fifth candidate without re-deriving it from scratch.

**Depends on.**
- **AU21** — this WP relocates code AU21 built/touched (`CoreApiPort`, `AgentOrchestrationPort`, `RegistryFilesystemMounter`'s composition wiring, the K1 bake mechanism this WP deletes) and reuses patterns AU21 established (the seam, the anti-regrowth guard, the per-Service ACL discipline); it cannot be meaningfully scoped or built until AU21 has shipped those doors.

**Complexity.** L

**Engineering tier.** production (matches AU21's own tier).

**Pre-build gates.**
- **Refinement:** Not required for the connections relocation — already settled via Decision J. Required, implicitly, for the `filesystems`-mounting-engine, `model-gateway`, and `users`-columns challenges — but that challenge IS the architecture work itself (see Plan calls), not a separate goal-sharpening pass; there is no fuzzy user-facing goal, only a domain question to answer per candidate, using the test stated above.
- **Design:** Not required — backend/infra, no new UI surface. Connections' and filesystems' Settings UI frontends are unchanged (only backend delegation re-points); if the `users`-columns split surfaces a genuine UI-facing consequence, that gets scoped at architecture time.

**Human review gates.** Yes — mandatory for every work package, and load-bearing here specifically: the `filesystems`-engine, `model-gateway`, and `users`-columns verdicts are real, consequential domain calls the founder must confirm before those relocations (if any) are built, not accepted from an agent's audit alone.

**Plan calls.** For `connections`: do NOT re-derive the design from scratch — Decision J's four-increment breakdown is locked; build it. For `filesystems`' mounting engine: a real architecture sub-pass applying the "administers vs. works with" test specifically to `mounter-registry.ts` — trace whether core-api ever calls `.mount()`/`.captureBack()` for its own purpose (if it genuinely never does, the engine relocates; the filesystem *record* + reachability-probe UI stay core regardless, since those are human-administered configuration data, a different question from who runs the mount). For `model-gateway`: trace its actual dependents (core-side vs. agent-orchestration-side callers), re-test the "dual consumer, consumer-locus" argument under direct scrutiny rather than re-asserting it, and conclude stays or relocates. For `users`' agent-execution columns: propose the identity/operational-config split (mirroring server_credentials-stays / service_connections-moves), tracing every real reader/writer of `harnessType`/`modelId`/`modelProvider`/`maxConcurrentSessions` to confirm a clean cut is possible without breaking `users`' role as the single agent+human identity record. Any candidate whose verdict is "relocate" gets built using the connections relocation as the structural precedent (new SQL-owning agent-orchestration Service or table/module, ACL-enforced by a guard, `AgentOrchestrationPort`-style read door back to core-ui only if core-ui needs one). Expect this WP to fan out into independently-shippable increments — connections first (locked, largest), then the filesystems-engine, `model-gateway`, and `users`-columns moves as separately-scoped increments once each has its own architecture verdict. If, while applying the test to these four, a fifth genuine candidate surfaces, name it and its evidence explicitly rather than silently expanding scope — a real find is welcome, an unbounded audit is not.

**Contracts / constraints.**
- No data migration for any relocation: table *definitions* stay in `packages/db/src/schema.ts`; only the ACL-holder (which Service package is the sole importer of a given table object, or which package composes a given engine) changes. If the `users`-columns split concludes a genuinely separate table is warranted, that IS a schema change and must be scoped explicitly at architecture time, not assumed free.
- `Work`, `Conversation`, `Knowledge`, `Users` (identity), `Settings` are fixed as core app domains by this track's own charter (`.pipeline/AU.md`'s own header) — this WP does not re-open whether these belong in core; it challenges specific agent/agent-environment capabilities embedded inside otherwise-core packages, not the packages themselves.
- The filesystem *record* (team-registered repo/doc-set configuration) and the reachability-probe UI are NOT automatically relocated alongside the mounting engine — apply the test to each separately; a human-administered configuration record that core-ui genuinely displays/edits for its own purpose is a different case from an engine core never exercises itself.
- `server_credentials` / `@hyperidle/credentials` (the LLM-key catalog) stays core-api-owned — Decision J already ruled this on a consumer-locus argument; this WP does not re-litigate that specific ruling without new evidence, but DOES re-examine `model-gateway` itself, a different question (the Service that CALLS the catalog, not the catalog itself).
- `AgentOrchestrationPort` stays strictly read-only (its existing, already-shipped contract) for every relocation that needs a core-ui-facing read door — mutations stay HTTP-hosted in core-api, delegating to the relocated Service, never routed through a read-only seam.
- Must not attempt to give `agent-execution` any Service/DB access for any relocation — that Layer is structurally disqualified (zero DB credentials, may run on a separate machine) and is not a candidate destination for anything this WP moves.
- Every relocation this WP performs must delete its own throwaway boundary-patch precedent where one exists (connections: delete K1's bake mechanism entirely) rather than leaving both the old patch and the new home coexisting.
- Every verdict (stays or relocates) must be evidenced — real dependents traced, real "does core itself call this" tracing — not asserted from a plausible-sounding narrative.

**Out of scope.**
- A blanket audit of every core-api Service package — `conversation`, `git-export`, `knowledge`, `notifications`, `org`, `policy`, `review`, `routine`, `settings` (as a whole), `work`, `realtime`, `observability` are NOT individually challenged here; a quick real check found no agent-environment capability sitting in them that core doesn't itself work with. If a future pass finds one, that's a named, evidenced fifth+ candidate under the same test, not silently folded in.
- The filesystem *record*/reachability-probe UI as a whole — only the mounting engine is challenged; the record's own domain status is a separate, narrower question this WP resolves alongside the engine, not a foregone "stays" conclusion either way.
- Any UI redesign of the Settings connections/filesystems/agents pages — behavior only, no redesign.
- Moving or renaming the LLM-key catalog (`server_credentials`/`@hyperidle/credentials`) itself, unless the `model-gateway` re-examination produces new evidence that changes Decision J's consumer-locus ruling.
- AU21's assistant-turn output/execution de-specialization (Decision K2) — that is AU27's scope, unrelated to this WP's domain-ownership axis.

**Effort.** L (~3-4 weeks) — the connections full relocation alone is ~4-6d (independently testable per Decision J's four-increment breakdown); the filesystems-engine, `model-gateway`, and `users`-columns challenges are smaller individually but each needs its own real architecture pass before sizing its build increment.

## Acceptance criteria

- `service_connections` (table, CRUD, crypto decrypt path, and the AN2 provisioning operation) has exactly one Service importer — a new SQL-owning agent-orchestration `connections` Service — with zero core-api Service reaching the table directly, enforced by a real guard. AU21 Decision K1's bake-at-emit mechanism is deleted entirely; a test proves a connection added or removed after an intent's emit but before its drain is correctly reflected at spawn (K1's staleness regression is gone).
- The "administers vs. works with" test is applied, with real evidence (not assertion), to `filesystems`' mounting engine, `model-gateway`, and `users`' agent-execution columns — each gets a documented stays/relocates verdict.
- `RegistryFilesystemMounter` (the mounting engine) relocates to agent-orchestration if the test concludes core never operationally exercises it — with the filesystem record/reachability-probe UI's own status resolved as a separate, explicit question, not assumed to follow the engine automatically.
- Every candidate whose verdict is "relocate" is actually moved into agent-orchestration in this WP (not deferred to yet another follow-up), with the same rigor as the connections move: guard-enforced ACL, an `AgentOrchestrationPort`-style read door back to core-ui only where core-ui genuinely needs one.
- The Settings UI's connections, filesystems, and agents pages all work identically end-to-end after any relocation, with zero required frontend changes; `model-gateway`'s LLM-provider credential resolution works identically to before the connections split.

## Validation scenarios

- Given a user adds a new held connection after a task_run intent has already been emitted but before it has drained, when the session spawns, then the newly-added connection is provisioned into the sandbox — proving the relocation reads live, in-layer, not from a stale emit-time bake.
- Given a core-api Service attempts to import the `serviceConnections` table object (or, if relocated, the filesystem-mounting engine's internals) directly, when the guard runs, then it fails the build — the ACL is enforced, not just documented.
- Given the mounting-engine test is applied to `RegistryFilesystemMounter`, when its real call sites are traced, then the evidence shows whether core-api ever calls `.mount()`/`.captureBack()` for a core-side purpose or exclusively on an agent's behalf — the verdict follows the evidence, not the connections precedent by default.
- Given a founder sets an agent's model/harness in Settings → Agents after any relocation, when that agent's next session spawns, then it uses the configured model/harness identically to before — proving the split (if any) didn't change observed behavior.
