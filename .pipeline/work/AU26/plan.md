# AU26 — Challenge every agent-related domain sitting in core: relocate what's actually agent-orchestration's

## Work package

**Work package.** As a maintainer, I want every domain *that has to do with agents* but currently sits inside core-api individually challenged against the domain-only cut bar established during AU21 ("domain is the only accepted reason for such a cut — everything else has to engineer properly around it"), with anything that's actually agent-session/agent-execution domain relocated into agent-orchestration — so that core-api holds core product data (identity, work, conversation, knowledge, settings) and agent-orchestration holds everything about how an agent runs. This is deliberately narrower than "audit all of core-api": most of core-api (Work, Conversation, Knowledge, Org, Notifications, Git-export, Review/Policy's human-facing governance) is genuinely core and not in question. The candidates this WP challenges are the ones actually about agents: `service_connections` (the fully-investigated, locked case — AU21's Decision J already traced every dependent and concluded it belongs in agent-orchestration, in full: table, CRUD service, crypto decrypt primitive, and the `/api/connections` HTTP surface's backend delegation); `model-gateway` (Decision J flagged its own core-api placement as open, never resolved — it exists purely to resolve models/credentials *for agent runs*); and the agent-execution-config columns sitting directly inside the `users` table (`kind` ai/human, `harnessType`, `modelId`, `modelProvider`, `maxConcurrentSessions` — genuinely agent-execution configuration, not human identity, even though it's stored on the same row as a human's). `connections` is built whole in this WP — replacing the throwaway bake-at-emit mechanism AU21's Decision K1 shipped as an interim patch — while `model-gateway` and the `users` agent-config columns get the same domain challenge, with a real, evidenced verdict and (where the verdict is "relocate") a real move, not just a finding.

**Why this matters.** AU21 built and shipped a real "orchestration reads zero core-api state" boundary — but that boundary is only as clean as the domain model underneath it. AU21's own Decision K1 had to bake connections metadata onto an emitted request specifically because connections still lived in the wrong layer at the time — a real, if narrow, staleness cost (a connection added or removed between an intent's emit and its drain isn't reflected at spawn) and genuinely throwaway engineering (a new resolver, 8 wired call sites, several tests — all deleted by this WP). The same risk sits, unexamined, in at least two more places: `model-gateway` (an agent-model-resolution Service, core-api-owned on a "consumer locus" argument Decision J never fully re-tested), and `users`' agent-execution columns (an agent's harness/model config living inside the same table as a human's name and team membership — never challenged at all). Leaving these unexamined means the exact pattern that produced K1's throwaway patch can recur: a boundary read gets fixed with a bake instead of a move, because nobody asked whether the data was in the right layer in the first place.

**Type.** backend.

**What exists today.** `service_connections` and its full context: see AU21's Decision J (`.pipeline/work/AU21/architecture.md`) — locked four-increment design (extract the AES-GCM primitive to `@hyperidle/shared`, rename the core package to `@hyperidle/credentials` stripped to just the LLM-key catalog, stand up a new SQL-owning `packages/agent-orchestration/connections/` Service, re-host `/api/connections`'s backend delegation + extend `AgentOrchestrationPort` with a read family). AU21's Decision K1 (shipped, CI-green) bakes the held-connection list onto every emitted request as an interim mechanism — `resolveInjectedConnectionsForAgent`, `BakedConnectionsForProvisioning`/`HeldConnectionsForProvisioning`, and 8 composition-root call sites — precisely because the full move hadn't happened yet; this is now known-throwaway. `model-gateway` (`packages/core-api/model-gateway/src/`: `model-gateway.ts`, `ports.ts`) resolves the model + credential for every agent run; it owns zero tables itself (confirmed absent from `TABLE_OWNER`) but is core-api-owned today on a dual-consumer argument. `users` (`packages/db/src/schema.ts`) carries `kind` (`"ai"`/human), `harnessType`, `modelId`, `modelProvider`, `maxConcurrentSessions` directly on the same table as human identity/team-membership columns — confirmed by direct schema read, never individually challenged. `AgentOrchestrationPort` (a read-only seam, core-ui → agent-orchestration) already shipped in AU21 Increment 6/7, serving per-session cost — the re-hosting precedent every relocation here reuses. `filesystems` was already challenged during AU21's own build (found to be genuinely core-owned as a whole — team-registered resource access, not an agent-identity concern — with one leftover live seam call fixed in place, not a relocation) and does not need re-challenging. AU20 (a sibling, still-planned WP) already established the "challenge, don't just document" pattern for a *different* axis — reducing each Service's over-broad exposed method surface; this WP runs the same discipline on the *domain-ownership* axis, scoped to agent-related data specifically.

**What's genuinely missing.** The connections FULL move (not the K1 interim patch). A real, evidenced domain verdict on `model-gateway`'s own core-api placement (open since Decision J, never resolved). A real, evidenced domain verdict on whether `users`' agent-execution columns (`harnessType`/`modelId`/`modelProvider`/`maxConcurrentSessions` — NOT `kind`/name/team-membership, which stay identity) should be split out into an agent-orchestration-owned config table, the same "identity stays, operational config moves" shape Decision J already applied to connections vs. credentials. Anything the audit concludes should relocate, actually relocated — not deferred again.

**Depends on.**
- **AU21** — this WP relocates code AU21 built/touched (`CoreApiPort`, `AgentOrchestrationPort`, the K1 bake mechanism this WP deletes) and reuses patterns AU21 established (the seam, the anti-regrowth guard, the per-Service ACL discipline); it cannot be meaningfully scoped or built until AU21 has shipped those doors.

**Complexity.** L

**Engineering tier.** production (matches AU21's own tier).

**Pre-build gates.**
- **Refinement:** Not required for the connections relocation — the goal, the domain ruling, and the increment breakdown are already settled via AU21's Decision J investigation. Required, implicitly, for the `model-gateway` and `users`-columns challenges — but that challenge IS the architecture work itself (see Plan calls), not a separate goal-sharpening pass; there is no fuzzy user-facing goal, only a domain question to answer per candidate.
- **Design:** Not required — backend/infra, no new UI surface. Connections' Settings UI frontend is unchanged (only its backend delegation re-points); if the `users`-columns split surfaces a genuine UI-facing consequence (e.g. Settings → Agents needing to read from a different table), that gets scoped at architecture time, not assumed here.

**Human review gates.** Yes — mandatory for every work package, and load-bearing here specifically: the `model-gateway` and `users`-columns verdicts are real, consequential domain calls the founder must confirm before those relocations (if any) are built, not accepted from an agent's audit alone.

**Plan calls.** For `connections`: do NOT re-derive the design from scratch — Decision J's four-increment breakdown is locked; build it (extract crypto → rename/split the core package → stand up the agent-orchestration Service + delete K1's bake mechanism → re-host the management surface + extend `AgentOrchestrationPort`). For `model-gateway`: a real architecture sub-pass re-examining its core-api placement — trace its actual dependents (which are core-side vs. agent-orchestration-side callers), test whether the "dual consumer, consumer-locus" argument that kept it core-side during Decision J still holds under direct scrutiny (not just re-asserted), and conclude stays or relocates. For `users`' agent-execution columns: a real architecture sub-pass proposing the identity/operational-config split (mirroring server_credentials-stays / service_connections-moves), tracing every real reader/writer of `harnessType`/`modelId`/`modelProvider`/`maxConcurrentSessions` to confirm a clean cut is possible without breaking the `users` table's role as the single agent+human identity record. Any candidate whose verdict is "relocate" gets built using the connections relocation as the structural precedent (new SQL-owning agent-orchestration Service or table, ACL-enforced by a guard, `AgentOrchestrationPort`-style read door back to core-ui only if core-ui needs one). Expect this WP to fan out into independently-shippable increments — connections first (locked, largest), then `model-gateway` and `users`-columns as separately-scoped increments once each has its own architecture verdict.

**Contracts / constraints.**
- No data migration for any relocation: table *definitions* stay in `packages/db/src/schema.ts`; only the ACL-holder (which Service package is the sole importer of a given table object) changes. If the `users`-columns split concludes a genuinely separate table is warranted, that IS a schema change and must be scoped explicitly at architecture time, not assumed free.
- `Work`, `Conversation`, `Knowledge`, `Users` (identity), `Settings` are fixed as core app domains by this track's own charter (`.pipeline/AU.md`'s own header) — this WP does not re-open whether these belong in core; it challenges specific agent-related data that happens to be embedded inside otherwise-core packages/tables, not the packages/tables themselves.
- `server_credentials` / `@hyperidle/credentials` (the LLM-key catalog) stays core-api-owned — Decision J already ruled this on a consumer-locus argument; this WP does not re-litigate that specific ruling without new evidence, but DOES re-examine `model-gateway` itself, which is a different question (the Service that CALLS the catalog, not the catalog itself).
- `AgentOrchestrationPort` stays strictly read-only (its existing, already-shipped contract) for every relocation that needs a core-ui-facing read door — mutations stay HTTP-hosted in core-api, delegating to the relocated Service, never routed through a read-only seam.
- Must not attempt to give `agent-execution` any Service/DB access for any relocation — that Layer is structurally disqualified (zero DB credentials, may run on a separate machine) and is not a candidate destination for anything this WP moves.
- Every relocation this WP performs must delete its own throwaway boundary-patch precedent where one exists (connections: delete K1's bake mechanism entirely) rather than leaving both the old patch and the new home coexisting.
- Every verdict (stays or relocates) must be evidenced — real dependents traced, real layer-model reasoning cited — not asserted from a plausible-sounding narrative.

**Out of scope.**
- A blanket audit of every core-api Service package — `conversation`, `git-export`, `knowledge`, `notifications`, `org`, `policy`, `review`, `routine`, `settings` (as a whole), `work`, `realtime`, `observability` are NOT individually challenged here; they are core product domains with no agent-specific slice a quick investigation surfaced as questionable. If a future pass finds a real candidate inside one of these, that's a separate follow-up, not silently folded in here.
- `filesystems`' own record/routes/UI — already resolved during AU21 (mostly stays core; one seam call already fixed); not re-audited here.
- Any UI redesign of the Settings connections/filesystems/agents pages — behavior only, no redesign.
- Moving or renaming the LLM-key catalog (`server_credentials`/`@hyperidle/credentials`) itself, unless the `model-gateway` re-examination produces new evidence that changes Decision J's consumer-locus ruling.
- AU21's assistant-turn output/execution de-specialization (Decision K2) — that is AU27's scope, unrelated to this WP's domain-ownership axis.

**Effort.** L (~2-3 weeks) — the connections full relocation alone is ~4-6d (package relocation + rename + crypto-primitive move + route re-hosting + a new `AgentOrchestrationPort` read family, independently testable per Decision J's four-increment breakdown); the `model-gateway` and `users`-columns challenges are smaller individually but need their own real architecture passes before sizing their build increments.

## Acceptance criteria

- `service_connections` (table, CRUD, crypto decrypt path, and the AN2 provisioning operation) has exactly one Service importer — a new SQL-owning agent-orchestration `connections` Service — with zero core-api Service reaching the table directly, enforced by a real guard (mirroring AU21's own anti-regrowth guard pattern), not just documentation.
- AU21 Decision K1's bake-at-emit mechanism (`resolveInjectedConnectionsForAgent`, the `injectedConnections`/`BakedConnectionsForProvisioning` payload field, its 8 composition-root call sites) is deleted entirely; session-launch provisioning resolves an agent's held connections by reading the relocated Service in-layer, at spawn time — a test proves a connection added or removed after an intent's emit but before its drain is correctly reflected at spawn (the staleness regression K1 accepted is gone).
- `model-gateway`'s core-api placement has a documented, evidenced domain-ownership verdict (real dependents traced, the consumer-locus argument re-tested, not re-asserted) — resolved one way or the other, not left open.
- The `users` table's agent-execution columns (`harnessType`, `modelId`, `modelProvider`, `maxConcurrentSessions`) have a documented, evidenced domain-ownership verdict, distinct from the identity columns (`kind`, name, team membership) that stay core — resolved with real reader/writer tracing, not asserted.
- Every candidate whose verdict is "relocate" is actually moved into agent-orchestration in this WP (not deferred to yet another follow-up), with the same rigor as the connections move: guard-enforced ACL, an `AgentOrchestrationPort`-style read door back to core-ui only where core-ui genuinely needs one.
- The Settings UI's connections page (list, add, delete, validate) and the Settings → Agents page (model/harness configuration) work identically end-to-end after any relocation, with zero required frontend changes; `model-gateway`'s LLM-provider credential resolution works identically to before the connections split.

## Validation scenarios

- Given a user adds a new held connection after a task_run intent has already been emitted but before it has drained, when the session spawns, then the newly-added connection is provisioned into the sandbox — proving the relocation reads live, in-layer, not from a stale emit-time bake.
- Given a core-api Service attempts to import the `serviceConnections` table object directly (a regression attempt), when the guard runs, then it fails the build — the ACL is enforced, not just documented.
- Given the `model-gateway` or `users`-columns challenge concludes a relocation is warranted, when that piece ships, then it follows the same guard-enforced, `AgentOrchestrationPort`-fronted pattern as connections — no bespoke one-off mechanism.
- Given a founder sets an agent's model/harness in Settings → Agents after any relocation, when that agent's next session spawns, then it uses the configured model/harness identically to before — proving the split (if any) didn't change observed behavior.
